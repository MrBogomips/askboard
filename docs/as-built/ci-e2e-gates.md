# As built: `ci-e2e-gates`

Refs #196, #197, #198. No contract set is widened, so no version is bound.

**Runner factor (#196).** In `packages/view/test/browser/harness/perf.ts`: `PERF_RUNNER_FACTORS` (`Linux` 2, `macOS` 3), `perfFactor(runner)` (unset is 1; any other value throws, naming the value and both keys), `PERF_FACTOR` (evaluated at load, so a bad value fails before any judgement), `perfScaled(ms)`, and a `factor` parameter on `perfLine`, `expectMedianWithin`, `judgeMedians` and `perfRuns`. A perf line carries `factor n bound m` only when the factor is not 1. The gates themselves are unchanged. `ASKBOARD_PERF_RUNNER: ${{ runner.os }}` is set only on the step "Browser tests against the built session process" of `.github/workflows/browser.yml`; a test in `tools/ci/e2e-workflows.test.ts` fails if any other step or workflow names it.

**Waits around timed samples (task 1.5).** A fixed wait around a sample caps the scaled bound, so these go through `perfScaled`: the dense Markdown case's wait and test timeout (`markdown-total.browser.ts`), the Document review's waits and test timeouts (`document-review-cost.browser.ts`), the LaTeX ten-items wait and the field-error wait (`latex-bounds.browser.ts`) and the frame's parent wait (`harness/latex-frame.ts`). `harness/perf-files.test.ts` fails when a perf file gives `eventually` a literal wait.

**Keyboard navigation (#197).** The step "Keyboard navigation on (macOS)" of `browser.yml` (macOS only, after the engine install, before the tests) runs `defaults write -g AppleKeyboardUIMode -int 2` and fails unless the value reads back as 2. Probe P1 on a Mac: with `defaults write org.webkit.Playwright AppleKeyboardUIMode -int 0` the keyboard cases fail on WebKit with "ten presses of Tab never reached Answer"; after `defaults delete` they pass. No other workflow writes a `defaults` key.

**Decisions.** D1 to D3 are the architect's defaults: scale the bounds on hosted runners rather than make perf informational; factor 2 on Linux and 3 on macOS, in one table beside the perf helpers; the dense Markdown case takes the same factor. D4 is the PO's answer to Q1 on #197, option (a): turn keyboard navigation on in the macOS job.

**Reopen-session case (g) (#198).** The cause is the test, not the product. Case (g) of `packages/view/test/browser/reopen-session.browser.ts` moves a task, answers, then reopens and closes the ask and reloads. The move's draft record is mirrored 300 ms after the move; the empty record that replaces it goes out 300 ms after the answer; the reopen and the close come within about 110 ms of the answer, before that record. A closed ask's board page mirrors nothing more (the mirror sends only while the board is live), so the empty record never leaves and `board-host` restores the stale record (`received draft {"plan":{"rev":1,...}}`) after the reload. The session process sends one `state` for the reopen and the close together, so the prefill gate never sees an open ask and the product's refusal to fill a closed ask holds. A 600 ms pause between the move and Answer made it fail 3 of 3; after the fix 10 of 10. The fix: before the reopen and the close, the case waits (`eventually` over `sentDrafts`) for the last draft record the page sent to hold no work for the question, which establishes that `board-host` holds no record. Every assertion is kept; no `quiet` call or fixed wait was added; no product code changed. #198 moved from `sev:M` to `sev:L`.
