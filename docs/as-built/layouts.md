# As built: `layouts`

In code since `layouts`: the walker `contract/src/nested-items.ts` (`LAYOUT_TYPES`, `isLayoutType`, `LAYOUT_MAX_DEPTH` = 4, `layoutListsOf`, `nestedItemsOf`, `mapNestedItems`, `layoutDepthProblem`; plain ECMAScript, no JSON, no registry), through which every reader of a question's `items` that must see the items inside layouts goes, and the source guard `tools/nested-items.test.ts`, which lists every direct read left (each with its reason, per package) and fails on a new one; four registry entries under `widgets/{stack,row,group,tabs}/` (a Row of two to four items with weights 1 to 4 keyed by item ID, a Group's title and description, Tabs of two to eight titled tabs with their own IDs), `layoutItem` composed into the question props only when the registry holds a layout and reserved as a type name, `LAYOUT_WIDGETS` in the fixtures for `withWidgetTypes`, and the skill's generated `{{layoutNote}}`. The ask's checks: `placedItem`, `itemKey` and `innerItemOf` recurse through the layouts, a problem inside a layout names the inner item (each placed item carries its question's path, `questionAt`), `layoutDepthProblem` runs before the schema in `validateAskRequest` (and `validateAskRequestOver`, which runs the same pipeline over a registry, for the tests) and for each `add` of `update`, so a hostile nest never reaches Ajv, and a molecule definition may not hold a layout. In `core`: the answer's value map, `editedProps`, the graph and `fetch` (a layout's full value holds each item inside as the answer left it; a layout is never given a value, a result or a derived key) through the walker, `holderOf` and the merge of a `change` at any depth, and `BoardModel`'s `#held` and `inUse`: every item ID at every depth stays held after a revision or a delete (a deleted question's IDs, top-level ones included, are refused later and `fetch` of one answers `deleted`), and `updates.ts`' `inUseRefusal` holds a molecule reference's ID against plain items, never pruned, the holding question's own included. In `view`: `ItemProps.renderItem` and `BoardContent.entries` appended to the port, `RenderItem` giving every item its own frame, boundary, read-only state and revision step, `view/src/nested-items.ts` (the one helper over the walker for the tracker, `componentsOf`, entries, drafts, reasons, revision confirmation, `widgetChanges` and the board page's act checks, so a nested item's value, result and entry are mirrored, restored and sent, and an act naming a layout is refused), `catalog/{stack,row,group,tabs}/` (a Row's items stack in order when each would get less than 240 px, measured with a `ResizeObserver` on the Row; the Tabs on Radix Tabs from the `radix` chunk, every panel force-mounted so a hidden item reports ready and keeps its draft, with a destructive dot and the string `tabs.needsCorrection` on a tab whose panel holds a field to correct; no `style` attribute anywhere), and Snapshot kept renders read through the walker (`keptComponents`). Browser scenarios: `layouts.browser.ts`, `tabs.browser.ts`, the tab triggers in `hover-audit.browser.ts`, `layouts-session.browser.ts` and `layouts-snapshot.browser.ts`. Versions: input format 1.10, tool envelopes 1.10 and board document 1.9, bound on 2026-11-07 one minor past atoms' and confirmed on 2026-11-08 on main e87841d5, each one minor past `main`'s (output format 1.9, board protocol 1.7, Snapshot data 1.1 and view manifest 1.1 unchanged).
