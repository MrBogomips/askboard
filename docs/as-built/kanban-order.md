# As built: `kanban-order`

In code since `kanban-order` (Issue #79): the Kanban's cards are ordered within their column, by drag and from the keyboard, and the answer carries the order. `contract`'s generic diff (`packages/contract/src/widgets/element-diff.ts`) gained a grouped flat list: `ListShape.group`, the field each element holds naming its group, order counting within a group only (a grouped list is flat, so its shape names no `children`; `FLAT_ONLY`). `elementChanges` takes the grouped branch (`groupedChanges`, `groupsOf`, `groupStayers`, `longestKeeping`) when a shape has `group`, and gives the changes group by group in the code-unit order of the group values, each element in edited order giving an `add`, or its `set`s then a `move` when it is outside its group's longest run in the sent order; `add` and `move` name as `after` the preceding element of the same group, omitted for the group's first, and never a `parent`; a group the user kept gives no `move`; among runs of equal length the run keeping most elements whose group did not change stays (`longestKeeping`, dynamic programming over a weight of the run's length first and a kept-group flag second; where the flags do not differ it is `longestIncreasing` as before; equal ties go to the run ending last, each link to the latest equal predecessor), so a card moved into another column is the one that moves. `applyElementChanges` rebuilds a grouped list: a placed element's group must be a string and its `after` an element of that group, else the rebuild throws and the answer is refused (`element-diff.ts` has its own internal `placeIn`, unrelated to the widgets' `placeIn` below). Other shapes are unchanged. `KANBAN_SHAPE` is `{elements: "cards", group: "column"}`; `kanban-changes.json` admits, beside the `set` of `<item>.<card>.column`, a `move` of `<item>.<card>` with an optional `after` and no `parent` (`KanbanColumnChange`, `KanbanMove`, `KanbanChange`); the fixtures are in `contract/src/fixtures/kanban-order.ts` (`KANBAN_ORDER_ITEM`, `KANBAN_REORDERED_PROPS`, `KANBAN_PLACED_PROPS`, `KANBAN_BOTH_PROPS` and their changes, tests only). `core` has no source change: its round trip (`roundTripProblem`) already rebuilds the edited value exactly and checks the changes against the type's schema, so a reorder is logged with its `move`s and a value whose changes do not rebuild it is refused with the log unchanged (NFR-10).

In `widgets/src/kanban/`: `model.ts` holds `arranged(sent, raw)` (the value the changes of `raw` against `sent` rebuild: `raw`'s order in each column, the flat list in the interleaving the inverse gives; idempotent), `placeIn(props, card, column, slot)` (the slot among the column's other cards, clamped; into an empty column the card keeps its index; identity where nothing changes), `moveWithin` ("Move up", "Move down", "To top" and "To bottom" through `placeIn`), `moveTo` ("Move to…", still one `set` at the card's sent place), `movedOf` (the cards the changes name, so the counter equals what the agent receives) and `valueFor` (one diff of the arranged value against the sent props; `undefined` for no change, so a move put back leaves no value). `props.ts`' `valueFits` takes a held value only when it holds the revision's columns and cards with their labels and descriptions, in any order, and is in normal form (only `set`s of `.column` and `move`s, and the changes rebuild it); `shownProps` falls back to the agent's props otherwise. `drop.ts` (no React) holds `slotAt(middles, clientY)` (the number of the column's other cards whose middle is at or above the pointer: before the first card whose middle is below it, else last), `DragState` `{dragging, over?: {column, slot}}`, `indicatorOf`, `lineOf` (the line before the card at the slot or after the last, none for the card's own place, an empty column or another column) and `afterDrop`; `drag.ts` reads `location.current.input.clientY` and the other cards' boxes in the column's `onDragEnter`, `onDrag` and `onDrop` (Pragmatic drag and drop 4.0.0's documented events; no new dependency); `card.tsx` carries `data-drop-line` and `aria-posinset` and `aria-setsize` (the card's place in its column's group), `classes.ts` the line, from the tokens, with no `style` attribute. `keys.ts` holds `kanbanPressOf(input)` (Alt+Shift with Up and Down, Alt+Shift with Home and End, Ctrl or Cmd with Shift and Up and Down, each held exactly, never while composing, Ctrl and Cmd together never; the arrow keys alone still move the current card) and `kanbanTools` (the five tools' enabled flags: up and top off for the column's first card, down and bottom for its last, all off with no current card, an unknown card or a read-only Kanban); `widget.tsx` prevents the default of a bound press also where it cannot act, acts only when the Kanban is not disabled, keeps the moved card current and refocuses it after the next props are drawn, and puts the four tools before "Move to…" in `MoveToolbar`. Four strings in both tables (`kanban.moveUp`, `kanban.moveDown`, `kanban.toTop`, `kanban.toBottom`; the Italian texts "Sposta su", "Sposta giù", "In cima", "In fondo" to review). The Approval summary needs no code: a `move` is one "moved" line naming the card. `skills/askboard/references/widgets/kanban.md`, `items.md` and `answers.md` teach the order (the `cards` list gives each column's order; how to apply a `set` and a `move`), regenerated by `bun run build:skills`. Browser scenarios: `kanban.browser.ts` (drag within and across columns with the line, each card dragged back, Escape, every key and tool, read-only once the ask closes), the Kanban in `hover-audit.browser.ts`, `edit-widgets-session.browser.ts`, `edit-widgets-snapshot.browser.ts`, `edit-widgets-it.browser.ts` and `keep-mine-reload-session.browser.ts`; the conformance case is in `edit-widgets.e2e.ts`.
