## Goals / Non-Goals

**Goals:**

- Each type is a registration: its own folders in `contract` and `widgets`, one registry line, its teaching text, its strings. The shared changes are generic: a diff shape, a changes check and package stylesheets, which later widgets reuse (the Diagram, Document review's Markdown, the Form).
- Every answer of the three carries only the changes its type declares, checked by `ask-core` whatever the board sends.
- KaTeX renders agent text as data, with no request.

**Non-Goals:**

- Resizing, adding or deleting entries, cards, lanes or columns; reordering cards within a column; a zoom control (proposal, open questions 5 and 6).
- A check that a range keeps its length (open question 9).
- The Diagram's renderers and their `renders` (`diagram-render`).

## Decisions

### 1. One change, three registrations (open question 1)

The three widen the same four sets, append to the same registry, strings, skill and chunk sizes, and give no result, so one binding and one rebase serve them. Registry order follows the PO's order: `latex`, `kanban`, `timeline`, after `main`'s types and `approval-scale-ranking`'s. Each type has `packages/contract/src/widgets/<type>/` (`<type>-props.json` `urn:askboard:input:<type>-props`, `<type>-changes.json` `urn:askboard:output:<type>-changes`, `constants.ts`, `checks.ts` plain with no Ajv so a chunk may import it, `wording.ts`, `widget.ts`, `index.ts`) and `packages/widgets/src/<type>/`. Nouns: "a LaTeX", "a Kanban", "a Timeline". No entry declares `result` or `derived`. FR-11's "Rendering" for LaTeX is the board's work and never reaches the agent.

### 2. The whole-field shape lands here (open question 2)

`ElementShape` gains `FieldsShape = {readonly fields: readonly string[]}`, with `diagram-render`'s name and semantics (its design decision 2, read at 9281d923). Over it, `elementChanges` compares each named field as a JSON value and gives `{op: "set", target: "<item>.<field>", value}`, with `null` for a field that is gone, in the shape's order. A named field holding `null` reads as absent, as in the list and keyed shapes: a `set` to `null` applies as a delete, so an edit that turns a field to `null` does not round-trip and `ask-core` refuses it (no type of this change admits a `null` field; `diagram-render` inherits the rule). A difference in any other key throws a problem naming the item and the key, which `ask-core` turns into a refusal. `applyElementChanges` sets the fields back with `define`, so that `__proto__` stays a key. A shape is told apart by `"fields" in shape`; no reader outside `element-diff.ts` reads `elements` (task 0.2 lists the readers). `spine-update-draft.md` blocks 1 and 2 carry `diagram-render`'s AD-20 blocks 3 and 4, with a LaTeX expression as the example. `diagram-render` drops its own task 1.1, its blocks 3 and 4 and its ADDED requirement of the same name, which this change's contract delta holds, and borrows `FieldsShape`.

*Alternatives:* the expression as a result `{expression}` (AD-20 keeps edits of agent content in values); LaTeX waiting for `diagram-render`, which comes later in the PO's order.

### 3. LaTeX's entry (open question 4)

Props `{expression}`, a string of 0 to `LATEX_EXPRESSION_MAX_CHARS` = 2,000 characters, `additionalProperties: false`. Characters are code points, as JSON Schema's `maxLength` counts them, in the schemas, `checks.ts` and its wording alike (group 1 review X-1). Shape `LATEX_SHAPE = {fields: ["expression"]}`. Changes: an array of `set`s whose target matches `^[A-Za-z0-9_-]{1,64}\.expression$` and whose value is a string of at most 2,000 characters. The contract never parses LaTeX (KaTeX is a view dependency), but its check reads the expression's control words and nesting in one linear pass, `scanLatex(text)` in `checks.ts`, which gives `{refused, depth}` and replaces task 4.5's `latexDefiningCommand` (group 4 review S-1; 4.7 re-review X-1 and X-2; decision 7, Bounded work):

- Control words are read as KaTeX's lexer reads them: a backslash then `[A-Za-z@]+`, else a backslash and one character, so `\\def` is a line break and `\left` is not `\let`. `refused` is the first control word that defines a macro, one of `LATEX_DEFINING_COMMANDS` in `constants.ts` (KaTeX 0.19.1's `def` functions `\def`, `\gdef`, `\edef`, `\xdef`, `\global`, `\long`, `\let`, `\futurelet`, and its macros `\newcommand`, `\renewcommand`, `\providecommand`), or that holds `@`, KaTeX's internal names (`\df@tag`, `\current@color`, `\@ifnextchar`, …), which no author needs.
- `depth` is the most levels open at once, counted as KaTeX nests them. A level opens at `{`, `\bgroup`, `\begingroup`, `\begin` and `\left`, and closes at `}`, `\egroup`, `\endgroup`, `\end` and `\right`; the environment's name in braces after `\begin` or `\end` is no level, and a closer with no level open closes nothing (KaTeX refuses it). `^` and `_` open a level for their argument, which closes with the group that opens next if one opens before any other token (blanks skipped), else after the next token: `x^{y}` is 2 deep, `x^y` 1. Control symbols (`\{`, `\}`) are no level.
- A brace KaTeX reads as text closes nothing, or a nest could hide behind closers that do not close (probed on 0.19.1: `\sqrt{%` and a line feed, `\sqrt{\verb|}|`, ``\sqrt{\char`}`` and `\sqrt{\show}`, each repeated 10 times with 10 closing braces, nest 10 deep). In a comment, from a `%` to the next line feed, and in a `\verb` body, read as KaTeX's lexer reads it (`\verb` or `\verb*`, a delimiter, then up to the same delimiter before the line ends), closers count for nothing while openers still count, so a reading that differs from KaTeX's only refuses more: inside `\url{…}` and `\href{…}`, KaTeX reads `%` as a character, and the scan, ignoring the closers after it, counts more, never less. After `\char` and a backquote, and after `\show` and its blanks, the next character or control sequence is consumed and is no group.
- KaTeX 0.19.1 lets no command stand unbraced as its own argument (`\frac \frac x x x` fails: "Unexpected end of input in a macro argument"), so arguments nest only through groups and scripts; a source guard keeps it so (task 4.9).

`latexPropsProblems` words a definition "the expression defines a macro with `\def`, which a LaTeX item does not allow", an internal command "the expression names `\df@tag`, one of KaTeX's internal commands, which a LaTeX item does not allow", and a depth past `LATEX_NESTING_MAX_DEPTH` "the expression nests 14 levels deep, more than the limit of 12" (the numbers as read; the limit as task 4.10 measures it). The scan reads every character once, with no nested quantifier and no backtracking, and runs only on a text within the 2,000 code points. The registry runs the check on what an agent sends and, through `valuesProblem`, on an answer's edited value, so `ask-core` refuses either. No schema set moves: these are checks, not schemas. Skill draft: use "one mathematical expression in LaTeX that the user reads and corrects, with a live preview"; notes "The answer's change is one `set` of `<id>.expression`: the whole expression as the user wrote it, which may not parse." and "KaTeX renders it: `\href`, `\url` and `\includegraphics` show no link or image; a macro definition (`\def`, `\newcommand`, …), a KaTeX internal command (a name holding `@`) and a nest deeper than `LATEX_NESTING_MAX_DEPTH` levels are refused." Example: `{type: "latex", id: "formula", props: {expression: "x = \\frac{-b \\pm \\sqrt{b^2-4ac}}{2a}"}}`.

### 4. Kanban's entry

Props: `columns`, 2 to 12 `{id, label}` (label 1 to 60), and `cards`, 1 to 200 `{id, label, description?, column}` (label 1 to 200, description 1 to 500), each `additionalProperties: false`. `checks.ts`: IDs unique across columns and cards (AD-7, child IDs within their item); each card's `column` names a column. Problems name the element: `card "fix-login"`. Shape `{elements: "cards"}`. Changes: `set`s only, target `^<id>\.<id>\.column$`, value an ID. Skill draft: use "cards the user moves between 2 to 12 columns, such as statuses, priorities or owners"; note "Each card names its `column` by ID; the answer's changes are `set`s of `<id>.<card>.column`. The user only moves cards: their order, labels and the columns stay." Example: three columns, three cards.

### 5. Timeline's entry

Props: `lanes`, 1 to 20 `{id, label}` (label 1 to 60), and `entries`, 1 to 200 `{id, label, lane, date?, start?, end?}` (label 1 to 200), dates in the Gantt's `fullDate` pattern. `checks.ts`: IDs unique across lanes and entries; `lane` names a lane; an entry holds `date` alone or `start` and `end` together ("an entry holds `date` alone, a milestone, or `start` and `end`, a range"); every date exists and lies within `GANTT_FIRST_DATE` and `GANTT_LAST_DATE`, through the date checks the Gantt's props use; `end` is on or after `start`. One object schema with optional dates and the rule in the check gives one worded problem, where a `oneOf` would need a `schemaErrors` hook. Shape `{elements: "entries"}`. Changes: `set`s only, target `^<id>\.<id>\.(lane|date|start|end)$`, value an ID or a full-date; never `null`, so no date can be removed. A milestone given an `end`, or a range losing one, is refused by the edited props' check. Skill draft: use "milestones and date ranges the user moves in time and across lanes, as in a roadmap"; note "An entry is a milestone with `date` or a range with `start` and `end` (inclusive), in a `lane`; the answer's changes are `set`s of `lane`, `date`, `start` and `end`." Example: two lanes, a range and a milestone.

### 6. Changes checked against their type (open question 8)

`contract` exports `widgetChangesProblems(item: {type, id}, changes, types = WIDGET_TYPES): readonly Problem[]`, beside `widgetResultProblems`. It validates `changes` against the entry's `edits.changes` through the shared widget validator, compiled once per type, and prefixes `item <id>: `, returning every problem. An entry without `edits` refuses any change; an unknown type gives none. In `widget-values.ts`, step 3 computes each value's changes once, inside `roundTripProblem`'s `try`, so a throw of `elementChanges` (a fields shape's unnamed key) is a refusal naming the item and the key, the key cut as `operationOf` cuts a target; the round trip runs on them, then `widgetChangesProblems`, with `[]` for a type that has no shape (Approval and Ranking answers carry no changes); the first problem refuses the answer (`content`), so nothing is appended, kept or published. The changes check stays after `valuesProblem`, whose props bounds keep its input small (group 1 security review). A decline carries no value and runs nothing. `core` names no type. The check runs for every type: task 2.1 replays the Tree, Gantt, WBS and Gantt plan suites, and a Tree or Gantt edit that fails its own schema stops the task for `/opsx:update`. `spine-update-draft.md` block 3 records the rule in AD-20.

*Alternative:* a check in each new type's `checks.ts` comparing sent and edited values, a new registry seam that duplicates the changes schema.

### 7. The LaTeX component (open questions 3 and 4)

`packages/widgets/src/latex/`:

- `render.ts`: one options object built fresh for each call: `displayMode: true`, `throwOnError: true`, `trust: false` (the literal, never a function), `strict: "ignore"`, `maxExpand: 1000`, `maxSize: 20`, `output: "htmlAndMathml"`, and `macros: {}` new each time, so `\gdef` never outlives a render. `renderInto(element, expression)` calls `katex.render`, which builds nodes and sets styles through the CSSOM; it catches every error, not only `ParseError` (a browser's smaller stack may throw a `RangeError` on a deep nest): an `Error` gives `{error: message}`; any other thrown value gives a failure with no text, for which the component shows the string tables' "The expression could not be drawn." (task 5.1 moves the English literal task 4.1 built out of `render.ts`). `katex.render` empties its element before it parses (0.19.1, `katex.mjs:16313`), so `renderInto` renders into a scratch `span` made from `element.ownerDocument` and, on success only, moves its children into the element: a failure leaves the last good preview, which a test checks with real KaTeX (as built in task 4.1). `parseProblem(expression)` runs `katex.renderToString` with the same options, for unit tests in Bun (no DOM); nothing ever puts its output into markup. Both run decision 3's `scanLatex` first (task 4.11): a refused command or a depth past the limit gives `{refused: {command}}` or `{refused: {depth, limit}}` and KaTeX is not called, so every caller of `render.ts` is bounded, not only the component.
- **Bounded work** (group 4 review S-1 and the 4.7 re-review's X-1 and X-2, folded on 2026-11-07). `maxExpand` counts expansions, not the tokens they emit, so `\def\b{<900 x>}\def\a{\b…\b}\a` within 2,000 code points drew 36,011 nodes in 3.3 seconds in Chromium at 998 code points and did not finish in 280 seconds at 1,998. The bounds are on the source, in decision 3's `scanLatex`, run by the contract on what reaches `ask-core` and by `renderInto` before KaTeX:
  - *No definitions.* No expression holding a macro definition renders.
  - *No internal names.* KaTeX also defines macros by side effect: `\tag` defines `\df@tag` and `\color` defines `\current@color` with the author's text (`katex.mjs:14007`, `:7748`), and its lexer reads `@` as a letter, so the source can call them: `\current@color` typed 78 times after a 900-glyph color took 10.2 seconds, and the two combined drew 504,228 nodes in 18.6 seconds at 1,636 code points in Chromium (4.7 re-review X-1). Every control word holding `@` is refused. Task 4.5's claims, that the list held "every way KaTeX defines a macro" and that none of KaTeX's macros repeats its argument, were false. What holds is narrower: of the control words without `@`, none drew more than 3.4 times the markup of its 200-glyph argument three deep (task 4.5's probe), and a source guard (task 4.8) checks that every name `katex.mjs` defines by side effect (`macros.set(` with a literal name, a `\gdef` in a macro's body) holds `@` or has a fixed body (`\cr`, `|`, `\|`), and that no macro whose name lacks `@` calls a name defined with author text. A bound on the calls of internal or author-defined macros is then not needed: no macro the source can call holds author text.
  - *Bounded nesting.* Output size does not bound render cost. Without any macro, about 130 nested vertical-list constructs (`x^{`, `\sqrt{`, `\frac{…}{x}`, `\hat{`, `\overbrace{`, `\cancel{`, `\stackrel{x}{`, `\boxed{`; 521 code points for `x^{`) crash Chromium's renderer, and the parent page with the sandboxed frame; and WebKit's MathML layout doubles with each nested numerator (18 deep: 1.4 seconds; 20: 5.4; 30: over 30) (4.7 re-review X-2). `scanLatex`'s depth is refused past `LATEX_NESTING_MAX_DEPTH`. The limit is measured, not chosen: task 4.10 renders each construct at increasing depth in Chromium and WebKit with KaTeX's fonts loaded, alone, repeated side by side to 2,000 code points and, for a construct whose time doubles per level, as a branching nest (a chain whose deepest levels each hold two copies, which multiplies the doubling), and takes the largest depth at which every fixture renders in under 1 second, half the 2-second bound, with no crash; it then renders every control word `katex.mjs` names nested to that depth. A limit under 8 stops for `/opsx:update`. The reviewer's estimate was about 12 (16 numerators: 364 ms in WebKit, one nest, no fonts). Measured: (filled at task 4.10) "Measured on <date> on <machine>, Chromium <version> and WebKit <version>, KaTeX's fonts loaded: limit <n>; worst fixture at the limit <fixture>, <ms> ms in <engine>."
  - `maxExpand: 1000` stays, bounding the expansion of KaTeX's macros. `render.test.ts` pins KaTeX at 0.19.1, so a bump re-reads the list and the source guards and re-runs task 4.10's probe, which is committed for that purpose.
  - *Rejected:* rendering in a worker with a deadline. `katex.render` needs a DOM, which a worker lacks; a worker could only run `renderToString`, whose markup the page policy's `style-src-attr` blocks and which decision 7 never puts into markup; and the review measured the cost in the DOM build and layout on the page's thread, which a worker's deadline cannot stop. Also rejected: counting the parse tree's nodes before drawing (`katex.__parse` is internal, and the parse itself does the expansion), and a lower `maxExpand` alone (40 expansions already cost 3 seconds).
  - *Rejected:* KaTeX's HTML output alone (`output: "html"`, the source as an accessible label). It removes WebKit's exponential MathML case but not Chromium's crash, which comes from the HTML output (with `"html"` alone the crash stays at 130, with `"mathml"` alone there is none at 333), and screen readers lose the MathML KaTeX gives them as math; a label holding LaTeX source is not math. `output: "htmlAndMathml"` stays, the depth limit bounding the MathML's cost (proposal, open question 13).
- `model.ts` (pure): `valueFor(props, text)` (not `valueOf`, which Biome's `noShadowRestrictedNames` refuses) gives `{...props, expression: text}`, or `undefined` when `text` equals the props as sent.
- `index.tsx` registers `latex` with `{shape: () => LATEX_SHAPE, name: "change.widgetLatex"}`. It checks its props with `checks.ts` (the schema's limits, restated plain) and throws on a problem. Layout per DESIGN, LaTeX: a `<textarea>` in `{typography.code}` with the input atoms' look, labelled "LaTeX source", with no `maxLength` attribute (it counts UTF-16 units): its input handler keeps the first 2,000 code points through the contract's `cutLatexExpression`, so the page never offers what the contract refuses; the preview under it on `{colors.card}`, labelled "Preview", scrolling sideways; a refusal from `renderInto` gives its field error and no render, the preview keeping its last render: "This expression defines a macro with {command}, which a LaTeX item does not allow. Remove it before you answer.", "This expression uses {command}, one of KaTeX's internal commands, which a LaTeX item does not allow. Remove it before you answer." or "This expression nests {depth} levels deep, more than the limit of {limit}. Simplify it before you answer."; the draft holds the text as typed, so an answer carries what the field shows and `ask-core` refuses it (NFR-10); the parse error under the field, "This expression does not render: {message}", where the message is KaTeX's own, untranslated, and quotes the source: it is shown as text, its bidirectional controls as visible escapes through the contract's `agentTextRuns` (on `main`, `contract/src/index.ts:372`), as #28's excerpts mark them (view's `markedRuns` is not in the port). The field takes the `{colors.change}` border while it differs from the agent's expression, and the counter reads `widget.noChanges` or "Your changes: expression edited". The preview renders in a layout effect on each change; ready (`useReadyAfterLayout`) once the first render has run, succeeded or failed, and `document.fonts.ready` has settled. When `disabled`, the field is read-only with the read-only look.

### 8. Package stylesheets in a chunk

`tools/build/stylesheets.ts` holds `CHUNK_STYLESHEETS: {latex: ["katex/dist/katex.min.css"]}`, each path resolved from `packages/widgets`. The build reads each file, keeps each `@font-face` source's woff2 entry as `url(data:font/woff2;base64,…)`, drops its woff and ttf entries, and appends the result to the chunk's styles after Tailwind's. `styleUrlProblems(chunk, css)` in `checks.ts`, run on every chunk's styles and the board page's, parses the styles with lightningcss and walks the stylesheet its `StyleSheet` visitor gives (4.7 re-review X-3; it replaces the hand tokenizer of tasks 3.5 and 3.8, in which the group 3 review's X-2, the 3.7 re-review's X-1 and the 4.7 re-review's X-3 each found a gap):

- an `import` rule is a problem;
- every node holding a `url` string is a URL, and so is every string token of a function named `image-set` or `-webkit-image-set`, in any case, in a value lightningcss keeps as tokens (a custom property);
- a URL passes only as a `data:font/woff2` URL in the `src` of a `@font-face` rule, the one kind the font rewrite makes; any other URL, a `data:` image included, is a problem naming the chunk and the URL as decoded, cut at 80 characters;
- styles that do not parse are one problem naming the chunk and the parser's message and line, so the check fails closed.

lightningcss decodes escapes as CSS Syntax does, reads `xurl(` as a function and only `url(` as a URL, and reaches rules nested in `@media`, `@supports` and `@layer`: probed with 1.32.0 on 2026-11-07, the forms of the three reviews each gave their URL, `u\72l(` and `imag\65-set(` decoded, and KaTeX's stylesheet parsed in 2 ms with its 60 URLs. It is Tailwind's own CSS engine (`@tailwindcss/node` pins 1.32.0) and already in `bun.lock`; it becomes an exact root devDependency, build-time only and in no chunk. Adoption (2026-11-07): MPL-2.0, which the rule admits for unmodified dependencies; `parcel-bundler/lightningcss` 7,728 stars, not archived, pushed 2026-11-04, last release v1.33.0 on 2026-07-20; its one dependency `detect-libc` is Apache-2.0. The spine's Stack gains its row (`spine-update-draft.md` block 4, task 3.9). Should task 3.9 find that lightningcss cannot give what its tests need, the fallback is the hand scanner with `callBefore` fixed (the character before `url` cannot belong to an identifier), and the task stops for `/opsx:update` of this paragraph and of the view delta's requirement "No URL in a chunk's styles".

The style assembly of `finish` (Tailwind's output over the chunk's sources, then its package stylesheets, then both checks) is the exported pure function `assembleChunkStyles({chunk, own, packages})`, giving `{css, problems}`, which `finish` calls for every chunk and for the board page, so a test proves the check's reach without a build (group 3 review S-1). The listed stylesheets' files join the chunk's inputs for `collectNotices`, so the chunk's notices hold the package of every stylesheet it carries, even one its script does not import (group 3 review X-3; built in task 3.4). The build also fails on a listed chunk that does not exist and on a missing file. The rewrite is the spike's `inlineFonts`, run on the file rather than as a Bun plugin.

**Font licences** (task 3.4; corrected on 2026-11-07, when task 3.1 read the fonts' name tables). A font file can carry a licence other than its package's: KaTeX's `LICENSE` says MIT, its fonts' name tables say SIL OFL-1.1 with Reserved Font Names. The adoption rule admits OFL-1.1 only for unmodified font files shipped with their licence text, and `tools/licence-texts.json` serves only packages that ship no licence file, so it does not fit. The mechanism:

- `tools/font-licences.json`, keyed `<name>@<version>` like `licence-texts.json`: for a package whose fonts a chunk inlines, `{licence, fonts, derived, source, date, reason, text}`, where `fonts` is the font folder within the package (`dist/fonts` for KaTeX), `derived` the package's files whose code holds glyph outlines its upstream derived from those fonts (`["dist/katex.mjs"]`, the file Bun bundles for `import "katex"`, whose `var path = {` holds what `dist/katex.js:6970-6974` says is adapted from the KaTeX fonts under OFL-1.1; group 3 review X-1; an empty list when there are none), `licence` is an SPDX ID that is `OFL-1.1` or one `tools/check-licences.ts`'s `classify` calls permissive (any other fails the build, so the table admits nothing outside the rule), and `text` is the whole notice for the fonts: a first line naming the package version, the folder and the `derived` files, the fonts' copyright lines with every Reserved Font Name as their nameID 13 gives them, then the licence's full text. `source` is the licence text at a commit (default: `spdx/license-list-data`'s `text/OFL-1.1.txt` at a pinned commit, its template copyright line replaced by the fonts' lines, which `reason` says), never fetched by the build. One entry today: `katex@0.19.1`, `OFL-1.1`.
- `loadChunkStylesheets` reports, per chunk, the package (`<name>@<version>`, from the innermost `node_modules/<name>` folder on the stylesheet's path and its `package.json`) of each stylesheet whose fonts it inlined; a stylesheet with an inlined font outside any package fails the build, naming the chunk and the stylesheet. The listed stylesheets' files join the chunk's inputs for `collectNotices`, so the package has a notice even when the chunk's script does not import it.
- `collectNotices` takes the table (default `FONT_LICENCES`): the notice of a package version that has an entry reads `licence: "<package licence> AND <entry licence>"` (the package's expression in parentheses when it holds a space), `"MIT AND OFL-1.1"` for KaTeX, and its text is the package's own text, a blank line, then the entry's text; it records the key it took. It applies wherever that package version's notice is collected, so its notice stays one file at one `licencePath` (the build writes notices by path, and a Snapshot keeps one notice per package and version, `view/src/assemble/licences.ts`).
- The build fails when a chunk inlines fonts of a package version with no entry, and on an entry no chunk used, neither through its inlined fonts nor through a `derived` file among its inputs (stale, as `staleLicenceTexts`). A chunk that bundles KaTeX's script without its stylesheet still gets the `MIT AND OFL-1.1` notice, since the entry applies wherever the package version's notice is collected. A version bump of `katex` therefore fails the build until the entry is re-read and re-keyed.

## Risks / Trade-offs

- [A Tree or Gantt answer that fails its own changes schema is now refused] → task 2.1 replays every Tree, Gantt, WBS and Gantt plan suite before the check is on; a failure stops for `/opsx:update`, never a schema widened in passing.
- [Moving the Gantt's time code breaks the Gantt] → task 3.2 moves code only, its tests with it, and runs the Gantt's unit and browser files with task 0.3's counts.
- [KaTeX renders agent text as DOM] → `trust: false`, macro definitions, internal commands and nests past the limit refused before KaTeX runs (decision 7, Bounded work), bounded expansion and size, fresh macros, the DOM API only (no markup string), and the view's policy; task 4.1 tests `\href`, `\url`, `\includegraphics`, `\htmlClass`, `\gdef` and a self-expanding macro, and the security checkpoints review it.
- [A KaTeX construct nests or repeats in a way the scan does not count] → the source guards of tasks 4.8 and 4.9 read `katex.mjs` for names defined by side effect, macros whose braces do not balance, macros that consume raw tokens and commands allowed unbraced as arguments; task 4.9's property test bounds the MathML's depth by the scan's; task 4.10 renders every control word at the limit; a KaTeX bump fails `render.test.ts` until all of them are re-read.
- [The depth limit refuses deep but valid LaTeX] → the limit is the largest depth measured safe, and a script counts twice (`x^{y}` is 2 deep); the field error names the depth and the limit, and the skill teaches it to the agent. Expressions in practice rarely pass six levels.
- [lightningcss reads CSS unlike a browser] → it parses by CSS Syntax as Tailwind's own engine does, and task 3.9's tests hold every form the three reviews found; styles it cannot parse fail the build; the page policies stay the run-time defence (`default-src 'none'`, `img-src data: blob:`, hash-only `style-src`).
- [The Timeline's chunk carries the Gantt's schemas] → `timeline/checks.ts` imports `GANTT_FIRST_DATE` and `GANTT_LAST_DATE` from `gantt/index.ts`, which imports the Gantt's schema JSON; task 5.3 checks the built chunk for it and, if present, imports the dates from a plain module instead.
- [The LaTeX chunk is about 650 KB, 370 KB of it fonts] → only boards with a LaTeX item take it; task 5.1 records the size with its reason. A fonts chunk shared with a future MathLive is not needed while MathLive is out (renderer row 13).
- [Two KaTeX versions with the Diagram] → Mermaid brings its own 0.18 (renderer D5); a board with both carries both, as the spike measured; no change here.
- [Packed tracks guess label widths] → labels are cut at 200 pixels with the whole label in the accessible name and title; an overlap shows a cut label, never a lost entry.
- [Native drag fails by hand in Safari] → the keyboard moves answer; task 6.6 records the PO's check; a failure is a later change to pointer drag, as for the Ranking.
- [A resized range passes the contract] → the board offers no resize, and the answer still reports exactly what the value holds (open question 9).
- [The Approval summary shows column and lane IDs, not labels] → values are shown as sent; naming them by label is a later polish.
