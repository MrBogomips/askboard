# Proposal

## Why

The build order puts the widgets AXFX needs first: the Tree with the WBS-with-PERT molecule, and the Gantt with the Gantt plan (SOLUTION-DESIGN §3.1, AXFX FR-38). `compute` now schedules a plan over a WBS (CPM, `compute-engine`), and the `tree-widget` change builds, once for every widget, the seams a widget needs: widget items in a question, their values in the draft record, their chunks, their answers and the generic element diff. This change builds the Gantt on those, together with the Gantt plan that UJ-2 shows: a schedule the user reschedules by dragging, whose dates and critical path AskBoard computes as the user edits, with the agent's original plan as a baseline (FR-11, FR-12, FR-15).

## What Changes

- **`contract`, new files only:** the Gantt's item props as a part of the input format: the plan's `start` and its `tasks`, either the Gantt's own list (`{id, label, duration}` each) or, for a Gantt plan that names a Tree item (`workPackages`) whose leaves are its tasks, a map from task ID to what the plan says of that task; every task may carry a requested `start` and its finish-to-start `dependencies`. The Gantt's `changes` as AD-20's generic diff gives them for its two shapes, a flat list (`GANTT_SHAPE = {elements: "tasks"}`) and a keyed map (`GANTT_PLAN_SHAPE = {elements: "tasks", keyed: true}`); the checks a schema cannot express (the widget element ID rule for tasks and predecessors, the plan's link to its Tree, dates, limits); the derived values a Gantt answer carries (its finish date and critical path, F7); Gantt fixtures checked against the approved `uj2-wbs-gantt` examples. The schemas are standalone, `urn:askboard:input:gantt-props` and `urn:askboard:output:gantt-changes`, compiled only through `validateGanttProps` and `validateGanttChanges`, which sit on the seams' shared `widgetValidator`; nothing registers at import time, `sets.ts` does not change, and each of the three entry modules gets one appended export block. The Gantt writes no diff and no Ajv of its own.
- **`compute`:** a standalone Gantt as a graph source of its own (task durations as inputs); a requested start per task, so a task starts on the date the user dragged it to or as soon after as its predecessors allow; each task's `earliest` start and its date, which the drag guide and the start field read; `boardGraphSource`, which maps a board's Gantt items, and the Trees their plans name, onto the graph source; the working-day calendar helpers the widget snaps to (FR-12, AD-13 "In-house computations").
- **`molecules`:** the Gantt plan's parameters (`workPackages`, `start`, `dependencies`) as JSON Schema data, and what its expansion gives: one Gantt plan item whose `tasks` map holds each task's `dependencies` from the data, by task ID (AD-9, FR-15).
- **`widgets`, the Gantt:** a pure model (task rows, the edits, the moving rules of a drag and a resize, the zoom scale, the en-US date parser, change marks, grid keys) and the component: a grid of task, start, duration and predecessors beside AskBoard's own SVG chart with finish-to-start arrows and the critical path; drag to reschedule, resize to change a standalone task's duration, the earliest start shown during a drag; start and duration editable from the keyboard in the grid; the change highlight and counter (FR-11, FR-12; EXPERIENCE Widgets, Gantt; DESIGN.md Widgets, Gantt). In the plan, tasks are the WBS's leaves, durations follow their PERT estimates, and the toolbar adds the "Day | Week | Month" zoom; the agent's original plan is drawn as a baseline under the bars (FR-15; DESIGN.md and EXPERIENCE Molecules, Gantt plan).
- **`view`, on top of the `tree-widget` seams:** the port also gives a component the board's items and the draft record, read-only, so the Gantt builds the board's graph (AD-9), and takes the derived values it reports; the view's answer message carries those derived values beside the full edited value (AD-20); `compute` becomes a library chunk that only boards with a Gantt load, and the `radix` chunk adds Toggle Group for the zoom. The seams themselves are not built again.
- **Tests:** unit tests at 80% per file for the contract part, the `compute` additions, the molecule and the Gantt model; browser scenarios in Chromium, Firefox and WebKit through the `tree-widget` change's widget host: keyboard edits, drags and resizes, the earliest-start stop, the zoom, the baseline, the critical path, UJ-2's edits giving the approved answer's `schedule` edit and derived values, markup as text and no CSP violation.
- **Spine:** clarifications drafted in `spine-update-draft.md`: AD-13, how the view builds the board's graph and the baseline, applied only if the PO accepts open question 6; AD-20, the keyed maps of the generic diff, only if the `tree-widget` change's own AD-20 block does not already carry them. No PRD or UX document change.
- **Not in this change:**
  - The seams the `tree-widget` change builds once for every widget (open question 21).
  - Widening the input format, the board document and the board protocol so that an agent can ask a Gantt and `collect` its `changes` and `derived`: the follow-up after E1 merges that the `tree-widget` change already names, now for both widgets (input format 1.1).
  - `ask-core`'s molecule expansion through `MoleculeSource`, the molecule definition's own format, how an expanded plan names its expanded WBS, and the mapping of a molecule's answers to the reference's addressing (open question 20): the molecules epic.
  - The WBS-with-PERT molecule: expected effort and spread shown in the Tree, roll-ups, the excerpt per package, and the WBS-side rules that reach the plan (an added package's predecessors, F20; deleting a package with dependents; open question 11).
  - Holidays and a declared working calendar, dependency types other than finish to start, lags, summary bars, a draggable plan start, pointer linking of dependencies on the chart, the Date Picker, the TanStack Table grid and virtualised rows (open questions 8, 9, 16 and 19).
  - Revisions, the draft mirror and reload restore (E3), it-IT input (E8), Snapshots of a Gantt.

## Open questions for the PO

The PO is away and asked every session to keep working. Each question records the narrowest choice taken and why; the change is applied with these choices, and each can be reversed later.

1. **The input format is not widened.** As agreed between the sessions, the Gantt's schemas are standalone with their own `$id`s, outside `sets.ts`, compiled on the first validation through the seams' shared `widgetValidator`, as the Tree's are, since `contract` is free of side effects. No ask can carry a Gantt until the follow-up joins them to the input and output sets (input format 1.1).
2. **One widget, two shapes of `tasks`** (agreed with the `tree-widget` session). A Gantt's own `tasks` are a list, in the agent's order, each with a `label` and a `duration`: the flat shape `{elements: "tasks"}`. A plan's `tasks` (`workPackages` set) are a map from task ID to what the plan says of that task, its requested `start` and its `dependencies`, with no label, duration or order, which come from the Tree through `compute`: the keyed shape `{elements: "tasks", keyed: true}`, so an entry exists only for a task the plan says something about. In both, a task's `start` and `dependencies` are fields, so AD-20's one generic diff gives a changed predecessor list as one `set` of `item.task.dependencies`.
3. **A dragged start is a requested start.** A task starts on its requested start or as soon after as its predecessors allow ("not before"). Dropping a task on its earliest start clears the request; a typed start before the earliest start, or on a non-working day, is refused with a field error naming the earliest working day. The change is `set item.task.start`, `null` when cleared.
4. **The plan's durations are not edited in the plan.** EXPERIENCE gives each package its PERT expected effort, rounded up to whole working days, and also lets the plan edit durations "as in the Gantt". The plan shows the duration as a read-only value and the user changes it through the estimates in the WBS; a standalone Gantt edits durations. No override that would make the plan disagree with its WBS; the approved answer carries none.
5. **Zoom and baseline only in the plan** (EXPERIENCE open item 24). DESIGN.md puts them in the Gantt plan's row, and FR-11's Gantt row is the standalone ceiling (L68): a standalone Gantt shows the week scale with no zoom control and no baseline. The critical path, FR-11's derived value, shows in both.
6. **The baseline is the plan as sent.** `compute` builds the graph of the board's items as the agent sent them once per board revision, and the Gantt draws each task's start and finish from it; the live plan is the graph of the items with the draft's values. The spine draft states this in AD-13.
7. **The baseline's and the drag guide's looks** (DESIGN.md open item 8). The baseline is a 4px bar in `border-strong` under each task's bar, for tasks the agent sent; the guide is a 1px dashed vertical line in `muted-foreground` at the earliest start, over the dragged task's row. Both are provisional.
8. **The calendar.** Only AD-7's default calendar, Monday to Friday with no holidays; the props take no `calendar` key. The axis shows calendar days, as the UJ-2 mock does, with non-working days unmarked (DESIGN.md open item 9).
9. **Editing predecessors.** EXPERIENCE says the user edits dependencies but not how. The grid gains a "Depends on" column (label provisional); Enter opens an inline panel under the row with one checkbox per other task, and a task that would close a cycle is disabled with its reason. No popover, no pointer linking on the chart. Agents never send lags or other link types.
10. **Cycles and missing tasks are warnings.** A dependency cycle or a predecessor that names no task, as the agent sent it or after a WBS edit, is `compute`'s warning: the task's row shows a field error, it has no bar, and the answer is not blocked (AD-13, FR-14). A plan whose `workPackages` names no Tree with the three estimate columns in its question is refused, since the plan has no tasks without it (AD-10). A plan entry whose leaf the user deleted in the Tree has no row and no warning.
11. **The WBS side of the link waits.** A package added in the Tree becomes a task with no predecessors until the user sets them, as the approved answer does for `u-1`; EXPERIENCE's "its parent's predecessors" and F20 come with the WBS-with-PERT change, and so does reconnecting a deleted package's dependents. A Tree edit never writes the Gantt's draft.
12. **The plan's WBS is a Tree.** `boardGraphSource` reads the Tree a plan names as compute's `wbs-pert` source, its `optimistic`, `mostLikely` and `pessimistic` fields as estimates; the Tree shows plain values until the WBS-with-PERT change shows expected effort and spread.
13. **A task added through the Tree is a `set` in the plan** (resolved with the `tree-widget` session). The keyed shape gives only `set`s: a new entry is one `set` per field, so linking the package `u-1` the user added in the WBS gives exactly the approved answer's `set schedule.u-1.dependencies`; a field or an entry that is gone is a `set` to `null`, one per field it held. No `add`, `remove` or `move` arises in a plan, and nothing needs folding later.
14. **Derived values ride in the view's answer.** AD-20 has the view answer carry them; the Gantt's are `<item>.finish` (a `full-date`) and `<item>.criticalPath` (the critical tasks' IDs in task order), as the approved answer has them (F7). A value in error is left out. The board page still refuses widget answers until the follow-up.
15. **What the change highlight shows.** A task whose start, duration or predecessors the user changed takes the `gantt-user-change` outline and its changed cells the change fill; in the plan, a task the user added or re-estimated in the WBS is marked the same way, while dates that moved only because a predecessor moved are not. "Your changes: N" counts the tasks changed in this item only.
16. **No new dependency.** EXPERIENCE puts the grid on TanStack Table, and DESIGN.md's DateField uses the Date Picker (Radix Popover and `react-day-picker`); none of them is installed. The grid is plain rows, unvirtualised, and dates are typed in a text input read by AskBoard's own en-US parser (`11/16/2026` or `2026-11-16`), echoing the parsed day. Dates are the Gantt's, as the `tree-widget` session agreed: the parser lives in `packages/widgets/src/gantt/model/date.ts` until a second widget needs it; durations are read by the shared `shared/number.ts`.
17. **Limits.** At most 500 tasks, 50 predecessors per task, 50 tasks depending on one task, durations of 1 to 2,000 working days, 200 characters in a name; dates from 1900-03-02 to 9999-12-31: `compute`'s dates hold 1900-03-01 too, but a plan's first working day is found from the day before its start. The dependency limits keep each generated scheduling formula under the formula length limit.
18. **Keyboard and Tab stops.** The grid is one Tab stop (`role="grid"`): the arrow keys, Home and End move between cells; Enter or F2 edits the focused start, duration or predecessors; Enter commits, Escape cancels; Delete or Backspace on a start clears the request. In the plan the toolbar is a second Tab stop, as the Tree's is. The chart is not focusable: the grid carries every keyboard path (EXPERIENCE, keyboard minimum for the Gantt).
19. **The plan's start is the agent's.** No control moves the plan's `start`; only tasks are rescheduled.
20. **The molecule's parameters and what its expansion gives, not the expansion itself.** `packages/molecules` holds the Gantt plan's parameters as JSON Schema data (`{molecule, version, parameters}`). What the expansion gives is a requirement: one Gantt plan item with `workPackages` and `start` as given and a `tasks` map holding each task's `dependencies` from the data, by task ID; a test-only expansion checks it against the fixtures. The molecule definition's format, with its composition and pointers, `ask-core`'s expansion and the IDs it gives are the molecules epic's. Test board documents hold the plan under the reference's ID (`schedule`), which is how answers address it (AD-9).
21. **The seams are the `tree-widget` change's.** This change builds none of them again, the keyed shape and the shared validator included: it lists them as a dependency and adds only what the Gantt needs beyond them, the port's `board` and `onDerived`, the view answer's `derived` and two library chunk entries, each small, tested first and listed for the integration session.
22. **The zoom is view state.** It opens at week, is not saved in the draft, and the answer does not carry it.
23. **Seams cherry-picked, not rewritten** (agreed between the sessions). Task group 1 merges E1's integration head, or `main` once E1 has merged, then cherry-picks unchanged the commits the `tree-widget` session lists: its package manifest, the contract's `"sideEffects": false` and its widget-neutral seams, the keyed shape and `widgetValidator` (seam 2.10) among them, which touch no Tree file and nothing under `openspec/`. The Gantt's validators wait for that cherry-pick; its schemas alone, the `compute` group and the date parser do not. The Gantt plan waits for the Tree's own groups 3 to 6, since its WBS is a Tree.
