# Proposal

## Why

The build order puts the widgets AXFX needs first: the Tree with the WBS-with-PERT molecule, and the Gantt with the Gantt plan (SOLUTION-DESIGN §3.1, AXFX FR-38). `compute` now schedules a plan over a WBS (CPM, `compute-engine`), and the `tree-widget` change gives `packages/widgets` its first widget, widget items in a question and the seams for their answers. This change builds the Gantt on those, together with the Gantt plan that UJ-2 shows: a schedule the user reschedules by dragging, whose dates and critical path AskBoard computes as the user edits, with the agent's original plan as a baseline (FR-11, FR-12, FR-15).

## What Changes

- **`contract`, new files and one additive edit to the Tree's diff:** the Gantt's item props as a part of the input format: the plan's `start`, its tasks either listed (`tasks`, each `{id, label, duration}`) or taken from the leaves of a Tree item (`workPackages`, the Gantt plan), and two maps keyed by task ID, `dependencies` (finish-to-start predecessors, the approved example's shape) and `starts` (the start the user asked for); the Gantt's `changes` as `set` operations on a task's `duration`, `start` and `dependencies`; the checks a schema cannot express (the widget element ID rule for tasks, map keys and predecessors, the plan's link to its Tree, dates, limits); the Gantt's shape for the generic element diff (`element-diff.ts`, the `tree-widget` change's seam), whose shape gains maps keyed by element ID; the derived values a Gantt answer carries (its finish date and critical path, F7); Gantt fixtures checked against the approved `uj2-wbs-gantt` examples. The schemas are standalone, `urn:askboard:input:gantt-props` and `urn:askboard:output:gantt-changes`, compiled only inside `validateGanttProps` and `validateGanttChanges`, as the Tree's are; `sets.ts` does not change, and each of the three entry modules gets one appended export block.
- **`compute`:** a standalone Gantt as a graph source of its own (task durations as inputs); a requested start per task, so a task starts on the date the user dragged it to or as soon after as its predecessors allow; each task's `earliest` start and its date, which the drag guide and the start field read; `boardGraphSource`, which maps a board's Gantt items, and the Trees their plans name, onto the graph source; the working-day calendar helpers the widget snaps to (FR-12, AD-13 "In-house computations").
- **`molecules`:** the Gantt plan as data: its parameters (`workPackages`, `start`, `dependencies`) as JSON Schema over the Gantt's definitions, a composition of one Gantt item and the JSON Pointers each parameter fills (AD-9, FR-15).
- **`widgets`, the Gantt:** a widget-neutral en-US date parser in `packages/widgets/src/shared/`, beside the Tree's number parser; a pure model (task rows, the edits, the moving rules of a drag and a resize, the zoom scale, change marks, grid keys) and the component: a grid of task, start, duration and predecessors beside AskBoard's own SVG chart with finish-to-start arrows and the critical path; drag to reschedule, resize to change a standalone task's duration, the earliest start shown during a drag; start and duration editable from the keyboard in the grid; the change highlight and counter (FR-11, FR-12; EXPERIENCE Widgets, Gantt; DESIGN.md Widgets, Gantt). In the plan, tasks are the WBS's leaves, durations follow their PERT estimates, and the toolbar adds the "Day | Week | Month" zoom; the agent's original plan is drawn as a baseline under the bars (FR-15; DESIGN.md and EXPERIENCE Molecules, Gantt plan).
- **`view`:** the port also gives a component the board's items and the draft record, read-only, so the Gantt builds the board's graph (AD-9); the view's answer message carries the derived values beside the full edited value (AD-20); `compute` becomes a library chunk that only boards with a Gantt load, and the `radix` chunk adds Toggle Group for the zoom.
- **Tests:** unit tests at 80% per file for the contract part, the `compute` additions, the molecule and the Gantt model; browser scenarios in Chromium, Firefox and WebKit through the `tree-widget` change's widget host: keyboard edits, drags and resizes, the earliest-start stop, the zoom, the baseline, the critical path, UJ-2's edits giving the approved answer's `schedule` operation and derived values, markup as text and no CSP violation.
- **Spine:** two clarifications drafted in `spine-update-draft.md` (AD-13 for how the view builds the board's graph and the baseline, AD-20 for maps keyed by element ID in the generic diff), applied only if the PO accepts open questions 6 and 13. No PRD or UX document change.
- **Not in this change:**
  - Widening the input format, the board document and the board protocol so that an agent can ask a Gantt and `collect` its `changes` and `derived`: the follow-up after E1 merges that the `tree-widget` change already names, now for both widgets (input format 1.1).
  - `ask-core`'s molecule expansion through `MoleculeSource`, the molecule definition's own schema, and how an expanded plan names its expanded WBS: the molecules epic (open question 20).
  - The WBS-with-PERT molecule: expected effort and spread shown in the Tree, roll-ups, the excerpt per package, and the WBS-side rules that reach the plan (an added package's predecessors, F20; deleting a package with dependents; open question 11).
  - Holidays and a declared working calendar, dependency types other than finish to start, lags, summary bars, a draggable plan start, pointer linking of dependencies on the chart, the Date Picker, the TanStack Table grid and virtualised rows (open questions 8, 9, 16 and 19).
  - Revisions, the draft mirror and reload restore (E3), it-IT input (E8), Snapshots of a Gantt.

## Open questions for the PO

The PO is away and asked every session to keep working. Each question records the narrowest choice taken and why; the change is applied with these choices, and each can be reversed later.

1. **The input format is not widened.** As agreed between the sessions, the Gantt's schemas are standalone with their own `$id`s, outside `sets.ts`, compiled on the first call of `validateGanttProps` or `validateGanttChanges` into an Ajv of their own with `createAjv`'s options, as the Tree's are, since `contract` is free of side effects. No ask can carry a Gantt until the follow-up joins them to the input and output sets (input format 1.1).
2. **One widget, two task sources.** A `gantt` item lists its tasks, or names a Tree item whose leaves are its tasks (`workPackages`, the Gantt plan). `dependencies` and `starts` are maps keyed by task ID in both, so the plan's props are exactly the approved `gantt-plan` data plus the user's starts, and an agent learns one dependency format.
3. **A dragged start is a requested start.** A task starts on its requested start or as soon after as its predecessors allow ("not before"). Dropping a task on its earliest start clears the request; a typed start before the earliest start, or on a non-working day, is refused with a field error naming the earliest working day. The change is `set item.task.start`, `null` when cleared.
4. **The plan's durations are not edited in the plan.** EXPERIENCE gives each package its PERT expected effort, rounded up to whole working days, and also lets the plan edit durations "as in the Gantt". The plan shows the duration as a read-only value and the user changes it through the estimates in the WBS; a standalone Gantt edits durations. No override that would make the plan disagree with its WBS; the approved answer carries none.
5. **Zoom and baseline only in the plan** (EXPERIENCE open item 24). DESIGN.md puts them in the Gantt plan's row, and FR-11's Gantt row is the standalone ceiling (L68): a standalone Gantt shows the week scale with no zoom control and no baseline. The critical path, FR-11's derived value, shows in both.
6. **The baseline is the plan as sent.** `compute` builds the graph of the board's items as the agent sent them once per board revision, and the Gantt draws each task's start and finish from it; the live plan is the graph of the items with the draft's values. Block 1 of the spine draft states this in AD-13.
7. **The baseline's and the drag guide's looks** (DESIGN.md open item 8). The baseline is a 4px bar in `border-strong` under each task's bar, for tasks the agent sent; the guide is a 1px dashed vertical line in `muted-foreground` at the earliest start, over the dragged task's row. Both are provisional.
8. **The calendar.** Only AD-7's default calendar, Monday to Friday with no holidays; the props take no `calendar` key. The axis shows calendar days, as the UJ-2 mock does, with non-working days unmarked (DESIGN.md open item 9).
9. **Editing predecessors.** EXPERIENCE says the user edits dependencies but not how. The grid gains a "Depends on" column (label provisional); Enter opens an inline panel under the row with one checkbox per other task, and a task that would close a cycle is disabled with its reason. No popover, no pointer linking on the chart. A plan's predecessors are its tasks; agents never send lags or other link types.
10. **Cycles and missing tasks are warnings.** A dependency cycle or a predecessor that names no task, as the agent sent it or after a WBS edit, is `compute`'s warning: the task's row shows a field error, it has no bar, and the answer is not blocked (AD-13, FR-14). A plan whose `workPackages` names no Tree with the three estimate columns in its question is refused, since the plan has no tasks without it (AD-10).
11. **The WBS side of the link waits.** A package added in the Tree becomes a task with no predecessors until the user sets them, as the approved answer does with `schedule.u-1.dependencies`; EXPERIENCE's "its parent's predecessors" and F20 come with the WBS-with-PERT change, and so does reconnecting a deleted package's dependents. A Tree edit never writes the Gantt's draft.
12. **The plan's WBS is a Tree.** `boardGraphSource` reads the Tree a plan names as compute's `wbs-pert` source, its `optimistic`, `mostLikely` and `pessimistic` fields as estimates; the Tree shows plain values until the WBS-with-PERT change shows expected effort and spread.
13. **The generic diff gains maps keyed by element ID.** The plan's tasks are no element list of the Gantt's own, and the approved answer writes `set schedule.u-1.dependencies`, where an element list holding `u-1` would give an `add`. The Tree's `ElementShape {elements, children?}` gains an optional `keyed`, the maps whose keys are element IDs, each with the field it stands for; a changed key is one `set` of that element's field, a removed key a `set` to `null`, and an absent elements key is an empty list. Keyed `set`s come after the element list's operations, by element ID and then field name, in UTF-16 code-unit order, as the Tree orders an element's `set`s. Block 2 of the spine draft states this in AD-20, after the `tree-widget` change's Block 2.
14. **Derived values ride in the view's answer.** AD-20 has the view answer carry them; the Gantt's are `<item>.finish` (a `full-date`) and `<item>.criticalPath` (the critical tasks' IDs in task order), as the approved answer has them (F7). A value in error is left out. The board page still refuses widget answers until the follow-up.
15. **What the change highlight shows.** A task whose start, duration or predecessors the user changed takes the `gantt-user-change` outline and its changed cells the change fill; in the plan, a task the user added or re-estimated in the WBS is marked the same way, while dates that moved only because a predecessor moved are not. "Your changes: N" counts the tasks changed in this item only.
16. **No new dependency.** EXPERIENCE puts the grid on TanStack Table, and DESIGN.md's DateField uses the Date Picker (Radix Popover and `react-day-picker`); none of them is installed. The grid is plain rows, unvirtualised, and dates are typed in a text input read by AskBoard's own en-US parser (`11/16/2026` or `2026-11-16`), echoing the parsed day; the parser is widget-neutral, in `packages/widgets/src/shared/date.ts`, and durations use the Tree's `shared/number.ts`.
17. **Limits.** At most 500 tasks, 50 predecessors per task, 50 tasks depending on one task, durations of 1 to 2,000 working days, 200 characters in a name; dates from 1900-03-01 to 9999-12-31, the range `compute`'s dates hold. The dependency limits keep each generated scheduling formula under the formula length limit.
18. **Keyboard and Tab stops.** The grid is one Tab stop (`role="grid"`): the arrow keys, Home and End move between cells; Enter or F2 edits the focused start, duration or predecessors; Enter commits, Escape cancels; Delete or Backspace on a start clears the request. In the plan the toolbar is a second Tab stop, as the Tree's is. The chart is not focusable: the grid carries every keyboard path (EXPERIENCE, keyboard minimum for the Gantt).
19. **The plan's start is the agent's.** No control moves the plan's `start`; only tasks are rescheduled.
20. **The molecule as data, not yet expanded.** The Gantt plan is written in `packages/molecules` as `{molecule, version, parameters, composition, fills}`, the first molecule; its definition schema, `ask-core`'s expansion and how the expansion names the WBS the plan links to are the molecules epic's. Test board documents hold the Gantt item under the reference's ID (`schedule`), which is how answers address it (AD-9).
21. **E1's and the seams' view files change here.** The port's props, the view protocol's answer and the library chunk table; each edit is small, tested first and listed for the integration session.
22. **The zoom is view state.** It opens at week, is not saved in the draft, and the answer does not carry it.
23. **Seams cherry-picked, not rewritten** (agreed between the sessions). The `tree-widget` change's groups 1 and 2 are widget-neutral and come to this branch as its code commits, cherry-picked unchanged; the Gantt writes no second diff, ID helper, number parser, port value type or widget host. The Gantt plan waits for the Tree's own groups 3 to 6, since its WBS is a Tree.
