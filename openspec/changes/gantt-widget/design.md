## Goals / Non-Goals

**Goals:**

- A Gantt and a Gantt plan that meet FR-11's Gantt row, FR-12's Gantt consequences and FR-15's Gantt plan scope on the board, every date and the critical path from `compute`, edited from the draft record alone and sent only by "Answer".
- The seams the follow-ups extend are real: the Gantt's schemas, the keyed maps of the generic diff, the board's graph source in `compute`, the molecule as data, the derived values in the view's answer.
- Every behaviour the specs name is tested: pure logic under `bun test` at 80% per file, the rest in three browser engines.

**Non-Goals:**

- Anything proposal.md lists under "Not in this change".
- Touching `packages/core` or `server`, E1's or Tree's schema files, constants and existing fixtures, or `docs/`.
- Screen-reader announcements and reduced motion (EXPERIENCE open item 22); text on the chart for screen readers beyond its label: the grid carries the data.

## Decisions

### 1. The base comes first, in two steps

- **Before group 1:** E1's integration branch is merged into this branch (task 0.1), with `compute-engine`'s merge notes (both export blocks kept in `contract`'s `index.ts`, `bun install` changing nothing more); then the `tree-widget` change's group 1 and 2 code commits are cherry-picked unchanged, never its `docs(tree-widget)` tick commits (task 0.2), as that change's design, "Merge points", provides. The Gantt needs every seam they build, and writing them twice would make the merge the hard part.
- **Before group 7, the Gantt plan:** the plan's WBS is a Tree, its fixtures extend the Tree's, and its UJ-2 scenario edits the Tree, so the Tree's groups 3 to 6 must be in the base, merged from the Tree's branch or cherry-picked the same way (task 7.1). Groups 1 to 6 build and test everything that does not need them: the standalone Gantt, the keyed diff, `compute`'s scheduling and the model.

A Tree commit that differs from what this design names (a function, a shape, a file) stops the task that meets it: the design is revised with `/opsx:update` before any code works around it.

*Alternative:* wait for the Tree change to be merged before starting (no cherry-picks to drop later, but the standalone Gantt, which needs none of the Tree's own code, would wait too).

### 2. The Gantt's contract: standalone schemas, compiled where they are used

`packages/contract/src/widgets/gantt/` holds:

- `gantt-props.json` (`urn:askboard:input:gantt-props`): `start` (`$defs/fullDate`: the `YYYY-MM-DD` pattern), `tasks` (at most 500 of `{id, label, duration}`, `duration` an integer from 1 to 2,000, `label` 1 to 200 characters), `workPackages` (the input set's ID schema), `dependencies` (`$defs/dependencies`: `propertyNames` the ID schema, each value a unique array of at most 50 IDs) and `starts` (`$defs/starts`: `propertyNames` the ID schema, each value a `fullDate`); `additionalProperties: false`; `required: ["start"]`. "Exactly one of `tasks` and `workPackages`" sits in the checks, since a `oneOf` of bare `required` branches breaks Ajv's `strictRequired`.
- `gantt-changes.json` (`urn:askboard:output:gantt-changes`): an array of `{op: "set", target, value}`; `target` is `<id>.<id>.(duration|start|dependencies)`; `value` is an `anyOf` inside the property of an integer, a `fullDate`, `null` or a unique array of IDs.
- `index.ts`: the types (`GanttTask`, `GanttProps`, `GanttItem` `{type: "gantt", id, props}`, `GanttChange`), the limits (`GANTT_MAX_TASKS` 500, `GANTT_MAX_PREDECESSORS` 50, `GANTT_MAX_DEPENDENTS` 50, `GANTT_MIN_DURATION` 1, `GANTT_MAX_DURATION` 2,000, `GANTT_LABEL_MAX_CHARS` 200, `GANTT_FIRST_DATE` `1900-03-01`, `GANTT_LAST_DATE` `9999-12-31`), `GANTT_PLAN_ESTIMATES` (`optimistic`, `mostLikely`, `pessimistic`), `GANTT_SHAPE` (decision 3), `GANTT_ANSWER_DERIVED` (decision 4) and `ganttSchemas`, the two schema objects.
- `checks.ts`, plain ECMAScript: `ganttPropsProblems(props, origin)` (exactly one task source; the widget element ID rule for task IDs, map keys and predecessors, the `u-` prefix refused when `origin` is `agent`; each date a real day in range, by a small proleptic-Gregorian check in the contract, since `contract` imports nothing; a predecessor listed once; the dependents count per task); `ganttPlanLinkProblems(gantt, question)` (the named item exists in the question, is a Tree, and its columns declare the three estimates as numbers); `ganttChangesProblems(itemId, changes, props)` (each target's item is the Gantt's; `duration` only when the Gantt lists its tasks, an integer in range; `start` a real day or `null`; `dependencies` within the limits and never naming the target task). Problems name the task or operation and the field, as E1's and Tree's do. Unknown tasks and cycles are not problems (spec, "Gantt references are not refused").
- `validate.ts`: `validateGanttProps(value, origin)` and `validateGanttChanges(itemId, value, props)`, the schema and then the checks, returning E1's `Checked`.

**Standalone, compiled inside the function**, as agreed between the sessions and as the Tree's design (decision 2) does it: the two schemas are in no set, so `sets.ts`, `SCHEMA_SETS`, `SCHEMA_IDS` and `createAjv` do not see them. On the first call of either validator, the module makes an Ajv with `createAjv`'s options (`strict: true`, `allErrors: true`), adds E1's ID schema and the two Gantt schemas, and keeps it in a module variable; Ajv's errors map to E1's `Problem` as the Tree's validator maps them (if the Tree's group 3 has made that mapping a shared module by then, the Gantt imports it instead). Nothing happens when a module loads. The schema tests compile the two schemas in strict mode with `createAjv`'s options and check the Consistency Conventions' shape rules directly (JSON Schema 2020-12, the `$id` in its future set's namespace, no root combinator). One export block is appended to each of `index.ts` (types, limits, checks, `GANTT_SHAPE`, `GANTT_ANSWER_DERIVED`, and the two schema objects for the molecule's tests), `validate.ts` (the two validators) and `fixtures/index.ts` (decision 4).

*Alternatives:* the schemas inside the input and output sets (the follow-up's step, input format 1.1, which the sessions agreed to take together); `dependencies` inside each task, as an array field the Tree's flat-list diff already handles (the approved `gantt-plan` data keys them by task, and the plan has no task list of its own, so the plan would need the keyed maps anyway, and two dependency formats would teach the agent two shapes); a `oneOf` at the props' root (refused by Ajv's strict mode, as above).

### 3. Keyed maps in the one generic diff

AD-20 has one generic diff, in `contract`, that addresses elements by ID: the Tree's seam, `element-diff.ts`. The plan's tasks are not an element list of its own, and the approved answer writes `set schedule.u-1.dependencies`, so `ElementShape` gains an optional `keyed`, the maps keyed by element ID: `GANTT_SHAPE` is `{elements: "tasks", keyed: {dependencies: "dependencies", starts: "start"}}`, each map's props key mapped to the element field it stands for. An absent elements key reads as an empty list, so the plan's props, which hold no `tasks`, diff through the same shape. `elementChanges` first diffs the element list as the Tree's design says (for a Gantt only `set`s of `duration` arise, since no task is added, removed or moved); then it gathers, over every keyed map, each key whose value differs as a JSON value between the sent and the edited map, one `set` of `item.key.field` with the edited value, or `null` for a key the edited map lacks; and lists them by element ID, then field name, each in UTF-16 code-unit order, as the Tree orders an element's `set`s. `applyElementChanges` applies a `set` on a keyed field by writing the key, or deleting it on `null`, and throws, naming the operation, on a `set` that names neither a keyed field nor an element's field. Tests, on generic data as the seam's are: table cases of the spec's scenarios, the order whatever the keys' order in either value, and a seeded property test, in a keyed-only and a mixed shape, that applying the diff rebuilds the edited props. The change is additive: a shape without `keyed` diffs as before, which the seam's own tests keep checking.

The model never writes a key whose value equals the sent state (decision 7), so an edit undone by hand gives no operation. Block 2 of `spine-update-draft.md` adds the keyed maps to AD-20, after the `tree-widget` change's Block 2.

*Alternatives:* a Gantt-only diff function (widget semantics where AD-20 wants one generic diff); reshaping the plan's maps into an element list before diffing (a key the user adds would come out as an `add`, where the approved answer has a `set`).

### 4. Checked against the approved UJ-2 examples, and the fixtures built from them

E1 already holds the approved files, unchanged, under `packages/contract/test/fixtures/asks/` and `answers/`. The Gantt's checks:

- **The same:** the `schedule` data validates as a plan's props and passes the link check against Tree's `treeBoardDocument` question; the `schedule.` operation validates as a Gantt change; the diff of the plan as sent and as edited (the key `u-1` added to `dependencies`) gives exactly that operation; and `compute`, over the edited Tree and plan, gives the approved `schedule.finish` and `schedule.criticalPath`.
- **What differs, and why:** the example holds `schedule` as a molecule reference, which `ask-core` will expand (proposal, open question 20), so the fixture writes the Gantt item under the reference's ID with the data as its props; the answer's `derived` holds `wbs.*` values too, which are the WBS-with-PERT change's (F7), so the check compares the `schedule.` keys only.

`GANTT_ANSWER_DERIVED` declares the two keys: `finish` read from the graph's `finishDate`, and `criticalPath` the task IDs whose `critical` is true, in task order (proposal, open question 14). The fixtures (`packages/contract/src/fixtures/gantt.ts`, tests only): `ganttBoardDocument`, a question `schedule-review` holding a Gantt `release` that lists UJ-2's six work packages with the durations the UJ-2 plan computes (6, 4, 5, 13, 9, 6) and its four dependencies, and `ganttEditedValue`, that Gantt with a requested start and a changed duration; `ganttPlanBoardDocument`, Tree's `treeBoardDocument` question with the Gantt `schedule` appended; `ganttPlanEditedValue`, the plan after the approved edit; `ganttPlanChanges` and `ganttPlanDerived`, from the approved answer. A contract test checks that they agree (spec, "Gantt fixtures"); a `compute` test checks the derived values and that `release` schedules like the plan (compute spec, "A Gantt's own tasks are scheduled").

### 5. `compute`: a standalone source, requested starts, the board's graph source

- **`gantt` source kind** (`source.ts`): `{kind: "gantt", id, start, tasks: [{id, duration}], dependencies?, starts?}`; `gantt-plan` gains `starts?`. `cpm.ts`'s task fields are shared by both: `duration` is a number input for `gantt` and the PERT formula for `gantt-plan`; everything else is the same formulas.
- **Requested starts:** each task gains `earliest` (what `es` was: `MAX(0,[p.a.ef],…)` over its predecessors, else `0`), `earliestDate` = `WORKDAY([p.firstDay],[p.t.earliest])`, and `startOffset`, a number input: the working days from the plan's first working day to the first working day on or after the requested start, `0` without one or before the first day. `es` becomes `MAX([p.t.earliest],[p.t.startOffset])`; `ef`, `lf`, `ls`, `slack`, `critical` and the dates are unchanged. The offset is computed at expansion with `dates.ts`, since no whitelisted function counts working days between two dates; that is AskBoard's own code for rescheduling, as AD-13's "In-house computations" allows. A change to the plan's `start` would make the offsets stale, and the plan's start is not editable (proposal, open question 19); the view rebuilds the graph after each Gantt edit anyway (decision 7).
- **The board's graph source** (`board.ts`, new): `boardGraphSource(items)`, over the board's items as `{type, id, props}` with the draft's values in place: a `gantt` with `tasks` gives a `gantt` source; one with `workPackages` gives a `gantt-plan` source, and the Tree it names a `wbs-pert` source with that Tree's `nodes` (its other keys, `label` included, are ignored, as `compute`'s WBS source already ignores them); every other item gives nothing. A Tree named by two plans is mapped once. Types come from `contract` (`GanttItem`, Tree's `TreeItem`). `ask-core`'s send-time check calls it with `buildGraph` when the follow-up wires it.
- **Calendar helpers** (`dates.ts`, exported from the index): `isWorkingDate`, `firstWorkingDateFrom`, `addWorkingDays` and `workingDaysBetween` on `full-date` strings, over the existing serial arithmetic, with no `Date`.
- **Limits:** a test builds a Gantt at the contract's limits with 64-character IDs and checks every generated formula against the formula check (spec, "Scheduling formulas stay inside the limits"): 50 references of at most 134 characters keep `es` and `lf` under 8,192.
- **Determinism:** the new fixtures join the hash script that runs under the two time zones and two locales.

*Alternatives:* a requested start as a date compared inside the formulas (the backward pass and slack are in working days, which a date cannot give back without counting them); scheduling a standalone Gantt as a plan over a synthetic WBS (durations would pass through PERT's rounding); the mapping in `view` (`ask-core` needs the same mapping, and `view` is not on its import path).

### 6. The Gantt plan as data

`packages/molecules/src/gantt-plan/gantt-plan.json`: `molecule` `gantt-plan`, `version` `1.0.0`; `parameters`, a JSON Schema (`urn:askboard:molecule:gantt-plan:1`) of `{workPackages, start, dependencies}` whose properties `$ref` the Gantt's definitions (`urn:askboard:input:gantt-props#/$defs/…`), `required` `workPackages` and `start`, `additionalProperties: false`; `composition`, one item `{type: "gantt", id: "plan", props: {workPackages: "", start: "", dependencies: {}}}`; `fills`, each parameter's pointers (`/0/props/workPackages` and so on). `index.ts` exports it in `READY_MOLECULES`. `molecules`' `package.json` declares `@askboard/contract` (`workspace:*`), the spine's only allowed import, which its tests use to compile the parameters in an Ajv made with `createAjv`'s options, beside E1's ID schema and the Gantt's props schema they reference.

Tests: the file holds exactly those keys and no string with `<` or a `javascript:` scheme; the parameters compile in strict mode and accept the approved `schedule` data unchanged; an unknown parameter is refused, naming it; a test-only filler (`test/fill.ts`, the pointers written into a copy of the composition) gives one Gantt item that `validateGanttProps` accepts and `ganttPlanLinkProblems` accepts against the fixture question. The expansion, with its `<id>__` prefix and its rewriting of `workPackages` to the WBS's expanded item, is `ask-core`'s and the molecules epic's (proposal, open question 20).

*Alternatives:* the parameters written out again instead of `$ref` (two definitions of one data shape to keep in step); the molecule's schema in the input format now (the molecules epic decides the definition format for all molecules, FR-16 and FR-17 included).

### 7. The board's graph in the view, and the baseline

- **What a component gets** (`catalog/port.ts`): `ItemProps` gains `board`, read-only: the board's items as sent (the view document's questions' items, flattened) and the draft record's value per item ID. AD-9 lets a component render from the board document, the draft record and the compute graph; the port now gives it the first two whole.
- **Where the graph is built:** `packages/widgets/src/graph/board-graph.ts`, in the Gantt's chunk: `liveGraph(board)` maps the items with their draft values through `boardGraphSource`, then `buildGraph` and `evaluateGraph`; `sentGraph(board)` does the same with the items as sent. Both are memoized by the identity of the items list and of the draft record, so two Gantts on one board share one build, and the sent graph is built once per board revision. Edits rebuild the live graph when they commit (a drop, Enter, a checkbox), never during a pointer move: dependency edits change formulas, so a rebuild is needed for them anyway.
- **Why not the shell:** the shell is in every srcdoc, and `compute` is far larger than the shell; the shell would then carry it on plain boards. When a second computing widget arrives (the WBS-with-PERT change), the board graph moves behind the port into a library chunk that every computing widget needs; the module's interface is written for that move.
- **`compute` as a library chunk:** `LIBRARY_CHUNKS` gains `compute`, providing `@askboard/compute` with the names the Gantt imports, so `assemble` inlines it only for boards with a Gantt. `radix` adds `ToggleGroup` for the zoom.
- **The baseline:** the sent graph's `startDate` and `finishDate` per task, for tasks that exist in it (proposal, open question 6). Block 1 of `spine-update-draft.md` states in AD-13 that the view builds the graph from the board document with the draft's values and builds the baseline from the document as sent.

*Alternatives:* `set` and `recalc` on one graph per edit (cheaper per drag, but a dependency edit changes formulas, and two code paths would disagree on what a rebuild gives; kept as the fallback of "Risks / Trade-offs"); the baseline as extra fields in one graph (the WBS's estimates as sent would have to enter the graph twice).

### 8. The model: pure functions in `packages/widgets/src/gantt/model/`

- `tasks.ts`: the rows. For a Gantt that lists its tasks, its `tasks`; for a plan, the leaves of its Tree's current nodes in document order, with their labels. Each row knows whether it was sent, its label, and the cells it shows.
- `schedule.ts`: per row, from the live graph, `startDate`, `finishDate`, `duration`, `critical`, `earliestDate`, or the formula error and its kind; from the sent graph, the baseline dates; the plan's `finishDate`; the answer's derived values by `GANTT_ANSWER_DERIVED`, an error left out.
- `edits.ts`: `requestStart`, `clearStart`, `setDuration`, `setPredecessors`, each returning a new frozen value, or the same value when nothing changes; a key whose value comes back to the sent state is restored to it (absent when the sent value had none), and `sameGantt` tells the component to put `undefined` in the draft. `canPrecede(value, rows, task, candidate)` refuses a candidate that would close a cycle (a walk over the current predecessors) or break the predecessor or dependent limits, with the reason.
- `scale.ts`: per zoom, the pixels per calendar day (day 32, week 15 as the UJ-2 mock, month 4), the axis ticks (each day, each Monday, each month's first day) and labels in en-US (`Mon 2`, `Nov 2`, `Nov 2026`), and the conversion between a date and an x position. Calendar days, weekends unmarked (proposal, open question 8).
- `drag.ts`: a move's new start from the pointer's travel: the nearest day, then the first working day from it, never before `earliestDate`; a drop on `earliestDate` clears the request. A resize's new duration: the working days from the start to the nearest day under the bar's end, at least 1.
- `packages/widgets/src/shared/date.ts`, widget-neutral beside the seam's `number.ts`: the en-US date parser (`M/D/YYYY`, or `YYYY-MM-DD`), refusing anything else, a day that does not exist and a year outside the contract's range, with a reason; the echo (`= Wed, Dec 9, 2026`) and the grid's format (`12/9/2026`). Durations are read by `shared/number.ts` and refused unless whole and in range. The Gantt makes no element ID, so it does not use `shared/ids.ts`.
- `marks.ts`: per task, changed start, duration or predecessors against the sent value; in a plan, added (absent from the sent Tree) or re-estimated (its duration in the live graph differs from the sent graph's); the count "Your changes" shows (tasks changed in this item, once each).
- `keys.ts` and `focus.ts`: the grid's focus position, its moves on the arrow keys, Home and End, the action of each key in navigation and in edit mode (proposal, open question 18), and the toolbar's roving focus.

The model computes no date: every date and flag comes from `compute`, and the calendar helpers are `compute`'s.

### 9. The component: grid beside an SVG chart

`packages/widgets/src/gantt/index.tsx` registers `gantt` through `@askboard/view/catalog`; the rest of the folder renders the model:

- **Frame:** the widget frame with a toolbar row on `muted`: in a plan, the "Day | Week | Month" segmented control on Radix Toggle Group (labels provisional); in both, the counter on the right. Below, the body: the grid on the left and the chart on the right, the chart in a horizontally scrollable region; under them the legend ("task", "critical path", "your change") and the field errors that name no task.
- **Grid** (`role="grid"`, labelled by the question's text): a header row in `text-label` on `muted` ("Task", "Start", "Duration", "Depends on"; provisional), 36px rows under a 32px header as in the mock. Start and duration cells are text inputs in edit mode with the parsed echo in `text-code`; a plan's duration is a right-aligned value. "Depends on" shows the predecessors' names; Enter opens the inline panel under the row: Radix Checkboxes, one per other task, disabled with their reason when `canPrecede` refuses, with Enter or "Done" committing and Escape cancelling. A refused entry shows a `field-error` under the row and keeps the focus and the draft. One element holds `tabIndex` 0.
- **Chart** (SVG, `role="img"`, labelled "Gantt chart, <zoom> zoom"; not focusable): the time axis on `muted` with labels in `text-badge` and `muted-foreground` and gridlines in `border`; per task a 14px bar in `gantt-bar`, or `critical` on the critical path; finish-to-start elbow arrows, 1px in `gantt-bar` or 2px in `critical`, with arrowhead markers; a changed task's 2px `change` outline offset by 1px; in a plan the baseline, a 4px bar in `border-strong` under the task's bar (provisional, proposal open question 7). Geometry is written as SVG attributes and colours as classes; no `style` attribute (AD-8).
- **Pointer edits:** a bar takes pointer down, captures the pointer, follows its travel through `drag.ts`, and commits on pointer up; while it moves, the guide (a 1px dashed line in `muted-foreground` at `earliestDate`, over the row) shows; Escape or a lost capture cancels. In a Gantt that lists its tasks, the bar's last 6px resize it. A move below the drag threshold of 3px is a click and changes nothing.
- **States:** `disabled` keeps the zoom, the grid's navigation and the horizontal scroll, and turns off editing keys, the panel and pointer edits; `useReadyAfterLayout` reports ready once laid out; a task in error has a field error under its row and no bar (spec, "Gantt formula errors").
- **Data it did not get through the board page:** the component checks its props with `ganttPropsProblems(props, "agent")` and a plan's link with `ganttPlanLinkProblems` against its question, and throws on a problem, so the error boundary fails the item (AD-10). Only test documents reach it before the follow-up.
- **The answer:** on "Answer", the question card sends the Gantt's draft value as Tree's design does and, from `schedule.ts`, the Gantt's derived values in the new `derived` field.

*Alternatives:* TanStack Table for the grid, as EXPERIENCE chooses (not installed; proposal, open question 16); a drag-and-drop library (EXPERIENCE: Gantt tasks move by pointer drag with no library); a focusable chart with arrow-key moves (the grid's start field is the keyboard path EXPERIENCE names, and a second keyboard model would need its own tests in three engines).

### 10. View integration

Small edits to E1's and Tree's view, each with tests first, leaving Choice's and Tree's behaviour as their browser tests check it (proposal, open question 21):

- **Port** (`catalog/port.ts`): `board`, as decision 7 says.
- **View document** (`view-document.ts`, Tree's): a question's widget items may be `GanttItem`; `componentsOf` gives `gantt` for one.
- **View protocol** (`view-protocol.ts`): `ViewAnswer` gains an optional `derived`, reference to value; `readViewMessage` checks it structurally (own-property keys matching the reference pattern, JSON values). The question card collects each widget's derived values through a port callback, `onDerived`, which the Gantt calls with its declared values after each rebuild; the card sends those of its items when "Answer" is pressed.
- **Library chunks** (`tools/build/shared-modules.ts`): `compute`, and `ToggleGroup` in `radix`.
- **Board page:** unchanged; Tree's refusal already covers an answer with `values`, and a test adds a Gantt answer to its cases.

## Risks / Trade-offs

- [The Tree change is not applied yet, and its diff, types or port may come out different] → Task 0.2 stops if the seams are not all committed, and task 7.1 checks every Tree name the plan uses; a difference is recorded and the design revised with `/opsx:update` before any code.

If a drop takes more than 100 ms, starts and durations go through `set` and `recalc` instead (the offset is `workingDaysBetween`, a `compute` helper), and only predecessor and WBS edits rebuild; the note records the times.

- [The expansion may name the plan's items differently from the fixtures] → The fixtures use the reference's IDs, which answers use (AD-9); the molecules epic maps between the two, and the molecule's tests do not depend on the item ID.
- [E1's and Tree's view files change here, and their integration is still open] → Each edit is small, tested first and listed in the proposal's Impact; both browser suites run in every task that touches the view.
