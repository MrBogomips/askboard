## Goals / Non-Goals

**Goals:**

- A Tree that meets FR-11's row and EXPERIENCE's Tree rules on the board, edited from the draft record alone and sent only by "Answer".
- The seams the follow-ups and the Gantt widget extend are real and widget-neutral: the generic element diff `ask-core` will call, giving the output format's changes, the widget validator, the shared model helpers, widget chunks in the view's manifest, widget items in a question, and an answer message that carries a widget's full value; the Tree's standalone schemas, ready to join the input and output sets.
- Every behaviour the specs name is tested: pure logic under `bun test` at 80% per file, the rest in three browser engines.

**Non-Goals:**

- Anything proposal.md lists under "Not in this change".
- Touching `packages/core`, `server` or `compute`, E1's existing schema files, `sets.ts`, constants and fixtures, or `docs/`.
- Screen-reader announcements and reduced motion (EXPERIENCE open item 22).

## Decisions

### 1. The workspace change comes first

As agreed with the integration session, task 1.1 alone touches manifests: `packages/widgets/package.json` gains `@askboard/contract`, `@askboard/view` and `@askboard/compute` as `workspace:*`, `react` 19.3.1, `radix-ui` 1.8.1 and, for development, `@types/react` 19.3.0; its tsconfig gains `jsx: react-jsx`. `bun install` changes `bun.lock` only in that importer entry, which the commit message says. The isolated linker resolves only declared dependencies, so `widgets` declares what it imports, and `@askboard/view` for the port's export. `radix-ui` is declared for the components that follow; the Tree imports none of it (decision 6). If the lockfile conflicts after E1 merges, `bun install` regenerates it and the diff stays additive. The one other manifest change, `contract`'s `"sideEffects": false`, is the integration session's own commit, taken unchanged (task 2.1).

### 2. The Tree's contract: standalone schemas, compiled where they are used

`packages/contract/src/widgets/tree/` holds:

- `tree-props.json` (`urn:askboard:input:tree-props`): `columns` (at most 8 of `{field, label, type}`, `type` `text` or `number`) and `nodes`, a recursive `$defs/node`: `id` (E1's ID schema, `urn:askboard:input:id`), `label` (1 to 200 characters), `children`, and field keys by `patternProperties` `^(?!(?:id|label|children)$)[a-z][A-Za-z0-9]{0,63}$`, each a string of at most 1,000 characters or a number (an `anyOf` inside the property, since Ajv's strict mode refuses union types); `additionalProperties: false` everywhere.
- `tree-changes.json` (`urn:askboard:output:tree-changes`): an array whose items `$ref` E1's `urn:askboard:output:answer-event#/$defs/change`, so a Tree's changes are the output format's changes, defined once, by E1; the Tree's own rules are in `treeChangesProblems`. No combinator at its root.
- `index.ts`: the types (`TreeColumn`, `TreeNode`, `TreeProps`, `TreeItem` `{type: "tree", id, props}`; a Tree's changes are typed as E1's `Change`, with no alias), the limits (`TREE_MAX_NODES` 500, `TREE_MAX_DEPTH` 8, `TREE_MAX_COLUMNS` 8, `TREE_LABEL_MAX_CHARS` 200, `TREE_TEXT_MAX_CHARS` 1,000), `TREE_FIELD_PATTERN` and `TREE_SHAPE` (decision 3).
- `checks.ts`, plain ECMAScript: `treePropsProblems(props, origin)` for what a schema cannot say (node IDs unique across levels; the `u-` prefix refused when `origin` is `agent`, accepted when `edited`, decision 11; each field key declared by a column; each value of its column's type; column fields unique; the node count and depth limits) and `treeChangesProblems(itemId, changes, props)`, the Tree's rules on the output format's changes (each target's item is the Tree's; `add`, `remove` and `move` target `item.node`, `set` targets `item.node.field`; an `add`'s `value` is an object holding `label` and declared fields of their types, never `id` or `children`; each `set` field is `label` or a declared column, with a value of its type, `label` never `null`). Problems name the node or operation and the field, as E1's do.
- `validate.ts`: `validateTreeProps(value, origin)` and `validateTreeChanges(itemId, value, props)`, each the widget validator of its schema (`widgetValidator`, task 2.10) and then the checks, returning E1's `Checked`.

**Standalone, compiled on first use.** The two schemas keep their own `$id`s, in the namespaces of the sets they will join, and are in no set: `sets.ts`, `SCHEMA_SETS` and `SCHEMA_IDS` do not change, so `schemaSetProblems` and E1's shared Ajv do not see them. `validateTreeProps` and `validateTreeChanges` are built on `widgetValidator<T>(schemas, id)` (`src/widgets/validator.ts`, task 2.10), with no Ajv and no error mapping of their own. Nothing runs when a widget validator is made; on its first use it takes the one widget Ajv, made by `createAjv()` and so holding E1's schemas (the ID schema, which `tree-props.json` references, and the answer event, whose `$defs/change` `tree-changes.json` references), adds the schemas whose `$id` it does not hold, compiles its own in strict mode and maps Ajv's errors through E1's `problemOf`. Nothing happens when a module loads: no module of `contract` adds a schema to an Ajv or writes to a registry at import time, which the package's `"sideEffects": false` requires (task 2.1). The schema tests compile the two schemas in strict mode in an Ajv made by `createAjv()` and check the Consistency Conventions' shape rules directly (JSON Schema 2020-12, the `$id` in its future set's namespace, no root combinator), not through `schemaSetProblems`. Nothing in E1's input format references `tree-props`, so no ask can carry a Tree, and the board page's validators, generated from E1's board document, refuse any board document holding one.

**Joining the sets later.** The follow-up that takes the input format to 1.1, after E1 merges, adds the two schemas to the input and output sets, where `schemaSetProblems` checks their owner and version, and lets the validators call `validateAgainst`. Agent-facing wording of props problems then comes through E1's request validation (`src/requests.ts`, `src/problems.ts`), as for every item of the input format (proposal, open question 20).

**Exports**, each in one block appended to an E1 entry module and no other change to an E1 file (Merge points): `src/index.ts` (the element diff from group 2; the Tree's types, limits, checks and `TREE_SHAPE`), `src/validate.ts` (opened by the widget validator in task 2.10; the Tree's two validators join it) and `src/fixtures/index.ts` (decision 4).

*Alternatives:* registering the schemas in `sets.ts` beside E1's sets (the first draft: an edit to E1's set list before E1 merges, and a registration Gantt would repeat); a schema set of its own for the Tree (AD-7's table puts widget props in the input format and answers in the output format, so it would need a spine change); the schemas inside E1's set folders (an edit to E1's set modules, which the brief forbids); adding the schemas to a shared Ajv when the module loads (an import-time side effect, which `"sideEffects": false` would drop); an Ajv of the Tree's own with a copy of E1's error mapping (the first revision: one copy per widget, which `widgetValidator` makes one); a `tree-changes.json` that defines the four operations again (a second definition of AD-20's operations beside the output format's, free to drift from it); the Tree's fields under a nested `fields` object, as compute's graph source writes them (the approved examples write them flat on the node, and lean JSON keeps them there).

### 3. One generic element diff, in `contract`, for `ask-core` to call

AD-20 has the view send the item's full edited value and `ask-core` alone compute `changes`; SOLUTION-DESIGN §4.8 adds that widget-specific diffs would put widget semantics in the core. So the diff is generic and widget-neutral, in `packages/contract/src/widgets/element-diff.ts`, plain ECMAScript, shared with the Gantt widget, its second user. A widget declares only its shape, `ElementShape`, in one of two forms:

- **A list shape** `{elements: string, children?: string, keyed?: false}`: the props key that holds the elements, a list of objects keyed by `id`, and, for a tree, the element key that holds its children. Without `children` the elements are a flat list (the Gantt's `{elements: "tasks"}`). The Tree declares `TREE_SHAPE = {elements: "nodes", children: "children"}`. Every key of an element other than `id` and the children key is a field, `label` included.
- **A keyed shape** `{elements: string, keyed: true}`: the props key that holds an object from element ID to the element's fields, as the Gantt's `schedule` maps task IDs to their fields. Every key of an entry is a field.

**The operations are E1's `Change`** (task 2.11). `elementChanges` gives, and `applyElementChanges` takes, the output format's `Change` (`src/schemas/output/index.ts`; `answer-event.json` `$defs/change`), so `ask-core` puts the diff's result into an answer event as it is. `add` and `move` name the parent and the preceding sibling and omit `parent` at the top level and in a flat list, and `after` at the first position, as AD-20 now says; no position is ever `null`, and `applyElementChanges` refuses one. The diff's own `ElementChange` type, whose positions were `null` when there was none (task 2.2), goes: E1's output format refuses a `null` `parent` or `after`, and since E1's fix ee10f3e, merged here as 6b84e1c, it lets `parent` be omitted as `after` was, so a diff that wrote `null` would give changes no answer event could carry.

`elementChanges(itemId, sent, edited, shape)` and its inverse `applyElementChanges(itemId, sent, changes, shape)` take the item's props as sent and as edited, leave their inputs untouched and return frozen outputs. For a list shape:

1. Index both values: each element's parent (none at the top level, and always none in a flat list), its sibling list and its fields.
2. Walk the edited elements in pre-order. In each sibling list, the elements that keep their parent form a longest subsequence in their sent order; they stay. Every other element gets an `add` (new, its `value` the element's fields without its children) or a `move` (kept, with another parent or out of that subsequence), with `parent` and `after` from the edited value, each omitted when there is none. Then, for a kept element, its `set`s, one per field whose value differs, in field-name order (UTF-16 code units): field values compare as JSON values, by deep equality, so an array or object field gets one `set` with its whole new value when it changes and none when it is equal, whatever the order of keys in an object; a field the edited element no longer has gets `null`.
3. After the walk, one `remove` per sent element missing from the edited value whose parent stays, in sent document order.

For a keyed shape, only `set`s: for each element ID in the union of the sent and the edited keys, in code-unit order, then each field in the union of its sent and edited fields, in code-unit order, one `set` `itemId.elementId.field` when the value differs, by the same deep equality, its value `null` when the field or the entry is gone. So a new entry gives one `set` per field, and a removed entry one `null` `set` per field it had; in UJ-2, the Gantt's new entry `u-1` gives exactly the answer's `schedule.u-1.dependencies`. Applying creates a missing entry, deletes a field set to `null` and then an entry left with no field, and throws "a keyed shape takes only sets" on an `add`, `remove` or `move`. The round trip holds for entries that are non-empty and hold no `null` field. IDs such as `constructor` and `__proto__` are ordinary entries.

Targets use AD-13's reference syntax without brackets: `itemId.elementId` for `add`, `remove` and `move`, `itemId.elementId.field` for `set`. A field value is never `null`: `null` in a `set` empties the field, and `applyElementChanges` removes the key. Applied in order, each `after` and `parent` that is given names an element already placed, since the walk is in document order, and a removed element's subtree holds only removed elements by then, since every kept descendant moved out. `applyElementChanges` throws, naming the operation, on one that does not apply (an unknown target, a `parent` in a flat list, an `after` that is not a sibling, a `null` position, an `add`, `remove` or `move` on a keyed shape).

The diff's own tests run on generic data in three forms, never on the Tree: a nested shape, a flat shape whose elements carry an array field, and a keyed shape with an array and a scalar field. A property test over seeded random edit sequences in each form checks `apply(sent, diff(sent, edited)) = edited`; table tests check the minimal cases (one `move` for an element moved to the front, none for its siblings; one `remove` for a branch; one `set` for a changed array field and none for an equal one; one `set` per field for a new keyed entry and a `null` `set` per field for a removed one); every operation they produce, in all three forms, validates against E1's `$defs/change` (task 2.11). The Tree's contract group checks the diff on Tree values: every result passes `validateTreeChanges`, and FR-20's 200-node case gives exactly three operations for three changes. `ask-core` calls it when the follow-up wires widget answers; Block 2 of `spine-update-draft.md` records the placement and the keyed shapes (proposal, open questions 4 and 19).

*Alternatives:* the diff in `packages/core` (outside this change; the follow-up would write it with no fixture to check against); a per-widget diff in `contract`, or the diff under `widgets/tree/` (widget semantics where AD-20 wants one generic diff, and a second copy for the Gantt); the Gantt turning its `schedule` into a list before the diff (a conversion per widget, where AD-20 wants one generic diff); the diff's own operation type with `null` positions (task 2.2's first form: changes the output format refuses); `set`s in column order (the diff knows no columns) or in the value's key order (two equal values would give two orders); the view emitting operations (AD-20 forbids it, and a reload would lose their order).

### 4. Checked against the approved UJ-2 examples, and the fixtures built from them

`asks/uj2-wbs-gantt.json` and `answers/uj2-wbs-gantt.json` are already in `packages/contract/test/fixtures/`, copied byte for byte by E1's task 3.1 and merged here with d4a31c4; this change copies nothing, and task 3.4 checks with `cmp` that both still match the archive. The Tree part validates as follows:

- **The same:** node IDs, names, the three numbers per leaf, nesting under `children`; every `wbs.` operation of the answer, the `add` of `u-1` with `parent: "build"`, `after: "portal"` and a `value` of name and fields, and the `set`s on names and numbers.
- **What differs, and why:** the tree sits in a `wbs-pert` molecule's `data.nodes`, which declares its own fields, while a plain Tree is `{type: "tree", props: {columns, nodes}}`, so the check supplies the three number columns; each node's `excerpt` is the molecule's excerpt pointer (AD-12), resolved at send time and shown as a row detail, not a Tree field, so the check strips it and asserts it is the only key stripped; `schedule.u-1.dependencies` is the Gantt plan's operation, not the Tree's (the keyed shape gives it, decision 3, and the Gantt change checks it); and the answer lists operations in the user's order while the diff gives its own (decision 3), so the check compares them as sets and checks the diff's order separately. The answer's `derived` waits for compute (proposal, open question 3).

The fixtures (`packages/contract/src/fixtures/tree.ts`, tests only): `treeBoardDocument`, the UJ-2 plan as a board document whose question `plan` (rev 1, its text and header from the example, no options) holds the Tree item `wbs` with the three number columns and the eight nodes; `treeEditedValue`, that Tree after the approved edits; `treeAnswer`, the answer event of the example without the Gantt operation and `derived`, its `changes` in the diff's order, typed as E1's `AnswerEvent`. A contract test checks that they agree (spec, Tree fixtures), and that `treeAnswer` validates against E1's answer event, which is on this branch since d4a31c4. The board document's type is the contract's board document with a question that may hold widget items, written in the fixture file.

### 5. The edit model: pure functions in `packages/widgets/src/tree/model/`

Everything the Tree decides is a pure function over `TreeProps`, tested under `bun test` with no DOM. The widget-neutral helpers it uses live in `packages/widgets/src/shared/`, built with the seams (decision 12) and tested on their own: `ids.ts`, the next view-made ID (decision 11), and `number.ts`, the en-US parser (optional sign, digits with comma groups of three, optional decimal part), which refuses an ambiguous or malformed entry with a reason, and the formatter for the echo.

- `rows.ts`: the visible rows from the nodes and the expanded set (depth, parent, position and set size, whether it has children and is expanded); all expanded by default (proposal, open question 8).
- `edits.ts`: `addAfter`, `addChild`, `rename`, `setField`, `remove` (with the count of nodes it takes), `moveUp`, `moveDown`, `indent`, `outdent`, each returning a new frozen value, or the same value when nothing changes; a new node takes its ID from `shared/ids.ts`; `can(edit, value, nodeId)` for the toolbar and the keys, which enforces the moving rules (proposal, open question 13) and the limits (open question 16) through the contract's constants.
- `marks.ts`: per node, added, moved, renamed or which fields changed, against the sent value, and the count "Your changes" shows (proposal, open question 14); `sameNodes(a, b)`, so the component puts `undefined` in the draft when the edits come back to the agent's value.
- `keys.ts` and `focus.ts`: the treegrid's focus position (a row, or a cell of it), its moves on the arrow keys, Home and End, expand and collapse on Right and Left, and the action of each key in navigation and in edit mode (proposal, open question 9); the toolbar's roving focus; where focus goes after a delete (next sibling, previous sibling, parent).

The model never computes a value from another (proposal, open question 3) and never builds `changes`: the marks compare nodes for display only.

### 6. The component: a treegrid in the widget frame

`packages/widgets/src/tree/index.tsx` registers `tree` through `@askboard/view/catalog`; the rest of the folder renders the model:

- **Frame** (DESIGN.md, Widget frame): a bordered frame with a toolbar row on `muted`: the tools "Add node", "Add child", "Move up", "Move down", "Indent", "Outdent" and "Delete" as `button-secondary`, each with its key in `aria-keyshortcuts` and its title, then the counter on the right. One Tab stop with arrow keys among the tools (proposal, open question 10). The delete confirmation replaces the tools in that row (open question 11).
- **Grid:** `role="treegrid"`, labelled by the question's text; a header row of `columnheader`s in `text-label` on `muted`; one `row` per visible node with `aria-level`, `aria-posinset`, `aria-setsize` and, on a parent, `aria-expanded`; `gridcell`s for the name and each field. One element holds `tabIndex` 0 (roving focus), and keyboard focus shows the focus ring. Indentation is a class per level, written for the 8 levels, not a `style` attribute (AD-8). The chevron, in `muted-foreground`, points right when closed and down when open; a click on it toggles.
- **Editing:** Enter or F2 swaps the focused cell for a text input; Enter or blur commits through the model; Escape restores. A number field shows the parsed value beside it ("= 1234.5") in `text-code`, and a refused entry a `field-error` under the row, keeping the focus and the draft. A new node opens with its name in edit mode (open question 12).
- **States:** `disabled` (answered, being sent, locked) leaves navigation, expand and collapse and turns off editing keys and tools; the change highlight from `marks.ts` uses DESIGN.md's `change`, `change-subtle` and `change-text` tokens (a changed cell's fill, text and border; an added row's 2px bar; the name of a moved row); `useReadyAfterLayout` reports ready once laid out.
- **Data it did not get through the board page:** the view hands a widget item's props over as data (decision 7), so the component checks `item.props` with `treePropsProblems(props, "agent")` and throws on a problem, so the error boundary fails the item (AD-10). Only test documents reach it before the follow-up.

*Alternatives:* TanStack Table's tree mode with Pragmatic drag and drop, as EXPERIENCE chooses (neither installed; proposal, open question 6); Radix Toolbar (not in the Stack's list of Radix primitives); a modal Alert Dialog for the confirmation (open question 11).

### 7. View integration: widget items in a question

Small edits to E1's view, written for any widget item and tested with a test-only `probe` item (decision 12), each with tests first, leaving Choice's behaviour as E1's browser tests check it (proposal, open question 21):

- **Port** (`catalog/port.ts`): `ItemProps<Item, Value>` carries `item`, `questionId` (whose text labels the item), `value: Value | undefined` (the draft value; `undefined` is untouched), `onValueChange(value | undefined)`, `disabled` and `ready`; `register` takes any component. Choice reads `undefined` as no choice.
- **Draft record** (`shell/draft-store.ts`): one `unknown` value per item ID; setting `undefined` removes it; arrays compare by element and other values by identity, since a widget's model returns the same value for an edit that changes nothing.
- **View document** (`view-document.ts`, new): the board document as the view renders it, a question whose props may hold `items` of widget items and may have no options, as AD-7 (Questions) and F1 fix. A widget item is `{type, id, props}` with any `type` other than `question`; the view treats its props as data and leaves their check to the widget's component (decision 6). E1's `BoardDocument` is assignable to it; only test documents use the wider shape before the follow-up, since the board page validates every board document against E1's schema. `boot-data.ts`, `assemble` and `selectChunks` take it.
- **Components and readiness:** `componentsOf` gives `choice` for a question with options and each widget item's `type`; a type no chunk registers fails `assemble`, and in the shell the renderer's unregistered path. A question's items for the ready tracker are its own ID when it has options, then its widget items' IDs.
- **Question card:** options when there are any, then each widget item through `RenderItem` at the card's full width; `canAnswer` when the question is answerable and has a choice or any widget draft value; the act and `shown` per item.
- **View protocol:** `ViewAnswer` gains `values` (widget item ID to the item's full edited props), and `choice` becomes optional, one of the two being required; `readViewMessage` checks `values` structurally (own-property item IDs, object values). The content is checked by whoever can carry it.
- **Board page** (`board-page/model.ts`): `answerCommandFor` refuses an answer with `values`, or without `choice`, saying the board protocol carries no widget value yet; the card's act then drops and the question is open again (E1's answer-acts rule). Its host-message validators, generated from E1's board document, already refuse a board document whose question holds widget items; a test says so.

### 8. Build integration: widget chunks beside the catalog's

`tools/build/paths.ts` gains `WIDGETS_SRC` (`packages/widgets/src`); `chunks.ts` finds component chunks in the folders of both roots that hold an `index.tsx`, and fails the build naming both folders when one name appears in both. `shared/` holds no `index.tsx`, so it is no chunk. The roots are a parameter, defaulting to the two, so the tests use scratch chunk folders and a test-only `probe` chunk, never the Tree. Everything else applies unchanged: the shared-modules plugin maps a widget's `react`, `react/jsx-runtime` and `@askboard/view/catalog` imports to the React chunk and the shell, so `tree` needs `react` and `shell`; Tailwind scans its sources, which are under `packages/`; its licence notices are the repository's MIT, since React and the port come from other chunks; no `import.meta`. The contract code it uses (checks and limits) is bundled into it, and `"sideEffects": false` lets the bundler leave out the contract modules it does not use. `chunk-sizes.json` records `tree`, and the shell's growth from decision 7, with `--record-sizes`: a seam task that grows a chunk past the margin records it in its own code commit, and the Tree chunk group records `tree`. Block 1 of `spine-update-draft.md` states it in AD-9 (proposal, open question 22).

*Alternative:* a separate build or manifest for `widgets` (two manifests for `board-host` to read, and `assemble` would have to merge them).

### 9. The test-only path: a widget host

The real board page cannot show a widget item: its validators refuse the document (fail closed), and bypassing them would test a path production never takes. So the widgets' browser tests use a **widget host**, test code under `packages/view/test/browser/`, written for any board document:

- `fixtures/widget-host-page.ts`, bundled as a classic script the way the harness bundles its throwing Choice: it reads the srcdoc from a JSON data block, creates the frame with exactly `sandbox="allow-scripts"`, calls the board page's own `hostView` before setting the srcdoc, sends one update with the question open, and passes every view message to a Playwright binding, answering an answer with `{outcome: "sent"}`.

### 11. Widget element IDs: one rule for every widget

Every widget's element IDs follow one rule, which the Gantt widget shares: an element ID matches E1's `ID_PATTERN` and is unique in its item, at every level; `VIEW_ID_PREFIX` (`u-`) is refused in an agent's value and accepted in an edited value; view-made IDs are `u-<n>`, with `n` one more than the highest such number in the item's value (`shared/ids.ts`), so the first is `u-1` (F10). One rule keeps one ID for one element across the items of a molecule: in UJ-2 the Gantt task `u-1` (`schedule.u-1.dependencies`) is the Tree node `u-1` the user added, the task the molecule gives the added work package (F20, with the WBS-with-PERT change). Each widget's checks apply the rule to its own elements (`treePropsProblems` for the Tree), and the generic diff relies on it, since it addresses elements by ID.

## Risks / Trade-offs

- [Alt+Shift with the arrow keys may be taken by an engine or a desktop] → Each binding's test fails if the page navigates or the key does nothing; if one cannot hold, the move keeps its toolbar button, the key changes, and the PO is told.
- [The tree chunk may carry the contract's schema JSON through the barrel import] → The checks module imports no JSON, and `"sideEffects": false` lets the bundler drop the contract modules the chunk does not use; the task that first builds the chunk records whether it holds a schema `$id`. If the bundler keeps the JSON anyway, the size is recorded with its cause in the task's note, and a JSON-free `contract` entry, which needs a `package.json` change this change may not make, goes to the integration session.
- [Ajv's strict mode may refuse the look-ahead in the field-key pattern] → The schema test compiles it in strict mode first; the fallback is a plain pattern and the reserved names refused in `treePropsProblems`.
- [`tree-changes.json` depends on E1's `$defs/change` by `$id` and pointer] → `createAjv()` resolves it in the widget Ajv, and the Tree's schema test compiles it, so a moved or renamed definition fails that test by name.
- [A seam commit that touched a Tree file or `openspec/` would carry them into the Gantt branch] → Decision 12's commit rule, checked with `git show --stat` before each seam commit and recorded in the task's note.
- [The widget host could drift from the board page] → It uses the board page's own `hostView`, `assemble` and policy shape; only the socket and the validators are absent, and the follow-up re-runs the scenarios through the real board page.
- [E1's view files change here, and E1's integration is still open] → Each edit is small, tested first, and listed under Merge points; E1's browser suite runs in every task that touches the view.
- [No virtualisation] → The 500-node limit, and a browser test that a 200-node Tree becomes visible and moves a node within the step timeout; virtualisation comes with the drag and TanStack change.
- [A diff in `contract` is code where AD-20 names a format] → Block 2 of the spine draft; `ask-core` is its only run-time caller, and the view never imports it outside tests.
