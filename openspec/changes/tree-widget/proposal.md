# Proposal

## Why

The build order puts the widgets AXFX needs first, starting with the Tree that the WBS-with-PERT molecule is built on (SOLUTION-DESIGN §3.1, AXFX FR-38 through FR-11 and FR-15). E1 gave the view its shell, the `CatalogRenderer` port, the draft record, `assemble` and the chunk build, but every catalog component lives in `packages/view` and holds a list of option labels. This change builds the Tree as the first widget in `packages/widgets`, on those seams, so that the follow-up that lets an agent ask a Tree, and the WBS-with-PERT change after compute merges, only connect it. The Gantt widget, built in parallel (change `gantt-widget`), reuses the widget-neutral seams this change builds first.

## What Changes

- **`widgets` workspace:** `packages/widgets` declares `@askboard/contract`, `@askboard/view` and `@askboard/compute` (`workspace:*`), React 19.3.1 and `radix-ui` 1.8.1, and `@types/react` 19.3.0 for development, all already pinned in `bun.lock`, and compiles JSX. `bun.lock` changes only in that package's importer entry: no package or version is added.
- **Widget-neutral seams, first and shared with the Gantt widget:** built as their own task group, written for any widget item and tested with a test-only `probe` item and scratch chunk folders, never the Tree, so that the Gantt branch cherry-picks their commits instead of duplicating them (open question 23):
  - `contract`'s package manifest marks it `"sideEffects": false`, the integration session's own commit taken unchanged, so nothing in `contract` may register anything when it is imported;
  - the generic element diff, `packages/contract/src/widgets/element-diff.ts`: `elementChanges` computes AD-20's `changes` (`add`, `remove`, `move`, `set`) from an item's sent and edited value, for elements that form a tree or a flat list, and `applyElementChanges` is its inverse, for `ask-core` to call; each widget declares only its shape (open question 4);
  - the widget-neutral model helpers in `packages/widgets/src/shared/`: the next view-made ID and the en-US number parser and formatter;
  - in `view`: the port carries any value type and the draft record holds one value per item; a question can hold widget items beside or instead of its options, which the shell renders, tracks for readiness and answers together; "Answer" is enabled by a widget change and sends the item's full edited value (AD-20); `assemble` selects a widget's chunk; the board page refuses an answer carrying widget values, since the board protocol has no field for one yet (AD-10);
  - in `tools/build/`: component chunks are also found in `packages/widgets/src/<name>/index.tsx` and built with the same shared-module plugin, styles, licence notices and size check (AD-9);
  - a test widget host for the browser tests, since no E1 board document can hold a widget item.
- **`contract`, the Tree, new files only:** the Tree's item props (`columns` of text or number fields, and `nodes`, each `{id, label, children?, <field>…}`) and its `changes` (AD-20's operations on nodes), both owned by `contract` (AD-7), as standalone schemas with their own `$id`s, `urn:askboard:input:tree-props` and `urn:askboard:output:tree-changes`, compiled only inside their validate exports `validateTreeProps` and `validateTreeChanges` (open question 20); the checks a schema cannot express (node IDs unique in the item, the reserved `u-` prefix, declared fields, value types, limits); the Tree's element shape `TREE_SHAPE` for the generic diff; a Tree board document and a Tree answer as test fixtures, checked against the approved `uj2-wbs-gantt` examples. One export block is appended to each of `contract`'s three entry modules; `sets.ts`, `SCHEMA_SETS`, `SCHEMA_IDS` and every E1 schema, constant and fixture stay as they are.
- **`widgets`, the Tree:** a pure edit model (visible rows, add, rename, edit a field, delete, move up, down, indent and outdent, change marks, the keyboard map) on the shared helpers, and the component on it: a treegrid in the widget frame with a toolbar, expand and collapse, inline editing, an inline confirmation before deleting a node with children, the change highlight and the "Your changes" counter (FR-11, EXPERIENCE Widgets, Tree; DESIGN.md Widgets, Tree). Node fields hold plain values: no roll-up, formula or derived value (open question 3).
- **Tests:** unit tests for the seams, the contract part and the edit model at 80% per file; browser scenarios in Chromium, Firefox and WebKit through the test widget host, first on the plain Choice board document, then with the Tree: keyboard paths, the moving rules, the answer's `changes`, markup as text and no CSP violation.
- **Spine:** two clarifications drafted in `spine-update-draft.md` (AD-9 for widget chunks, AD-20 for where the diff function lives), applied only if the PO accepts open questions 22 and 4. No PRD or UX document change.
- **Not in this change:**
  - Widening the input format, the board document and the board protocol so that an agent can ask a Tree and `collect` its `changes`: the first follow-up after E1 merges, which also takes the Tree's schemas into the input and output sets (input format 1.1) and wires `ask-core` to the contract's diff.
  - WBS with PERT, PERT and formula columns, roll-ups and `derived` values: the WBS-with-PERT change after compute merges (FR-12, FR-14, FR-15).
  - Revisions, the draft mirror and reload restore, and the agent-change notice on an edited Tree (E3).
  - Drag, virtualised rows and the TanStack Table tree mode (open question 6); money, date and on/off fields and it-IT input (open question 7).

## Capabilities

### New Capabilities

- `contract`: standalone widget schemas compiled on demand, the widget element ID rule, the generic element diff, the Tree's item props, its `changes`, their checks and the Tree fixtures (AD-7, AD-13, AD-20). - `view-and-widgets`: widget items in a question, their chunks and their answers, and the Tree widget (AD-8, AD-9, AD-10, AD-20). The same holds for E1's requirements here.

### Modified Capabilities

None: `openspec/specs/` is empty.

## Open questions for the PO

The PO is away and asked every session to keep working. Each question records the narrowest choice taken and why; the change is applied with these choices, and each can be reversed later.

1. **The input format is not widened** (agreed with the integration session). The Tree's props and `changes` go in new contract files, and the board side is tested with test board documents. "Widen the input format so an agent can ask a Tree" is the first follow-up after E1 merges.
   - **Resolved (integration session, 2026-10-30):** agreed as stated.
2. **No PERT, no formula columns, no molecule** (agreed with the integration session). Node fields hold plain values, and items keep flat IDs so compute's references (`wbs.portal.optimistic`) address them unchanged.
   - **Resolved (integration session, 2026-10-30):** agreed as stated.
3. **No derived values.** The Tree shows no roll-up and no total, and its answer carries no `derived`. Plain sums written in the widget would be the private computation AD-13 forbids ("widgets read and write graph values and define no node"), and F7 fixes which derived values an answer carries per widget with compute. FR-12's Tree consequence is met by the WBS-with-PERT change, which wires compute.
4. **Where `changes` are computed.** As AD-20 and SOLUTION-DESIGN §4.8 say, the view sends the item's full edited value and widgets never emit diffs. The diff function itself is widget-neutral: `elementChanges(itemId, sent, edited, shape)` and its inverse `applyElementChanges(itemId, sent, changes, shape)` work on any item whose elements are ID-keyed, with `ElementShape = {elements: string, children?: string}` naming the props key that holds the elements and, for a tree, the key that holds an element's children. Without `children` the elements are a flat list, as the Gantt's tasks are, and every `add` and `move` has `parent: null`. Every key of an element other than `id` and the children key is a field, and field values compare as JSON values, so an array field gets one `set` when it changes and none when it is equal. The function lives in `contract`, beside the formats it produces, in `packages/contract/src/widgets/element-diff.ts`; the Tree declares only `TREE_SHAPE`, and `ask-core` is its only run-time caller once the follow-up wires it; the tests use it now. Block 2 of the spine draft states this in AD-20. The alternative, writing it in `packages/core`, is outside this change's scope.
   - **Revised (integration session, 2026-10-31):** the first draft put the diff under `widgets/tree/diff.ts` and allowed only trees. It is now shared with the Gantt widget: flat lists and array fields are part of its contract, and its tests run on generic data, not on the Tree.
5. **The test-only path.** E1's board document holds one plain question, and the board page validates every board document against it, so no Tree can reach the view through the board page (fail closed). The view renders a question that holds widget items (AD-7, Questions; F1) from data, and the browser tests load such a test document through a widget host: a test-only page that assembles the view from the real build with `assemble` and hosts it with the board page's own `hostView`, recording every view message. Until the follow-up, a widget answer gets no logged state, so the card stays read-only at "sent".
6. **No new dependency.** EXPERIENCE builds the Tree on TanStack Table's tree mode with Pragmatic drag and drop and virtualised rows; neither package is installed and this change adds none. The Tree's row model is a small pure function, there is no drag (every move has a toolbar button and a key, which EXPERIENCE requires anyway), and rows are not virtualised: FR-20's 200-node example renders as plain rows. Drag, virtualisation and the TanStack adoption come in a later change, with the sandboxed-frame drag spike item; EXPERIENCE stays as it is.
7. **Two field types, en-US only.** Columns are `text` or `number`. A number is typed in a text input and read by AskBoard's own en-US parser, never `type="number"`, with the parsed value echoed and an ambiguous entry refused (EXPERIENCE, Input atoms); E1 accepts only `en-US`. The parser and formatter are widget-neutral, in `packages/widgets/src/shared/number.ts`. Money, date and on/off fields, units and bounds, and it-IT input come with the atoms' epics and E8.
8. **Expand and collapse in a standalone Tree** (EXPERIENCE open item 24). The Tree component has them: DESIGN.md's Tree spec draws the chevron, the treegrid keyboard pattern uses them, and the WBS molecule needs them. A standalone Tree opens fully expanded and takes no depth prop; the molecule's "expanded to the depth the agent sets, or two levels" comes with it. Expand state is view state, not draft.
9. **Key bindings** (EXPERIENCE open item 21). WAI-ARIA treegrid navigation (arrows, Home, End; Right and Left expand, collapse and move between cells); Enter or F2 edits the focused name or field, Enter commits, Escape cancels; Alt+Shift+ArrowUp and ArrowDown move a node, Alt+Shift+ArrowRight and ArrowLeft indent and outdent; Delete or Backspace deletes. Alt+ArrowLeft and Alt+ArrowRight are avoided because they navigate history in Firefox and Chromium on Linux; the browser tests check in each engine that the chosen keys do nothing else.
10. **Two Tab stops.** EXPERIENCE gives each widget one Tab stop (F-67), and DESIGN.md's widget frame puts the tools in a toolbar. The toolbar is one Tab stop with arrow keys among its buttons and the tree another, as the Graph's keyboard minimum ("Add transition") implies for a widget with tools. The toolbar holds the tools and the counter and no widget name: the question's text labels the tree. No Radix Toolbar, which the Stack's Radix list does not name.
11. **Inline delete confirmation.** Deleting a node with children asks first and says how many nodes go with it, in the toolbar row, with the focus on "Cancel". An Alert Dialog would be modal, and its scroll lock needs the view's style-element shim (S-6), which E1 did not build. The wording is not recorded in EXPERIENCE.
12. **A new node needs a name.** "Add node" and "Add child" insert a node in rename mode with an empty name; an empty commit or Escape takes it away again. No default label is ever sent as if the user had written it (AD-10).
13. **The moving rules.** Up and down swap with the neighbouring sibling and stop at the ends; indent makes the node the last child of its previous sibling, which expands; outdent places it right after its parent, and its later siblings stay where they are. A move carries the subtree, and focus follows the node. A move that is not possible is disabled, never wrapped.
14. **What the change highlight shows.** Changed names and fields take the change hue and border, an added row the 2px bar, a moved row a change mark on its name; a removed node leaves no row but counts in "Your changes: N", which counts each added, removed, moved or edited node once (EXPERIENCE, By surface: Widget). Ghost rows for removed nodes are not built.
15. **Widget element IDs, one rule for every widget.** An element ID matches E1's `ID_PATTERN` and is unique in its item, at every level; the view-made prefix `u-` (`VIEW_ID_PREFIX`) is refused from the agent and accepted in an edited value; view-made IDs are `u-<n>`, with `n` one more than the highest in the item's value, so the first added node is `u-1`, as in the approved answer (F10). One rule keeps one ID for an element across the items of a molecule: in UJ-2 the Gantt task `u-1` is the Tree node `u-1`. The helper is widget-neutral, in `packages/widgets/src/shared/ids.ts`.
    - **Revised (integration session, 2026-10-31):** the rule was the Tree's; it is now every widget's, shared with the Gantt widget, and the helper moved from `tree/model/ids.ts` to `shared/ids.ts`.
16. **Limits.** At most 500 nodes, 8 levels, 8 columns, 200 characters in a name and 1,000 in a text field, so an unvirtualised tree stays responsive; FR-20's 200-node example fits. Indent past the depth limit and adding past the node limit are disabled.
17. **Field names** match `^[a-z][A-Za-z0-9]{0,63}$` and are not `id`, `label` or `children`. Every such name is a field name in compute's grammar and never a cell, since cells are upper case. `label` is the node's name and is addressed like a field (`wbs.portal.label`).
18. **`parent` and `after` are always given** on `add` and `move`, `null` for the top level and for the first place (F3), so an agent never infers a position from an absent field. The generic diff gives a flat list's `add` and `move` `parent: null` too (open question 4).
19. **The order of `changes`.** AD-20 fixes none. The diff walks the edited elements in document order, giving each element's `add` or `move` and then, for a kept element, its `set`s in field-name order, and lists the `remove`s last, for removed elements whose parent stays; applied in order, they rebuild the edited value. The approved UJ-2 answer lists its operations in the user's order, so the check compares them as a set.
    - **Revised (2026-10-31):** the `set`s of one element come in field-name order (UTF-16 code-unit order, so `portal`'s are `label`, `mostLikely`, `optimistic`, `pessimistic`), not the name first and then the column order: the generic diff knows no columns, and an order that ignores the keys' order in the value keeps the diff deterministic.
20. **The Tree's schemas are standalone** (agreed with the integration session). `tree-props.json` and `tree-changes.json` keep their own `$id`s, `urn:askboard:input:tree-props` and `urn:askboard:output:tree-changes`, in the namespaces of the sets they will join, and are compiled only inside `validateTreeProps` and `validateTreeChanges`: on its first call, each adds them, with E1's ID schema they reference, to an Ajv of the Tree's own, made with `createAjv`'s options (strict mode, all errors). `sets.ts`, `SCHEMA_SETS` and `SCHEMA_IDS` do not change, and nothing in `contract` relies on import-time side effects: no module adds a schema or writes a registry when it loads (task 2.1). Their tests compile them in strict mode with `createAjv`'s options and check the Consistency Conventions' shape rules directly, not through `schemaSetProblems`. They join the input and output sets in the follow-up that takes the input format to 1.1, after E1 merges, which also checks their owner and version as set parts and lets the validators use `validateAgainst`, dropping their own Ajv and their copy of E1's error mapping, which is private to `validate.ts`.
    - **Resolved (integration session, 2026-10-31):** replaces the first draft, which registered the two schemas in `sets.ts` as parts of the input and output sets, the output part on the examples' version `1.0`.
21. **E1's view code changes here.** The port's value type, the draft record, the question card, the view protocol's answer and the board page's answer check are E1 files; the seams edit them for any widget item, keep each edit small and list them for the integration session (design, Merge points). Choice keeps its behaviour, which E1's browser tests check.
22. **Widget chunks in the view's manifest.** AD-9 has `view` publish one chunk per catalog component, and the Structural Seed puts the widgets in `packages/widgets` as catalog components, but nothing says who builds their chunks. The view build finds them there as it finds the atoms in `packages/view/src/catalog/`, in one manifest, and a widget imports only the port from `view` (AD-1). Block 1 of the spine draft adds that sentence to AD-9.
23. **The widget-neutral seams come first** (agreed with the integration session). They form task group 2, right after the workspace: `contract`'s `"sideEffects": false`, the generic element diff, the shared model helpers, the draft record and the port, the view document with widget items, the answer path, the board page's refusal, the widget chunk discovery and the test widget host. Their code commits touch no Tree file and no file under `openspec/`, their tests use a test-only `probe` widget item and scratch chunk folders, and their ticks go in separate `docs(tree-widget)` commits, so the Gantt branch cherry-picks the code commits as they are. The Tree's contract, model, chunk and component follow.
    - **Resolved (integration session, 2026-10-31):** agreed as stated.
