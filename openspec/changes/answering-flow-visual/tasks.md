# Tasks

Each task writes its tests first and sees them fail for the right reason before implementing.

Terms used below:

- **"The check"** means `bun run build && GITHUB_TOKEN=$(gh auth token) bun run check`.
- **"File run"** means `ASKBOARD_E2E_ENGINES=chromium ASKBOARD_E2E_TARGET=session-process bun test ./packages/view/test/browser/<file>`, after `bun run build`: Chromium only, for the files a task names (PO's decision on #227, 2026-11-16: no multi-engine or full suite inside the change; Firefox and WebKit run in CI's e2e train on `main`). One browser process at a time on the machine.
- **"The fixture"** means `packages/view/test/browser/fixtures/answering-flow-asks.ts` as changes 1 and 4 left it (nine questions in three areas, sections, tabs and one question per view, en-US and it-IT, four recommendations, the TextFields "Service name" and "Ticket", a single-question ask). A task that needs more (a 120-character title, forty questions, a long option description) adds it there, neutral content only.
- **"Design Dn"** refers to design.md's decisions, so as not to be read as a short question number. A requirement cited by name is in this change's delta specs. Report sections ("§6.4") are `drafts/ux-review-168/ux-review-report-1.1.0.md`; "settling point n" is `drafts/ux-review-168/cabina-settling-1.0.0.md`; "frame nn" is a screenshot in `drafts/ux-review-168/proposals/screenshots/b-1.1.0/`.
- Browser tests find controls through the harness's locators (change 4's, and those of task 3.1), never by label, except tests that assert a label. Every new browser file is listed in `packages/view/test/browser/harness/suites.ts`, with no `engines` restriction; `answering-flow-frame.browser.ts` joins the smoke set. Waits are probes (`eventually`) or `quiet(reason)`; no time bound is asserted outside the perf files.
- Each group writes the DESIGN.md and EXPERIENCE.md rows of what it builds, in the group's own commit with its code, tests and task notes (PO's decision on #227, 2026-11-16); group 9 writes the records that span the change. Italian strings outside report §4 are marked "(to review)" in EXPERIENCE.md's Voice and Tone (PO, #168, 2026-11-15).
- An icon is added to `packages/view/src/icons/index.ts` in the task that first renders it, never ahead (icon-set's "every icon used" test), with its row in DESIGN.md's Icons table.
- Commit bodies say `Refs #168`, and `Refs #213` for the ask pill's records. Each group commits its own paths only (`git add <paths>`, never `-a`).
- **Reviews, checks and suites** (PO's decisions of 2026-11-16, the second on #227). No review checkpoint at the end of a group: the per-group checkpoint tasks are marked covered, and the one review is the pre-PR review (task 10.2). During the groups, verify with the unit tests of the packages touched, `bun run typecheck` and Chromium File runs; the whole check runs once, at task 10.3, before the pull request. No full or three-engine suite runs inside the change: the pull request gets CI's smoke set, and the full three-engine suite runs later in CI's e2e train on `main` (#227).

**Order and parallelism.** The base is task 0.2's local integration: this branch rebased onto `answering-flow-guidance`'s head dd2c23e4, which sits on `main` 46d3dcf7 and so holds #212, #210 and #225 (board-keys). Groups 1 and 2 start now, one after the other, since one implementer runs every group of the change (PO's decision on #227, 2026-11-16); their files are disjoint (group 1: `packages/contract/**`, `packages/core/test/**`, `packages/server/test/**`, the spine; group 2: new pure modules under `packages/view/src/shell/` with their tests, `packages/view/src/strings/**`, the comment on `askPillOf`); task 0.3's probes may run beside them. Group 3 and later wait until change 4 has finished its groups 6 to 10 (the sticky tab strip, `CompletionPanel`, the prefill result with "Undo", the ladder icons, the reduced-motion rule): the coordinator then rebases this branch onto change 4's later head (`git rebase --onto <new guidance head> <recorded guidance SHA>`), or onto `origin/main` once change 4 is squash-merged, records the new SHA in task 0.2's note and re-runs its checks (names, versions, sizes, the nine requirements); a difference goes through `/openspec-update-change` before group 3. Groups 3 to 11 run one after the other: they share `board.tsx`, the header, the rail, the strings, `suites.ts`, DESIGN.md, EXPERIENCE.md and the browser lock; group 7 needs group 1. Task 10.1 rebases onto `origin/main` after change 4's squash merge with `git rebase --onto origin/main <guidance SHA>`, the last guidance SHA task 0.2's note records. Within a group, tasks run in order. One implementer, effort high for groups 1 and 10, medium otherwise (askboard-delivery).
