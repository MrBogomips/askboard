# Track B requests

Changes Track B needs in files it does not own (tasks.md, Parallel tracks). Each entry says what, why, the task it blocks, and how Track B works around it meanwhile.

## 1. One rule for the board page's CSP (task 8.3, not blocking)

- **What:** a contract function, for example `boardPagePolicy(manifest: ViewManifest): string` beside `cspHashSource` in `packages/contract/src/hash.ts` or `routes.ts`, that builds the board page's policy from the manifest: `default-src 'none'`, `script-src` with the board page script's hash and every chunk script's, `style-src` with the board page's and every chunk's style hashes (`'none'` when there are none), `connect-src 'self'`, `img-src data: blob:`, `font-src data:`, and no `frame-src` in E1 (AD-8, design decision 5, board-host spec "The board page and its policy").
- **Why:** `board-host` (Track A, 6.3) computes this policy, and so does the view's test server (Track B, 8.3), which must answer as `board-host` does. Two copies of one rule can drift, in a directive or in whether `default-src 'none'` is there, and the browser tests would then pass against a policy the real session process does not send.
- **Blocks:** nothing. Workaround: the test server's own copy, `packages/view/test/browser/harness/policy.ts` (`boardPagePolicy`), unit-tested against the rule above; the harness check in `harness.browser.ts` compares the served policy with it by directives and sources, not by text, so 9.3 can run it against `board-host` whatever order that writes. If the contract gains the function, the test server uses it and its copy goes.

## 2. Serve the board page at a board link without `t` (task 8.6, blocking the reload scenario)

- **What:** in the contract's `BOARD_RESPONSES` and in `board-host` (Track A, 6.2 and 6.3), `GET /b/<askId>` without `t`, for an ask the session process serves and has not discarded, answers the board page (200, under its policy) instead of the invalid-link page. A wrong token, an unknown ask and a discarded ask's link answer as now. The page holds nothing of the ask: the socket's `connect`, `/m` and `/c/` check the token exactly as now, and a board page that finds no token shows that the link opens no board.
- **Why:** the review of 8.1 to 8.5 (M1) found that the view could read the token: a srcdoc document takes its base URL from the board page, so `document.baseURI` inside the view held the link with `?t=` in Chromium, Firefox and WebKit (AD-8, "the view never holds a token"). Since 8.6 the board page takes the token out of its URL with `history.replaceState({ token }, "", <path>)` before it creates the frame, and reads it back from `history.state` on a reload (not Web Storage, AD-20). The token cannot go back into the URL while the view lives: a probe showed that Chromium and WebKit fix the srcdoc's base URL when the frame loads, but Firefox reads the board page's current URL each time, so restoring `?t=` after the load put the token back into the view's `document.baseURI`. A `<base>` element is refused by both policies' `base-uri 'none'`. A reload requests the URL as it then is, so it reaches `/b/<askId>` without `t` (checked in the three engines, with the URL restored in `beforeunload`, `pagehide` or `unload` too: the reload had already taken the bare URL), and `history.state` survives the reload in all three.
- **Blocks:** the reload scenario of 8.6 (`board.browser.ts`, "a reload ...") fails in every engine against the test server, which answers a link without `t` with the invalid-link page as `BOARD_RESPONSES` says, and will against `board-host` (9.3). No workaround in Track B: keeping the token in the URL keeps it readable in the view in Firefox. Once the contract changes, the test server's `boardPage` in `packages/view/test/browser/harness/http.ts` answers the board page for the bare link of an open ask, and the test passes as written (the board page side is done).
