# Track B requests

Changes Track B needs in files it does not own (tasks.md, Parallel tracks). Each entry says what, why, the task it blocks, and how Track B works around it meanwhile.

## 1. One rule for the board page's CSP (task 8.3, not blocking): accepted

- **What:** a contract function, for example `boardPagePolicy(manifest: ViewManifest): string` beside `cspHashSource` in `packages/contract/src/hash.ts` or `routes.ts`, that builds the board page's policy from the manifest: `default-src 'none'`, `script-src` with the board page script's hash and every chunk script's, `style-src` with the board page's and every chunk's style hashes (`'none'` when there are none), `connect-src 'self'`, `img-src data: blob:`, `font-src data:`, and no `frame-src` in E1 (AD-8, design decision 5, board-host spec "The board page and its policy").
- **Why:** `board-host` (Track A, 6.3) computes this policy, and so does the view's test server (Track B, 8.3), which must answer as `board-host` does. Two copies of one rule can drift, in a directive or in whether `default-src 'none'` is there, and the browser tests would then pass against a policy the real session process does not send.
- **Blocks:** nothing. Workaround: the test server's own copy, `packages/view/test/browser/harness/policy.ts` (`boardPagePolicy`), unit-tested against the rule above; the harness check in `harness.browser.ts` compares the served policy with it by directives and sources, not by text, so 9.3 can run it against `board-host` whatever order that writes. If the contract gains the function, the test server uses it and its copy goes.
- **Outcome:** accepted. Track A added `boardPagePolicy(manifest)` to the contract (`packages/contract/src/hash.ts`). It has nine directives: the six above, and `base-uri 'none'`, `form-action 'none'` and `frame-ancestors 'none'`, which `board-host` already sent; the browser experiment showed those three safe in Chromium, Firefox and WebKit, both against the test server and against the real `board-host`. The harness copy matches it, except that its `base-uri` is `'self'`, as entry 2 asks of the contract. Integration switches the harness to the contract's function in group 9, and the copy goes.

## 2. `base-uri 'self'` in the board page's policy (task 8.6, not blocking Track B)

- **What:** in Track A's `boardPagePolicy` (`board-host`, 6.3), `base-uri 'none'` becomes `base-uri 'self'`; the other eight directives stay as they are. The spine does not fix the board page's `base-uri` (AD-8 lists `base-uri 'none'` for the view's own policy, which stays).
- **Why:** AD-8 says the view never holds a token, and the review of 8.1 to 8.5 (M1) found that it did: a srcdoc document takes its base URL from the board page's document base URL, which without a base element is the board page's URL, so `document.baseURI` inside the view held the link with `?t=` in Chromium, Firefox and WebKit (Firefox reads it again whenever the board page's URL changes). Since 8.6 the board page's HTML carries `<base href="/">` (`tools/build/board-page.ts`), so the view's base URL is the origin's root: no token on first load, after a reload, or after the board page's URL changes, checked in the three engines. The link keeps its token, so a reload works and every request carries one (AD-11); `base-uri 'self'` still refuses a base URL on another origin. With `base-uri 'none'` the browser refuses the base element and the view inherits the token again.
- **Blocks:** against the real `board-host` (9.3), the view-token test (`view.browser.ts`, "the view holds no part of the token ...", and the reload test's token check), and the board page raises a `base-uri` violation, until Track A changes the directive. Workaround: the test server's copy of the policy (`packages/view/test/browser/harness/policy.ts`) has `base-uri 'self'`; the harness check in `harness.browser.ts` compares the served policy with that copy, so it reports the difference too.
