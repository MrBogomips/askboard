## Goals / Non-Goals

**Goals:**

- A Document review is a registration: a contract folder, one registry line, a chunk, its teaching text; the annotation shape is settled for the later annotating widgets.
- A quote is placed by one rule, never by a guess; a quote that has lost its place blocks the answer until the user removes it.
- One Markdown renderer for every component that renders Markdown, loaded only by boards holding an item that may render it.

**Non-Goals:**

- Placing quotes in `ask-core` (open question 4), quotes of the Markdown source (open question 3), position selectors, re-attaching, overlaps, a pointer document (proposal, Not in this change).

## Decisions

### 1. The type and its props (open questions 1 and 2)

`packages/contract/src/widgets/document-review/` in the Chart's layout (`document-review-props.json`, `document-review-result.json`, `constants.ts`, plain `checks.ts` and `anchors.ts`, `wording.ts`, `widget.ts`, `index.ts`); type `document-review`, noun "a Document review", appended to `WIDGET_TYPES` after `pick-field`.

- `markdown`: 1 to `DOCUMENT_REVIEW_MAX_CHARS` (= `TEXT_MAX_CHARS`, 10,000, the renderer's bound) code points, refusing every character `agentTextRuns` would escape except line feed and tab; the problem names the first such character as its escape. One predicate decides it: notice-text's escape rule, exported in an appended block (`isEscapedCodePoint`), so the contract has one list of escaped characters.
- `title`: 1 to 120 code points, as the Chart's.
- Why refuse controls: the renderer shows them as six-character escapes, which a quote would then hold and the agent's source would not; a carriage return is normalised away by markdown-it. Refusing them keeps every character of a quote the agent's own, apart from Markdown marks.

*Alternatives:* `text` plus `format` as the Text has (open question 2); a pointer resolved at send time (open question 1).

### 2. The annotation body (open question 5; AD-7 amended in place)

`annotation.json`'s body becomes `{text?, replacement?}` with `minProperties: 1`: `text` as before, `replacement` 0 to `ANNOTATION_REPLACEMENT_MAX_CHARS` = 4,000 code points (beside `ANNOTATION_MAX_CHARS` in `lifecycle-limits.ts`). A suggested edit is an annotation whose body holds `replacement`, after the W3C model's editing motivation; an empty replacement deletes the target's text. Making `text` optional and adding a field is minor-compatible (askboard-contract-versioning). A later type that takes comments only requires `body.text` in its own result schema. The output format's constant moves in task 1.1.

*Alternatives:* a separate `edits` list beside the annotations (two shapes for one act); `body.text` as the replacement under a motivation field (no deletion, no note).

### 3. The result (open questions 7 and 10)

`{annotations}`: 1 to `DOCUMENT_REVIEW_ANNOTATIONS_MAX` = 100 items, each the annotation through `$ref` narrowed by `allOf` to a `quote` selector, no combinator at the root (the registry's empty-result rule). `shape` restates the schema in plain code; `problems(result, props)` adds: each ID starts with `VIEW_ID_PREFIX` and is unique (a `Set`, so `__proto__` is an ID like any other and refused for its missing prefix); `exact` holds a code point that is not white space and is no longer than the props' `markdown`; `exact`, `prefix` and `suffix` hold no character decision 1 refuses; a `replacement` differs from its `exact`. Problems name the item and `annotation "u-3"`. The registry checks the schema first and a type's `shape` and `problems` see only results it accepted (`widgetResultProblems`, `widgetResultFits`), so another selector fails at the annotation's selector, naming the item; `problems` never throws on any JSON value (review S-1, X-1). No `answerProblems`; no registry `fieldCheck` (form-widget's), since `ask-core` cannot place a quote.

### 4. Placing and quoting (open questions 3 and 10)

`anchors.ts`, plain ECMAScript with no regular expression over agent text:

- `quotePassage(text, start, end)`: the exact text and up to `QUOTE_CONTEXT_CHARS` = 32 code points of context on each side, widened to 64, 128 and `QUOTE_CONTEXT_MAX_CHARS` = 200 until the joined quote occurs once; a refusal `blank`, `too-long` (over 2,000 code points) or `repeated`. Offsets are UTF-16 indices of the text; boundaries never split a surrogate pair.
- `placeQuote(text, quote)`: the place of `prefix + exact + suffix` when it occurs exactly once (counting overlapping occurrences, and stopping at the second), else `missing` or `ambiguous`.
- `placeAnnotations(text, annotations)`: each annotation's place, or `detached` with its reason; of two whose places overlap, the later in the result is detached as `overlaps`.

`quotePassage` and `placeQuote` agree by construction: a test places every quote it makes, over generated texts.

### 5. The text a quote quotes, and who places it (open questions 3 and 4)

The **reading text** is the document as the user reads it: the concatenated text nodes of the sanitized fragment the shared renderer returns, in document order, or the source when the renderer shows plain text. One function in the widget gives it to the component and to the chunk's `check`, so the two never differ; it is kept per item, keyed by the item's props object (decision 7). Only the view can compute it: `ask-core` has no DOM (AD-1) and Markdown renders only in the view (AD-8). `ask-core` checks shapes, IDs and bounds (decision 3); a quote the text does not hold could reach it only in a board message forged with the board's token, which could as well pick any option, the reasoning of form-widget decision 3 for the TextField's pattern. The skill tells the agent to ask when it cannot find a quote, never to guess.

*Alternative:* markdown-it in `contract`, the reading text derived from its HTML in both layers: a renderer dependency in the session process and AD-8 amended, for a check a forged message could still pass.

### 6. The shared Markdown renderer (open question 12; AD-1 and AD-9 amended in place)

`packages/view/src/markdown/` takes `markdown.ts`, `links.ts` and `classes.ts` from `catalog/text/` with their tests, and an `index.ts` exporting what the Text and the Document review use. `view/package.json` exports `./markdown`. `LIBRARY_CHUNKS.markdown` provides `@askboard/view/markdown` (an exact list of names), and `BY_PATH` maps the file for the Text inside `view`, as the port is mapped; the build records the library among each importing chunk's needs, so `assemble` inlines it only for boards and Snapshots holding an item that may render Markdown: any Text (the `text` chunk imports the renderer statically, so a plain Text loads it too, as the `text` chunk carried it on `main`), an option with a Markdown preview, a Document review (review S-1 of 3.2 and 4.3: splitting the Text by format into two chunks would spare 146,989 bytes only to boards whose Texts are all plain, for a second chunk and a second registration; not worth it). `tools/check-imports.ts`: `widgets` may also import `view/markdown`. Licence notices follow the code into the library chunk, and `exceptedPackageProblems` still finds `argparse` in no chunk. The library chunk's stylesheet carries the Markdown element classes, so a Document review is styled as a Text is. `chunk-sizes.json` is re-recorded with the reason.

*Alternative:* the Document review as a catalog component in `view`, beside the atoms (open question 12): no import rule changes, but an FR-11 widget outside `widgets` against the Structural Seed, and still a library chunk to avoid two copies.

### 7. The component (`packages/widgets/src/document-review/`)

Pure modules over structural node interfaces, as `links.ts` is, so they run in Bun without a DOM:

- `reading.ts`: the reading text and the blocks (the innermost `p`, `h1`–`h6`, `li`, `pre`, `td`, `th` holding text) of a fragment; a selection's boundary points as reading-text offsets, skipping every element the widget adds, which carries `data-review-ui` (the sanitizer drops every data attribute of agent content, `ALLOW_DATA_ATTR: false`).
- `model.ts`: add, edit and delete annotations; the refusals (decision 4's, plus `outside`, `several-ranges`, `overlaps`, and `limit` once the item holds 100 annotations, since a 101st would make the result invalid: review S-3 of 5.6); the next view-made ID (`u-` and the lowest free number); the result, `undefined` with no annotation; `placesOf`, `placeAnnotations` memoized by the reading and the annotations' selectors (never their bodies), one memo shared by the component and `check`, so typing in a card never places again (review verdict 3); `check` (decision 8).
- **Per item, never by capacity** (review X-1 and U-1 of 5.6): the reading (text and fragment) is kept in a `WeakMap` keyed by the item's props object, and the places in a `WeakMap` keyed by that reading, each holding the last selectors' key and its places, as `form-widget` keeps its pattern outcomes. The shell passes the document's own props objects and the board page sends the view a document only when it differs from the last one sent, so a board of any number of Document reviews renders each source once and places each list once per selector change, and an update that replaces the document costs one render and one placement per item. A caller with only a source string (a test) keeps a small least-recently-used cache. *Proposed default accepted under the PO's unattended handoff (2026-11-08); alternative:* fixed caches sized past the most items a board holds, which no bound gives (a question's `items` has no `maxItems`).
- `marks.ts`: the mark plan for the placed annotations, applied to a fresh clone of the fragment when the places change: each text node segment of a passage wrapped in a `span` with fixed classes and `data-review-mark` (its text stays in the reading text), then, after the passage, an element with `data-review-ui` holding the pin's placeholder and, for a suggested edit, a text node holding the replacement (both left out of the reading text). That element never stands inside the agent's `a`: when a passage ends inside link text, it goes after the outermost `a` ancestor within the root, so a pin or a replacement never opens the link and the link's text and name stay the agent's (review X-1 of 6.5; decision 10). Typing in a card updates that text node in place; nothing re-applies while the places stay. Agent and user text reach the DOM only as text nodes; no `style` attribute, no `innerHTML`.
- `index.tsx`: the widget frame; the toolbar ("Comment", "Suggest edit", one Tab stop as the Ranking's); the counter; the document (one Tab stop apart from its links, decision 9); the shared pin rendered by React through `createPortal` into each placeholder; the shared comment card anchored to its pin; the shared annotation list under the document, holding the detached annotations; the selection refusal in a polite live region beside the toolbar. Ready after the first layout with marks applied.

The pin, the card and the list live in `packages/widgets/src/shared/annotations/` from the start, bundled into each chunk that imports them as the other `shared/` modules are, and name no widget type, so the Image annotation (its decision 9) and later annotating widgets import them unmoved:

- `pin.tsx`: a numbered button whose accessible name holds its number; where it stands is the caller's (a portal here, an overlay's button in the image).
- `card.tsx`: Radix `Popover`, non-modal, from the `radix` library chunk, anchored to the pin the caller gives, as the DateField's calendar; a header label from the caller ("Comment 2" here, "Pin 2" or "Box 3" in the image); the comment field; an optional suggested-edit field (the replacement, starting at the passage's text), given only by a caller that takes suggestions; "Done" and close, with optional "Edit" and "Delete", which a read-only card never shows; an optional `keepOpenOn(target)`, by which an interaction outside the card on a target the caller accepts (a toolbar tool that opens the next card itself) leaves it open, every other one closing it; it writes through the caller's callbacks as the user types and returns focus to the target the caller names.
- `list.tsx`: entries of a label, an excerpt and a text, each with an optional "Delete".
- Strings under one `annotations.` prefix of the view's tables, which a later type reuses; the Document review's own strings (toolbar, counter, refusals, hint) stay under its type's prefix.

Registered with `{fits: widgetResultFits over the contract's functions, name, revisionBound: true}` in task 6.3, and `check` in task 6.4, with the `detached` member it returns (review S-4 of 5.6): `fits` is structural, so a revision keeps the result and the component re-places it. The pin reaches its placeholder through `react-dom`'s `createPortal`, which the `react` library chunk already provides; task 6.1 moves `react-dom` from `widgets`' devDependencies to its dependencies, at `view`'s exact pin.

### 8. Detached annotations block the answer (open question 6)

The chunk registers form-widget's `ComponentFacts.check(result, props)`: the places of `result.annotations` in the reading of `props` (decision 7's per-item memo), giving `{code: "detached", count}` when any is detached. This change appends that member to `FieldCheckFailure` and its case to `fieldCheckMessage`; form's field block then stops "Answer", "Accept recommended", "Select recommended", Submit and the held mark, and `withEntries` marks a hidden tab (`kind: "check"`). The hint reads "Delete the detached comments in {label} first." with the `title` as the label, else "Delete the detached comments in the document first.": two strings, `documentReview.hint` and `documentReview.hintUntitled`, so that the Italian reads "nel documento" (review S-2 of 6.5). Detached annotations stay in the draft until the user deletes them (EXPERIENCE: never silently dropped or guessed).

*Alternatives:* "Attach to selection" (more UI, open question 6); dropping them through `fits` (the user's work lost whole, as a Chart's highlights are).

### 9. Cards and the keyboard (open question 9)

- **Cards write as the user types** (AD-9; the shared card of decision 7): a new comment becomes an annotation at its first non-blank character; emptying its text removes it while the card, holding the passage as view state, stays open. A suggestion is held while its replacement differs from the passage, with its note if one is written; while the replacement equals the passage, a written note is held as a comment `{text}`, marked as a comment and reopened as one, since the contract refuses a `replacement` equal to its `exact` (decision 3; review S-1 of 5.6). *Proposed default accepted under the PO's unattended handoff (2026-11-08); alternative:* the contract admits a `replacement` equal to its `exact` beside a `text`. "Done", Escape and the close control close the card; focus returns to the pin, or to the document when the pin is gone. EXPERIENCE's and DESIGN's Comment card rows say "Done" in place of a save action (`ux-update-draft.md`), which the Diagram and the Image annotation inherit.
- **Pointer**: the widget follows `selectionchange` and keeps the last selection inside the document as offsets; the toolbar's buttons prevent their `mousedown` default, so pressing one keeps the selection. A selection reaching outside the document is cut to it; several ranges (Firefox) are refused.
- **Keyboard** (EXPERIENCE, Accessibility Floor, block 3 of the draft): the document is one Tab stop, apart from the links it holds, each its own Tab stop after the current block as in a Markdown Text (review S-2 of 6.5); Up, Down, Home and End move the current block, which takes focus (`tabindex="-1"`, an outline class); Left and Right move between its pins; Enter opens the current pin's card. With no selection, the toolbar anchors the current block's text, trimmed of white space, through `quotePassage`, so a repeated or over-long block is refused with its message.

### 10. Links (AD-8)

The Document review mounts its fragment through the shared `mountMarkdown`, so a click on a link sends the open-link message on the board and opens natively in a Snapshot. Only the link itself opens it: `anchorHref` ignores a target inside `[data-review-ui]` (a pin, a replacement's text), and the marks keep those elements out of every `a` (decision 7), so the guard holds in both layers, on the board and in a Snapshot (review X-1 of 6.5; AD-8). `holdsMarkdown` holds also for a `document-review` item, found through layouts' walker at any depth; the URL check stays `isLinkUrl`, the one predicate of both layers.

### 15. Read-only on a revision the board cannot show

Coordinator decision of 2026-11-08 under the PO's unattended handoff, following the PO's answer to `image-annotation`'s open question 13 ("estendiamo la regola di sola lettura"). `keep-mine-shown-revision` (#66, on `main` since d6f5e453) makes read-only, while a card shows a revision other than the one its answer names (after a reload or a takeover, when the page never saw the revision the work was made on), each item whose chunk registers `ComponentFacts.shape` (`readOnlyItemsOf`, `shell/agent-change.ts:113`). A Document review registers no `shape` (it has no edits), yet its quotes point into the reading text of the revision they were made on: a comment made after the reload would quote revision 2's text while the answer names revision 1. This change closes the gap, as `image-annotation`'s decision 7 (3a82d722) designed it, and the Image annotation borrows what it adds:

- `ComponentFacts.revisionBound?: true`, appended after form-widget's `check` in `catalog/port.ts`: the item's result points into the agent's content of the revision it was made on. `readOnlyItemsOf`'s filter becomes `shape !== undefined || revisionBound === true`, at every depth as before. The Document review's chunk registers it (task 6.3).
- `itemCallbacks`' `onResultChange` writes nothing for an item in `readOnlyItems`, clearing included, and reports through `refuseWrite`, naming the item, as `onValueChange` does (keep-mine's decision 3 guards values only, since no result widget was read-only).
- The field block skips an item in the card's read-only set: its annotations were placed on the revision the answer names, which the page cannot show, so detachment from the shown text says nothing about them, and the user, who cannot delete them, would be left with a hint to do so. Every reader takes the set: the card's `blocked` and `answerHint` (`question-card.tsx:171`, `:207`), `blockedBy` (`card-acts.ts:242`), `heldWithBlock` (`submit.ts:175`) and `withEntries`' `failingIds` (`board-content.ts:142`, called at `renderer.tsx:195`). Items outside the set are checked as before (Open Questions).
- What the user sees: the comments and suggested edits held from before the reload stay shown read-only (drawn `disabled`, as on a closed ask or a locked board: no toolbar, cards without "Edit" or "Delete"; the keyboard still moves through blocks and pins), marked where their quote places once on the shown text, else listed as detached without actions, and sent as before, naming the kept revision; no comment or edit is added, changed or deleted; the line under it is keep-mine's `change.readOnlyAfterReload`; "Reload, losing my work" makes it editable on the current revision and the line goes. Without a reload the card keeps the kept revision's document and the item stays editable.
- **Every gate of an act reads the revision the card shows and the act names** (review S-1 of 6.5, H; Issue #92; proposed default accepted under the PO's unattended handoff, 2026-11-08). The card computes `shown = workingQuestion(question, work, revisions)` for its state, its hint and its reason prompt; the presses read the same question, never the current one: `blockedBy` (so `answer`, `acceptRecommended` and the card's `pressAnswer`), `heldWithBlock` (`submitStateOf`, `submitPress` and the confirmed press), `selectRecommended`, `withEntries`' `failingIds` for the items of the card's question (a hidden tab's mark), and the reason gate (`answerNeedsReason`, `heldMissingReason`), as the card's `reasonOf(shown, …)` does. They take it through `ShownOf` beside `ReadOnlyOf`: the card passes `() => shown` in `AnswerContext.shownOf`, and the board builds `shownOfBoard(board, revisions)` as it builds `readOnlyOfBoard`; with none given, the question itself. So after "Keep mine" with no reload the Document review's annotations are placed on the text they were made on: nothing detaches, and "Answer" sends them naming the kept revision. After a reload the page has not seen that revision, `workingQuestion` gives the current one, and the read-only rule above applies. Annotations detach, and block, only when held on a revision other than the one they were made on, while the card shows that revision: put back from an earlier answer after the agent changed the document ("Start from my previous answer", or the first edit of an answered question), or restored with such a draft. The mismatch is on `main` since `form-widget`, whose presses read the current revision (a TextField's check changes only when the agent changes its constraints, so its flows never showed it); this change fixes it for every field check, states it as the view-and-widgets requirement "The answer gates read the revision the card shows" (added beside form-widget's "A field check blocks Answer", which stays as it is), and its pull request closes #92. `ask-core` checks an answer's fields against the revision the answer names, so what the card shows as ready is what it accepts (task 6.6 records the line). The content of the act follows the same rule: `answer` and Submit's `actOf` build the values and results they send, and the recommended options "Select recommended" picks, from the shown question (an entry still blocks the act and never travels with it), and the confirmation before replacing a received answer is asked by the shown question's items (re-review 6.9 S-1 to S-3), so after "Keep mine" the work held on an item a later revision removed is sent with the answer that names the kept revision, as the card shows it, instead of being dropped (task 6.6's probe, Issue #93, H; proposed default accepted under the PO's unattended handoff, 2026-11-08). Its pull request closes #93 too.
- Why a fact: the shell imports no registry, so the predicate reads only what chunks register; `shape` means "gives edits", which the Document review does not; "every result widget" would lock a Scale's value or a TextField's text, which mean the same on any revision. No schema set moves.

*Alternatives:* a known limit (comments on the new text sent naming the old revision; NFR-10 does not admit it); revision 1's reading text kept in the draft record (a board protocol field for a case the agent-change notice already shows). ## Risks / Trade-offs

- [Selection differs across engines in the sandboxed frame, or the shell sets `user-select: none` around items] → task 0.4 probed selection, `selectionchange`, `mousedown` on the toolbar and the portal-anchored popover in Chromium and WebKit, and task 6.1's browser file makes the Firefox checks (several ranges, focus return from the popover, `selectionchange` in the sandboxed frame); offsets come from the widget's own walk, never from `Selection.toString()`.
- [The component and the check disagree on the reading text] → one cached function; a browser test reloads and compares places.
- [The agent cannot find a quote in its Markdown (marks, entities or a link inside the passage)] → `prefix` and `suffix` locate it; the teaching text says to ask rather than guess; CHANGELOG Known limits says so.
- [A block over 2,000 characters cannot be commented on from the keyboard] → the message asks for a pointer selection; Known limits.
- [Placing quotes is slow on a crafted repetitive document: 100 near-miss quotes over one repeated character took about 200 to 420 ms in Bun (task 1.4)] → the cost stays on the user's own board (`ask-core` places nothing); each search stops at its second occurrence, and `placesOf` places again only when an item's reading or a selector changes, per item with no capacity below the number of items (tasks 5.2 and 5.8 assert it, 5.8 with 32 items; review X-1 and U-1 of 5.6: past the former 8 readings and 16 placements, every keystroke rendered and placed every review again); task 6.4 times it once in Chromium, and both figures go to CHANGELOG Known limits (task 8.1; PO rule of 2026-11-07).
- [Two Document reviews filled to every bound pass `DRAFT_RECORD_MAX_CHARS` and the act `MESSAGE_MAX_BYTES` (review U-1, measured in task 3.1: draft 3,384,911 characters against 2,000,000, act 6,744,897 bytes against 6,004,096)] → `board-host` refuses both whole, nothing kept, logged or published (NFR-10, tested in 3.1). The board page did not (review X-1 of 3.2 and 4.3, pre-existing on `main`, reachable with about 160 TextFields): it refused the draft on the console only, and resent the act after every 1009 close, so later answers never arrived. `oversized-acts` (#88, Merge points) fixed it on `main`: the card says the answer is too large, nothing is resent, and the draft is mirrored without whole questions. This change moves no bound, names the limit in Known limits (task 8.1) and proves it with two filled reviews after the rebase (task 8.2).
- [A quote placed inside a surrogate pair, from a forged result or a document holding a lone surrogate (review U-2)] → task 5.3 checks the marks never split a pair; if `placeQuote` gives such a place, it treats it as missing.
- [The marks breach the sanitizer's guarantees] → only fixed classes and `data-review-ui` on the widget's own elements; a test walks a marked container and finds no other attribute outside DOMPurify's allow-list; security checkpoints at tasks 5.6 and 6.5.
- [The shared annotation change binds later widgets] → the body's members are optional; a type narrows them in its own result schema (decision 2); the shared card takes the suggested-edit field only when given one (decision 7).
- [`layouts`' or `form-widget`'s seams merge with other names or shapes] → task 0.2 stops for `/opsx:update`.
- [After a reload or a takeover under kept work, a comment made on the new text would be sent naming the old revision] → read-only through `revisionBound` (decision 15), unit-tested in task 5.5 and in the session in task 7.1.
- [The field block's read-only skip sends an annotation that was already detached on the kept revision, left in the draft across a reload] → the user made it, and the answer names the revision it was kept on; the skill tells the agent to ask when it cannot find a quote; CHANGELOG Known limits (task 8.1).
- [`withEntries` still marks a hidden tab for an entry of an item in the read-only set, while the field block skips it (review U-2 of 5.6)] → no shipped type is both `revisionBound` and an entry type, so nothing shows; a follow-up for the first such type, which filters the entries by the read-only set too.
- [A result widget whose result points into the agent's content forgets `revisionBound`] → `component-facts.test.ts` lists the types that register it (task 6.3); each later design states its choice.
- [A gate that reads another revision than the card, so a press refuses what the card shows as ready, without a word (review S-1 of 6.5, #92)] → decision 15's gates through `ShownOf`; task 6.6's unit cases make each press agree with `holdsBlock` and `answerHint` on the shown revision both ways, with mutants for each reader, and task 7.1 proves it in the session.
- [The act's content, built from the current revision's items (`answerContentOf(question, …)` in `answer` and Submit's `actOf`), may differ from the card's (`answerContentOf(shown, …)`) after "Keep mine" when the agent's update removed an item holding the user's work] → outside review 6.5's finding and unconfirmed: task 6.6 probes it without changing it; if confirmed, it becomes its own Issue (`source:review`).
- [A pin or a suggested replacement inside the agent's link opens it (review X-1 of 6.5)] → decisions 7 and 10: the element after a passage stands outside every `a`, and `anchorHref` ignores `[data-review-ui]` targets; task 6.7 tests both layers, and 7.2 a Snapshot.
