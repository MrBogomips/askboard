## Goals / Non-Goals

**Goals:** one source for every key a widget takes; a vocabulary checked across widgets, the PO's approved keys included; the Ranking at the full standard as the pattern the retrofits copy; `askboard-help` right from the first day for every widget, from tables tested against today's handlers; the user's own keys for any action, from the user file, wherever the board shows a Keys button (D1 to D5).

**Non-Goals:** behaviour changes to widgets other than the Ranking, beyond the modifier fix (decision 7); binding the approved keys outside the Ranking (the retrofits do it); board-wide shortcuts; changing keys from the board (a Settings section, key capture), presets, keys per widget and key sequences (D3, D4; the second input's section 9); a formal WCAG target (NFR-12 stands).

## Decisions

### 1. The tables live in the registry, in `contract`

Each widget type's registry entry gains an optional `keys` (its key table) beside `skill`, built from a shared vocabulary in `packages/contract/src/keys/`. The registry is what the generator, the registry check and every chunk already read: the generator gets the tables without a new export, the rule "the same keys for the same action in every widget" is one check over the registry (`widgetRegistryProblems`), and each chunk registers its type's table with the shell as `ComponentFacts.keys`, as it registers `fits` and `check`, so the shell still imports no registry. Tables are plain data, no DOM (AD-1).

*Alternatives:* each widget's own `keys.ts` with a pure `@askboard/widgets/keys` export the generator reads (the input's section 12 assumed it; the cross-widget rule would then live only in tests); `view`.

### 2. The vocabulary and the table's shape

An entry is `{action, part, keys, label, shows, readOnly, when?}`:

- `action`: a vocabulary ID, or the type's own `<type>.<name>`.
- `part`: the part of the widget the keys act in (`list`, `grid`, `editor`, `toolbar`, `edge`, `zoom`, `panel`; a type may name others).
- `keys`: bindings `{key, hold}`. `key` is a UI Events `key` value, a letter in lower case. `hold` is `none`, `shift`, `alt+shift`, `mod` (exactly one of Ctrl and Cmd), `mod+shift`, or `char` (a printed character, Shift as the layout needs it, no Ctrl, Alt or Cmd). No other hold can be written in a table, so Alt alone, Ctrl with Alt, and AltGr combinations stay the browser's; only the user's overrides may write `mod+alt`, on five keys (decision 17).
- `label`: the view string key of the action's name. A view test checks each label is in `STRING_KEYS`.
- `shows`: the visible counterpart, for the two-way test (input section 6) and nothing else: `tool`, `menu`, `pointer` (a click, Shift+click or drag the spec names), `navigation` or `panel` (both exempt). An entry may be `native`: keys a Radix or browser control takes by its documentation, listed and taught but not matched by AskBoard's handler (the Gantt's switch).
- `readOnly`: whether the keys still act while the item takes no edits (answered, locked, read-only, a Snapshot), as its component does today; the keys panel's read-only filter reads it (decision 5), never `shows` (review 1.6, S-3). `vocabularyEntry` defaults it to true for `cursor.*`, `toolbar.*` and `keys.open` and to false for the rest, and an entry overrides the default where its part says otherwise (the cursor keys of the Gantt's predecessors panel, which opens only on an item that takes edits); an own entry states it. A toolbar's navigation keys act on an item that takes no edits exactly when the toolbar keeps a Tab stop there (`toolbarStop`, `widgets/src/shared/toolbar-focus.ts:48`, gives none when every stop is off). A toolbar whose every tool is off and that has no Keys button gives its `toolbar.*` entries `readOnly: false`, overriding the default with a comment citing `toolbarStop` (review 1.12, S-7): the Kanban's and the Timeline's in this change, which have no Keys button yet; the lists retrofit, which gives them one, returns them to the default (decision 14). A toolbar with a Keys button keeps the default `true`: the button is always on, so it holds the Tab stop, and on a crowded toolbar the arrow keys move between it and "More", also always on (review 4.6, S-48: the Ranking's since task 4.4, set back by task 4.7). The Tree's toolbar keeps `true`, its "Select all" staying on. The Gantt's column edge is `readOnly` (it is rendered and resizes on every Gantt, `gantt/frame.tsx:248`); editors, the Gantt's predecessors panel and the Tree's two questions are not.
- `when`: `selected` for keys that act only while the widget holds a selection; otherwise the key goes on with its default.

The vocabulary (`KEY_VOCABULARY`), from the Tree (input section 4) and question 1, approved by the PO on 2026-11-09:

"Outside text fields" is the matcher's rule for every part but `editor` (decision 3). An action outside the vocabulary is the type's own, with keys the PO approves (decision 15's rule), as `ranking.keep`'s Enter (question 1).

`keyTableProblems(type, table)` refuses, naming the type and the action or key: a vocabulary action whose keys differ from the vocabulary's, by a key added or one left out, except `delete` (below); one binding twice in one part; Tab or Shift+Tab; `mod` with any key but `z` and `a`; `mod+shift` with any key but ↑, ↓ and Enter; `char` with any character but `?` and `%`; `alt+shift` with a key that types a character, a key of one code point that is no control character: a letter of any script, a digit, punctuation, a symbol or Space (review 8.6, S-25, and review 8.13, S-41: on macOS Option+Shift with such a key reports the composed character as `event.key`, so the binding would never match, and on some Linux desktops Alt+Shift switches the keyboard layout); F1 and F3 to F12; in an `editor` part, a key that types a character with no modifier or Shift alone, and any `char` (review 8.6: an editor's entries match inside its text field, so such a key would act while the user types); an empty label; a keyless entry whose `shows` is not `tool` or `menu`, or whose action is a vocabulary action (decision 6); a `readOnly` that is not a boolean, or true on an action that changes the answer (`move.*`, `add.*`, `delete`, `edit.*`, `undo`, `adjust.percent`). `widgetRegistryProblems` runs it for each entry.

`delete` takes one of three forms (review 1.6, S-4; `keys/check.ts`): the plain pair alone, Delete and Backspace (the Tree today, which decision 9 requires); both pairs, plain and with Alt+Shift; or the Alt+Shift pair alone, where another action of the same part takes the plain pair (the Table's cells, which Delete clears). Half a pair is a key left out, and any other key on `delete` is a key added.

*Alternative:* a key table per widget with free keys and a cross-widget test; it cannot refuse an action under two keys until the test is written for that pair.

### 3. One matcher, one press reader

`keyActionOf(table, part, press, selected)` in `contract` (pure, from the Tree's `holdOf` and `keyAction`): the entry whose binding matches the press's key and hold, else undefined. A press while an input method composes matches nothing; a press on a text field matches only an `editor` entry, so `?`, `%`, Cmd/Ctrl+A, Escape's `select.none` and Alt+Shift with an arrow stay the field's; a `when: selected` binding matches only while `selected`. `keyPressOf(event)` in the port reads a React or DOM event into the press `{key, hold, composing, inText}`, with the Tree's rule that `keyCode` 229 counts as composing (`tree/key-event.ts`) and `isTextTarget(target)` for `inText` (an `input` that takes text, a `textarea`, `contenteditable`, `role="textbox"`). A handler maps the entry's action through a typed record from the table's action union to a function, so an action without a handler fails the type check. A key the table binds has its default prevented also where it cannot act (Alt+Shift+↑ on the first row), as the Tree does, except a `when: selected` key with nothing selected; any other key never is, but a key decision 9 names as taken only to stop a browser action.

One reader (review 2.6, S-11): the port's `keyPressOf`. Group 2 added `pressOfEvent` (`widgets/src/shared/key-press.ts`) before the port's reader existed; task 2.10 moves its six callers to the port's `keyPressOf` and deletes it. The port's reader takes `isComposing` from the event itself or from its `nativeEvent`, so a raw DOM `KeyboardEvent` that composes counts, not only `keyCode` 229. The Tree's `treeKeyOf` and the Gantt's `keyPressOf` (`gantt/key-press.ts`), on main before this change, give their own press shapes to their own key functions; each goes when its retrofit moves those functions onto `keyActionOf` (decision 14).

A bound key that cannot act is still taken (review 2.6): today the Kanban's and the Timeline's cursor keys at the first or the last card or entry keep their default, so the view scrolls. Their handlers are not on the matcher here (decision 9), and their parity tests check the action, not the prevent; `keyboard-retrofit-lists` prevents those keys when it moves both onto `keyActionOf` (decision 14).

### 4. Labels and `aria-keyshortcuts`

`ariaKeyShortcuts(keys)` (contract, pure) writes WAI-ARIA 1.2's form: `Alt+Shift+ArrowUp`; `mod` and `mod+shift` as both `Control+…` and `Meta+…`, space-separated, as the Tree's undo does; `char` as the character alone (`%`, `?`), never `Shift+5` or `Shift+%` (review 1.6, S-5). WAI-ARIA 1.2 calls `Shift+5` the correct form on a layout where Shift types `%`, and admits the bare printable character where it is unmodified; the board matches the character and never knows the layout (`?` is Shift+/ on a US layout and Shift+' on an Italian one), so a modifier written there would be right on one layout only, and the character alone is the one form true wherever the character arrives. `keyLabel(binding, platform, say)` (port) writes what the user reads, by platform (question 6): macOS `⌃⌥⇧⌘` in that order then the key, with ↩ ⌫ ⌦; elsewhere `Ctrl+Alt+Shift+Key` with the key's name; arrows ↑ ↓ ← → everywhere; names from the strings (`key.*`, Italian provisional). `useKeyPlatform()` reads `navigator.userAgent` once (`Macintosh` or `Mac OS X`), and tests pass the platform in. The generator writes the Linux form with the macOS form beside it, in English.

### 5. Contextual help: hint, button, panel

- `KeyHint` (port) wraps a control in a Radix Tooltip, opened on hover and on keyboard focus and closed by Escape, showing the action's name and its keys as key caps, and puts `aria-keyshortcuts` on the control from the table. Radix Tooltip joins the `radix` library chunk (`LIBRARY_CHUNKS.radix`); its provider sits in the shell. The look is DESIGN's tooltip for agent-written labels (`{colors.popover}`, `{elevation.shadow-md}`, `{typography.body}`); a key cap is `{typography.code}` on `{colors.muted}` with a 1px `{colors.border}` and the small radius.
- `MenuKeys` (port, beside `KeyHint`; review 4.6, S-49): an item of a menu (the Ranking's "More") gets no tooltip, which a menu's own focus and pointer handling would fight; it shows its action's keys in effect as key caps at the item's end, the usual menu convention, after the name and aligned right. The caps are `aria-hidden`, since the item's `aria-keyshortcuts`, from the same entry in effect, announces them; a keyless entry and an action the user's file removed show none. The key cap's look is `KeyHint`'s, one class shared by both.
- `KeysButton` (port): a `button-secondary` "Keys", `aria-haspopup="dialog"`, its tooltip "Keys" with `keys.open`'s keys in effect (`?` by default; decision 19) and its `aria-keyshortcuts` from them; the last stop of the toolbar row and never in "More", or beside the counter where a widget has no toolbar (question 7). It opens the frame's panel through `useKeysPanel()`.
- The keys panel (shell) lives in the item frame for a type whose facts hold `keys`: `KeysFrame` (`shell/keys-frame.tsx`), a Radix Popover holding `KeysPanelBody` (`shell/keys-panel.tsx`), which the Keys button reaches through `KeysPanelContext` and `useKeysPanel()` (port); no component is named `KeysPanel` (review 8.6, S-30). `ItemFrame` (`shell/renderer.tsx`), which takes `itemId`, `tracker` and `children` today, gains the type's facts and whether the item takes edits, from `RenderItem`'s `disabled` and `readOnlyItems` (an item read-only while its card shows another revision, since `document-review`). The panel is a Radix Popover, non-modal, anchored to the Keys button, `role="dialog"`, named "<Widget> keys" from the type's string name (`ComponentFacts.name`), focus moving into it; it lists each entry that has keys, with its name and key caps, by group, the group following the action's family (cursor, selection, move, edit, other); a keyless entry (decision 6) is not listed, nor does it get a `KeyHint` or `aria-keyshortcuts`. An item that takes no edits (answered, locked, read-only, Snapshot) lists only its `readOnly` entries (decision 2). Escape or "Close" closes it and returns the focus to the element that held it before it opened; a close because the user clicked or moved the focus elsewhere leaves the focus where the user put it (review 3.6, S-16): Radix calls `onCloseAutoFocus` on every close, so the frame records why it closes (Escape and "Close" against an interaction outside) and prevents Radix's own focus move in every case, giving the focus back only after Escape or "Close". The frame opens it on `keys.open`'s keys in effect (`?` unless the user's file changes them, decision 19; with `[]` no key opens it, and the Keys button still does) when the key was not prevented, no input method composes and the target is not a text field; the nearest frame wins, so a Ranking in a Group opens its own panel. Only board strings and the table reach it; no agent text (AD-8).

### 6. The approved keys, and the types without a table

The PO approved question 1's keys on 2026-11-09; they join `KEY_VOCABULARY` in group 1 (decision 2). This change binds two of them, in the Ranking: Enter on the list for its own `ranking.keep`, and the vocabulary's `select.none` (decision 8). The Tree's and the Table's bindings come with the retrofits (decision 14). No entry waits for the PO.

Keyless entries, one rule for every table (review 1.6): a table binds only keys that act, and lists every tool and menu of the widget's toolbar that acts on its content or its selection, keyless where no key takes it, so that the two-way test ("Every visible action in the table") holds in both directions for every table. A keyless entry is an own action `<type>.<name>` with `shows: tool` or `menu`, since a vocabulary action keeps the vocabulary's keys; the retrofit that binds its keys replaces it with the vocabulary's entry. View controls (the Gantt's zoom options and its switch) appear only through their keys. So the Kanban keeps `kanban.moveTo`; the Tree gains `tree.addAfter`, `tree.addChild`, `tree.selectAll`, `tree.selectNone` and `tree.adjust`, and the Timeline `timeline.moveEarlier` and `timeline.moveLater` (`tool`) and `timeline.moveToLane` (`menu`), each labelled with the tool's existing string key. Keyless entries reach no tooltip, `aria-keyshortcuts`, keys panel or Keys section (decisions 5 and 10).

`packages/contract/test/keys-coverage.test.ts` lists every shipped type without a key table, with its reason: `standard` (only keys the browser or an adopted library documents, Radix's controls and react-day-picker's calendar among them, or the WAI-ARIA radio group defines, which `askboard-help`'s concepts teach; so the DateField, whose calendar's keys are react-day-picker's (correction 6), is `standard`, and the grids retrofit adds its requirement and browser test, not a table), `none` (no keys of its own), or the retrofit that adds its table (`keyboard-retrofit-grids` for the LaTeX, the Table and the Document review, corrections 7 and 9). It fails, naming the type, on a type with neither a table nor a line, as `tools/nested-items.test.ts` does for direct reads, so a widget that merges after this change declares its table or why it has none.

### 7. The modifier fix

The Kanban, the Timeline and the Chart act only on a key held with no modifier (the Chart's Space and Enter included), and their handlers prevent the default of no other key; the Ranking's list takes the holds its table names (decision 8). The Gantt's column edge and its "Critical path" switch take exactly the holds their table names (review 1.6, S-1): today the edge returns only on Alt, Ctrl or Cmd (`gantt/column-edge.tsx:42`), so Shift+Enter fits the column and Shift+Home and Shift+End act, and the switch ignores Shift (`gantt/chrome.tsx:45`), so Shift+← and Shift+Home move the focus to the zoom; after the fix the edge takes Shift only with ← and →, and the switch its ← and Home with no modifier, and every other press keeps its default. The Gantt's table stays as it is. `toolbarMoveOf(key)` stays as it is, since the Table's toolbar calls it behind its own modifier check; a new `toolbarPressMove(press)` beside it adds the hold check, and the Ranking's toolbar, `MoveToolbar` (the Kanban's and the Timeline's) and the Document review's `toolbarKeys` switch to it. AskBoard's radio group (`radioAt`) and the multiple choice's key handler take the arrows, Home and End with no modifier only (correction 8). If `kanban-order` merges first, its `kanbanPressOf` already takes only its bindings, and the Kanban's handler needs nothing here (Merge points). Radix's own keys (the Scale's slider, which its unset stand-in mirrors; Toggle Groups; Tabs) stay as Radix documents them. These are the only behaviour changes outside the Ranking (input section 2, anti-goal 2).

### 8. The Ranking, to the standard

- Model, pure, in `widgets/src/ranking/`: `selection.ts` (toggle, extend from the anchor by key, range by Shift+click, filter to the order's IDs after an agent's revision; review 4.6, S-51, the Tree's rule: Space on the current row and a click on a check box toggle that row and make it the anchor; Shift with ArrowUp or ArrowDown, and Shift+click, add every row from the anchor to the target and keep the anchor, so a range only grows, and Shift+ArrowUp after Shift+ArrowDown moves the current row back and deselects nothing; with no anchor, Shift with an arrow starts from the current row and Shift+click from the clicked row, which becomes the anchor; "Select none" and Escape clear the anchor with the selection) and `moves.ts` (each move for a selection or a single row, question 2's rule, and whether it moves anything, for the tools' enabled state). `model.ts` keeps the drop, the counter and the order's checks; its `moveBy`, which only the earlier single-row tools called, goes (review 4.6, S-54).
- `RANKING_KEYS` in `contract/src/widgets/ranking/keys.ts`, in the registry entry. ### 16. The user's keys: scope and trust (D1, D3 to D5)

- The user replaces or removes the keys of an action, a vocabulary action or a type's own (D5), and the change holds in every widget that has it, so one action keeps one set of keys everywhere. An override is a list of combinations that replaces the action's keys; `[]` removes them, and the action's tool, menu or click stays. No keys per widget, no sequences, no presets (D4).
- Where: only the user configuration file (AD-14), key `keys`, beside the file's `version`: `"keys": {"move.top": ["Mod+Alt+ArrowUp"], "select.all": []}`. A project file's `keys` is ignored with a warning, as `editor` is: an agent can write that file, and agent content never chooses what a key does (NFR-5, AD-8). The ask carries no keys; the input format is unchanged.
- How: by editing the file (D3). The board has no Keys section in Settings, no key capture and no write path: `setting` still admits only `theme`, `density` and `contextPlacement`, and `PRESENTATION_KEYS` is unchanged. `askboard-help` guides the user (decision 20).
- Trust: the user file's `keys` applies as its `theme` does. `editor`'s rule for a user file others can write does not apply: a key runs no command, and each table action is one the user can also take with a tool, a menu or a click; none sends an answer, Answer and Submit being the frame's, outside every table (confirmed at review 9.4; decision 19).

### 17. The notation and Mod+Alt (D2)

- A combination is its modifiers, each at most once and in any order, from `Mod`, `Alt` and `Shift`, joined by `+` to its key: a `KeyboardEvent.key` name (`ArrowUp`, `Home`, `Enter`, `Delete`, `Escape`, `F2`), a letter, read as lower case, `Space` for the space bar, or `?` or `%` alone (the `char` hold). At most 32 characters. `parseKeyCombination(text)` (contract, pure) gives the binding or why not; `keyCombinationText(binding)` writes it back for the problems and the help skill.
- `Mod` is the `mod` hold: Cmd or Ctrl on every platform, as the default tables take it, written ⌘ on macOS and Ctrl elsewhere, so one file serves both. No `Ctrl`, `Cmd` or `Meta` name exists.
- `Mod+Alt` is a new hold, `mod+alt`, admitted in overrides only; `keyTableProblems` refuses it in a registry table. It is exactly one of Ctrl and Cmd, with Alt and no Shift: Cmd+Option or Ctrl+Option on macOS (D2's Ctrl+Alt), Ctrl+Alt elsewhere. It takes only ↑, ↓, Home, End and Enter: ⌘⌥← and ⌘⌥→ switch tabs in Chrome on macOS, Ctrl+Alt with Delete or Backspace belongs to Linux desktops, and Ctrl+Alt with a printed character is AltGr's on some layouts. `pressHold` reads it, `ariaKeyShortcuts` writes `Control+Alt+ArrowUp Meta+Alt+ArrowUp`, `keyLabel` ⌥⌘↑ on macOS and Ctrl+Alt+↑ elsewhere. Task 0.8 probes the browsers; what the system takes first (VoiceOver's Ctrl+Option, workspace switches) is the PO's live check (task 7.5).

### 18. The effective table and the overrides check

- `effectiveKeys(table, overrides)` (contract, pure, total): the table with each entry's keys replaced by its action's override, parsed; `[]` empties them; part, label, `shows`, `readOnly` and `when` unchanged. A `native` entry, an action the table lacks, and an override any of whose combinations does not parse change nothing, so an action is never half-replaced. Lookups are own-property only; the input is untouched and the result frozen.
- `keyOverridesProblems(overrides, types = REGISTERED_KEY_TABLES)` (contract, pure): every problem, each `{rule, action, binding?, with?}`:
  - `action`: neither a vocabulary action nor an own action some registered table binds with keys (`__proto__`, a misspelling, a keyless tool's own action). A vocabulary action no table binds yet passes and acts once a widget binds it;
  - `native`: the action's entries are all `native`, whose keys a Radix control takes;
  - `notation`: a combination does not parse;
  - `hold` and `reserved`: decision 2's refusals per binding (Tab, F1 and F3 to F12, `mod` but with `z` and `a`, `mod+shift` but with ↑, ↓ and Enter, `char` but `?` and `%`, `alt+shift` with a key that types a character, of which the notation can write only a letter or Space), plus decision 17's `mod+alt` keys; and, for an action that any registered table has in an `editor` part, a key that types a character (decision 2's editor rule: `"edit.commit": ["e"]` is refused);
  - `conflict`: after the overrides, two actions of one part of a registered table share a binding, a `char` against the same plain key included, naming both (`with`). `keys.open` acts across the whole item (the frame's handler, decision 5), not in one part, so its keys in effect are checked against every keyed binding of every part of every registered table, each pair reported once, from the overridden action (review 8.6, the reviewer's unconfirmed point);
  - `reserved` for `keys.open` also: Enter, Space, Escape, the arrows, Home, End, PageUp, PageDown, Delete and Backspace with no modifier or Shift alone, which native controls (buttons, check boxes, Radix's toggle groups, sliders and menus) take inside an item: the frame acts on a key no part prevented, so `keys.open: ["Enter"]` would open the panel from a focused button instead of pressing it;
  - `exit`: an exit left with no key: `edit.cancel`, and each own action whose default keys hold Escape (the Tree's two questions' cancels), `select.none` apart.
- It applies `keyTableProblems`' per-binding and per-part rules to each effective table; the rule that a vocabulary action keeps the vocabulary's keys, `delete`'s forms and the keyless-entry rule do not apply, since replacing and removing keys is the point. It reads every registered table, not only those on the board, so a file valid today stays valid when a retrofit puts another widget on the effective table.
- The default tables (review 10.5, S-43): `REGISTERED_KEY_TABLES` (`contract/src/keys/tables.ts`), the frozen list of `{type, keys}` for each registered type that has a key table, in the registry's order, built from the `widgets/<type>/keys.ts` modules, which import only `keys/vocabulary.ts`. `keyOverridesProblems` and `keyExitActions` default to it, so `ask-core` and the board page, which pass no tables, run the same function on the same tables without loading the registry; their `types` parameter takes any list of `{type, keys?}`, so `WIDGET_TYPES` and a probe registry still pass (the generator, the tests). A contract test derives the expected list from `WIDGET_TYPES` and checks it both ways: every registered type with `keys` is in it with the same table object, and nothing else.
- One exception to decision 2's "one binding twice in one part" (review 8.6, S-26): a combination written twice in one override, or two spellings of one binding (`Shift+Mod+z` and `Mod+Shift+z`), counts once. `effectiveKeys` keeps the first (`bindingsOf`, `keys/effective.ts`) and the conflict rule skips the action against itself (`conflicts`, `keys/overrides.ts`): a repeat is a harmless slip in a hand-written file, not a second action on the key, so it is no problem and voids nothing.
- All or nothing (NFR-10; AD-14, never half-applied): any problem drops the whole `keys`, and every widget keeps its default keys. The configuration schema bounds only the shape of `keys` (at most 64 actions, names of at most 64 characters, at most 4 combinations each); a `keys` of another shape voids the file, as any schema failure does (AD-14), and its meaning is this check's, as `snapshotFolder`'s is `ask-core`'s. The contract exports those bounds as plain numbers (`KEY_OVERRIDES_MAX_ACTIONS`, `KEY_ACTION_MAX_CHARS`, `KEY_OVERRIDE_MAX_COMBINATIONS`, beside `KEY_COMBINATION_MAX_CHARS` in `keys/notation.ts`), a contract test ties them to `config.json`, and the view's `UPDATE_FIELDS.keys` check reads them, so a later widening of the schema cannot make the board page drop whole updates (review 10.5, S-44).
