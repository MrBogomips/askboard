## Goals / Non-Goals

**Goals:**

- A Gantt and a Gantt plan that meet FR-11's Gantt row, FR-12's Gantt consequences and FR-15's Gantt plan scope on the board, every date and the critical path from `compute`, edited from the draft record alone and sent only by "Answer".
- The seams the follow-ups extend are real: the Gantt's schemas, its two shapes for the one generic diff, the board's graph source in `compute`, what the plan's expansion gives, the derived values in the view's answer.
- Every behaviour the specs name is tested: pure logic under `bun test` at 80% per file, the rest in three browser engines.

**Non-Goals:**

- Anything proposal.md lists under "Not in this change", the `tree-widget` seams first.
- Touching `packages/core` or `server`, E1's or the Tree's schema files, constants, fixtures, diff and widget validator, or `docs/`.
- Screen-reader announcements and reduced motion (EXPERIENCE open item 22); text on the chart for screen readers beyond its label: the grid carries the data.

Tasks 2.2 and 2.3 need `widgetValidator` and the keyed `ElementShape`, and wait for task 1.2.

Two merge points change code: the board content is read from E3's `questionsOf` and follows each agent update (decision 7), and `derived` sits on E3's answer checks and send path (decision 10). ### 2. The Gantt's contract: two shapes of `tasks`, standalone schemas, the shared validator

`packages/contract/src/widgets/gantt/` holds:

- `gantt-props.json` (`urn:askboard:input:gantt-props`): `start` (`$defs/fullDate`: the `YYYY-MM-DD` pattern), `workPackages` (E1's ID schema) and `tasks`, an `anyOf` inside the property of `$defs/ownTasks`, at most 500 of `{id, label, duration, start, dependencies}` (`id` E1's ID schema, `label` 1 to 200 characters, `duration` an integer from 1 to 2,000, `start` a `fullDate`, `dependencies` a unique array of at most 50 IDs; `id`, `label` and `duration` required), and `$defs/planTasks`, an object of at most 500 entries whose `propertyNames` are E1's ID schema and whose values are `{start, dependencies}`; `additionalProperties: false` everywhere; `required: ["start", "tasks"]`. "A list without `workPackages`, a map with it" sits in the checks, since a conditional schema would be a root combinator.
- `gantt-changes.json` (`urn:askboard:output:gantt-changes`): an array of `{op: "set", target, value}`, `target` `<id>.<id>.(duration|start|dependencies)`, `value` an `anyOf` inside the property of an integer, a `fullDate`, `null` or a unique array of IDs.
- `index.ts`: the types (`GanttOwnTask`, `GanttPlanEntry`, `GanttProps`, `GanttItem` `{type: "gantt", id, props}`, `GanttChange`), the limits (`GANTT_MAX_TASKS` 500, `GANTT_MAX_PREDECESSORS` 50, `GANTT_MAX_DEPENDENTS` 50, `GANTT_MIN_DURATION` 1, `GANTT_MAX_DURATION` 2,000, `GANTT_LABEL_MAX_CHARS` 200, `GANTT_FIRST_DATE` `1900-03-02`, `GANTT_LAST_DATE` `9999-12-31`: `compute`'s `firstDay` formula, `WORKDAY([p.start]-1,1)`, reads the day before the start, and the graph holds no day before 1900-03-01), `GANTT_PLAN_ESTIMATES` (`optimistic`, `mostLikely`, `pessimistic`), `GANTT_ANSWER_DERIVED` (decision 4) and the two schema objects; task 2.3 adds the shapes (decision 3), which need the seam's `ElementShape` type.
- `checks.ts`, plain ECMAScript: `ganttPropsProblems(props, origin)` (`tasks` a list without `workPackages` and a map with it; the widget element ID rule for task IDs, entry keys and predecessors, the `u-` prefix refused when `origin` is `agent`; each date a real day in range, by a small proleptic-Gregorian check in the contract, since `contract` imports nothing; a predecessor listed once; the dependents count per task); `ganttPlanLinkProblems(gantt, question)` (the named item exists in the question, is a Tree, and its columns declare the three estimates as numbers); `ganttChangesProblems(itemId, changes, props)` (each target's item is the Gantt's; `duration` only on a Gantt's own task, an integer in range; `start` a real day or `null`; `dependencies` within the limits or `null`). Problems name the task or operation and the field, as E1's and the Tree's do. Unknown tasks and cycles are not problems (spec, "Gantt references are not refused"), a task naming itself among them: a self-loop is a cycle, which `compute` reports as a warning. The first draft refused a list naming its own task, which refused the diff of a valid edit, such as `a: [a]` becoming `[a, b]` (task 9.1).
- `validate.ts`: `validateGanttProps(value, origin)` and `validateGanttChanges(itemId, value, props)`, each the seam's `widgetValidator` over the two Gantt schemas for the schema step, then the checks, returning E1's `Checked`.

**Standalone, compiled on first use, through the shared validator**, as agreed between the sessions: the two schemas are in no set, so `sets.ts`, `SCHEMA_SETS`, `SCHEMA_IDS` and `createAjv` do not see them, and the Gantt builds no Ajv and maps no error itself: `widgetValidator` adds the schemas to the one widget Ajv on the first validation and maps errors through E1's `problemOf`. Nothing happens when a module loads. Task 2.1's tests compile the two schemas in strict mode with `createAjv`'s options and E1's ID schema, which needs no seam, and check the Consistency Conventions' shape rules directly (JSON Schema 2020-12, the `$id` in its future set's namespace, no root combinator). One export block is appended to each of `index.ts`, `validate.ts` and `fixtures/index.ts` (decision 4).

*Alternatives:* the schemas inside the input and output sets (the follow-up's step, input format 1.1, which the sessions agreed to take together); a plan's tasks as a list of entries (a package the user adds in the WBS would come out as an `add`, where the approved answer writes `set schedule.u-1.dependencies`); a Gantt's own tasks as a map too (a map has no order, and a Gantt's own tasks show in the agent's order); `dependencies` and starts as two maps keyed by task ID, as the approved `gantt-plan` data writes `dependencies` (two maps for one element would need a shape the seam does not have).

### 3. The one generic diff, with the Gantt's two shapes

The Gantt declares two shapes and nothing else: `GANTT_SHAPE = {elements: "tasks"}` for its own tasks, a flat list, and `GANTT_PLAN_SHAPE = {elements: "tasks", keyed: true}` for a plan; `ganttShape(props)` picks one by `workPackages`. Every task key but `id` (`label`, `duration`, `start`, `dependencies`) is a field. The seam's `elementChanges` then gives a Gantt's `changes`:

- **A Gantt's own tasks:** no task is added, removed or moved, so only `set`s arise: a changed `duration`, `start` or `dependencies` is one `set` with the field's whole new value; a cleared request or a list emptied of every predecessor leaves the field out, which is a `set` to `null`.
- **A plan's tasks:** the keyed shape gives only `set`s. An entry the user creates, for a task the agent's plan said nothing about or a package the user added in the WBS, is one `set` per field: linking `u-1` gives exactly the approved answer's `set schedule.u-1.dependencies`. A field the user clears is a `set` to `null`, and an entry the user empties gives one `set` to `null` per field it held, never one `set` on the entry. The order is the seam's: by task ID, then field name, each in UTF-16 code-unit order.

The model never writes a field whose value equals the sent one and never keeps an empty entry (decision 8), so an edit undone by hand gives no operation. The diff and its keyed shape are the seam's, tested there; this change tests the Gantt on them (spec, "Computing a Gantt's changes"), and every result of a seeded property test of Gantt edits, in both shapes, passes `validateGanttChanges` and applies back to the edited props.

*Alternatives:* a Gantt-only diff (widget semantics where AD-20 wants one generic diff); the plan's entries as a list (gives an `add` for an added package, decision 2).

### 4. Checked against the approved UJ-2 examples, and the fixtures built from them

E1 already holds the approved files, unchanged, under `packages/contract/test/fixtures/asks/` and `answers/`. The Gantt's checks:

- **The same:** the `schedule` data, expanded (decision 6), gives a plan whose props validate and whose link passes against the Tree's `treeBoardDocument` question; the diff of the plan as sent and as edited is exactly the approved `schedule.` operation, `set schedule.u-1.dependencies`; `compute`, over the edited Tree and plan, gives the approved `schedule.finish` and `schedule.criticalPath`.
- **What differs, and why:** the example holds `schedule` as a molecule reference with the data as its parameters, so the fixture writes the Gantt item the expansion gives, under the reference's ID (proposal, open question 20); the answer's `derived` holds `wbs.*` values too, which are the WBS-with-PERT change's (F7), so the check compares the `schedule.` keys only.

`GANTT_ANSWER_DERIVED` declares the two keys: `finish` read from the graph's `finishDate`, and `criticalPath` the task IDs whose `critical` is true, in task order (proposal, open question 14). The fixtures (`packages/contract/src/fixtures/gantt.ts`, tests only):

- `ganttBoardDocument`, a question `schedule-review` holding a Gantt `release` whose own tasks are UJ-2's six work packages with the durations the UJ-2 plan computes (6, 4, 5, 13, 9, 6) and its four dependencies, and `ganttEditedValue`, that Gantt with a requested start and a changed duration;
- `ganttPlanBoardDocument`, the Tree's `treeBoardDocument` question with the plan `schedule` appended, `{start: "2026-11-02", workPackages: "wbs", tasks: {prototype: {dependencies: ["ux"]}, portal: {dependencies: ["architecture", "prototype"]}, billing: {dependencies: ["architecture"]}, reporting: {dependencies: ["portal"]}}}`; `ganttPlanEditedValue`, the plan after the approved edit, with the entry `u-1`; `ganttPlanChanges`, the approved answer's `schedule.` operation; `ganttPlanDerived`, from the approved answer.

A contract test checks that they agree (spec, "Gantt fixtures"); a `compute` test checks the derived values and that `release` schedules like the plan (compute spec, "A Gantt's own tasks are scheduled").

### 5. `compute`: a standalone source, requested starts, the board's graph source

- **`gantt` source kind** (`source.ts`): `{kind: "gantt", id, start, tasks: [{id, duration}], dependencies?, starts?}`; `gantt-plan` gains `starts?`. The graph source keeps `compute`'s maps keyed by task ID, an internal shape that `boardGraphSource` fills from the task fields. `cpm.ts`'s task fields are shared by both kinds: `duration` is a number input for `gantt` and the PERT formula for `gantt-plan`; everything else is the same formulas.
- **Requested starts:** each task gains `earliest` and `earliestDate` = `WORKDAY([p.firstDay],[p.t.earliest])`. A task with no requested start keeps compute-engine's `es`, `MAX(0,[p.a.ef],…)` over its predecessors, else `0`, and its `earliest` is `[p.t.es]`, so compute-engine's formulas, warnings and tests stay as they are. A requested task gets `startOffset`, a number input: the working days (`countWorkingDays`) from the plan's first working day to the first working day on or after the request (`firstWorkingDay`), `0` when the request comes no later or the plan's start is no date; its `earliest` holds the predecessors' formula, and its `es` becomes `MAX([p.t.earliest],[p.t.startOffset])`. `ef`, `lf`, `ls`, `slack`, `critical` and the dates are unchanged for every task. A request delays the task, so its predecessors gain the wait as slack. The offset is computed at expansion with `dates.ts`, since no whitelisted function counts working days between two dates; that is AskBoard's own code for rescheduling, as AD-13's "In-house computations" allows. A change to the plan's `start` would make the offsets stale, and the plan's start is not editable (proposal, open question 19); the view rebuilds the graph after each Gantt edit anyway (decision 7).
- **The board's graph source** (`board.ts`, new): `boardGraphSource(items)`, over the board's items as `{type, id, props}` with the draft's values in place: a Gantt with its own tasks gives a `gantt` source, its tasks' `duration`, `start` and `dependencies` gathered into the source's fields and maps; a plan gives a `gantt-plan` source whose maps hold the `start` and `dependencies` of each entry whose key is a leaf of its Tree (an entry that is no leaf adds nothing, proposal open question 10), and the Tree it names a `wbs-pert` source with that Tree's `nodes` (its other keys, `label` included, are ignored, as `compute`'s WBS source already ignores them); every other item gives nothing. A Tree named by two plans is mapped once. The items are typed structurally, `{type: string, id: string, props: unknown}`, and the props it reads are checked as every graph source is, a malformed one refused with a `GraphSourceError`, so `compute` needs no widget type from `contract` and its group runs before the seams. The maps it builds take every ID as an own key, `__proto__` included, and it copies and freezes the lists it reads, so a caller's later change cannot reach the source. `ask-core`'s send-time check calls it with `buildGraph` when the follow-up wires it.
- **Calendar helpers** (`dates.ts`, exported from the index): `isWorkingDate`, `firstWorkingDateFrom`, `addWorkingDays` and `workingDaysBetween` on `full-date` strings, over the serial arithmetic (`firstWorkingDay`, `countWorkingDays`), with no `Date`; a malformed day, a result outside the graph's range or a count no serial can reach is a `RangeError`.
- **Limits:** a test builds a Gantt at the contract's limits with 64-character IDs and checks every generated formula against the formula check (spec, "Scheduling formulas stay inside the limits"): 50 references of at most 134 characters keep `es` and `lf` under 8,192.
- **Determinism:** the new fixtures join the hash script that runs under the two time zones and two locales.

*Alternatives:* a requested start as a date compared inside the formulas (the backward pass and slack are in working days, which a date cannot give back without counting them); scheduling a standalone Gantt as a plan over a synthetic WBS (durations would pass through PERT's rounding); the mapping in `view` (`ask-core` needs the same mapping, and `view` is not on its import path).

### 6. The Gantt plan: its parameters as data, its expansion as a requirement

`packages/molecules/src/gantt-plan/gantt-plan.json`: `molecule` `gantt-plan`, `version` `1.0.0`, and `parameters`, a JSON Schema (`urn:askboard:molecule:gantt-plan:1`) of `{workPackages, start, dependencies}`, `workPackages` and `start` `$ref`ing the Gantt's definitions (`urn:askboard:input:gantt-props#/…`), `dependencies` an object whose `propertyNames` are E1's ID schema and whose values are the Gantt's predecessor list, `required` `workPackages` and `start`, `additionalProperties: false`. `index.ts` exports it in `READY_MOLECULES`. `molecules`' `package.json` declares `@askboard/contract` (`workspace:*`), the spine's only allowed import, which its tests use to compile the parameters in an Ajv made with `createAjv`'s options, beside E1's ID schema and the Gantt's props schema they reference.

**What the expansion gives** (molecules spec, "The Gantt plan's expansion"): one Gantt plan item with `workPackages` and `start` as given and a `tasks` map holding, for each key of `dependencies`, the entry `{dependencies: <its list>}`. The data's map of lists becomes the keyed shape's map of entries, so the plan diffs through the one generic diff (decision 3). The expansion is `ask-core`'s, through `MoleculeSource`, in the molecules epic; here a test-only expansion (`packages/molecules/test/expand.ts`) applies the rule to the approved data and must give `ganttPlanBoardDocument`'s plan exactly.

Tests: the file holds exactly those three keys and no string with `<` or a `javascript:` scheme; the parameters compile in strict mode and accept the approved `schedule` data unchanged; an unknown parameter is refused, naming it; the expansion gives the fixture plan, whose props pass `validateGanttProps` and `ganttPlanLinkProblems`. The molecule definition's format, with its composition and pointers, and the IDs the expansion gives, are the molecules epic's (proposal, open question 20).

*Alternatives:* a composition with JSON Pointer fills now (a pointer copies a value and cannot turn the data's map of lists into a map of entries, so the format would need a construct the molecules epic has not decided); the parameters written out again instead of `$ref` (two definitions of one shape to keep in step).

### 7. The board's graph in the view, and the baseline

- **What a component gets** (`catalog/port.ts`, on the seam's `ItemProps`): `board`, read-only, the board's items as sent (every question's items, flattened, the questions inside E3's areas included, read through `questionsOf`) and the draft record's value per item ID; and `onDerived(values)`, by which a component reports its declared derived values. AD-9 lets a component render from the board document, the draft record and the compute graph; the port now gives it the first two whole.
- **Where the graph is built:** `packages/widgets/src/graph/board-graph.ts`, in the Gantt's chunk: `liveGraph(board)` maps the items with their draft values through `boardGraphSource`, then `buildGraph` and `evaluateGraph`; `sentGraph(board)` does the same with the items as sent. Both are memoized by the identity of the items list and of the draft record, so two Gantts on one board share one build, and the sent graph is built once per board revision. The shell lists the items once per board document and lists them again when an agent update replaces the document (`shell/board-content.ts`, task 10.2), so the graph follows the agent's latest revision. Edits move the live graph on only when they commit (a drop, Enter, a checkbox), never during a pointer move. `graph/recalc.ts`, pure, says which input changes a built graph can take: a Gantt's changed duration (`<item>.<task>.duration`), and the moved start of a task that holds a request before and after the edit (its `startOffset`, counted with `compute`'s `firstWorkingDateFrom` and `workingDaysBetween` as `cpm.ts` counts it). Those go through `set` and `recalc` on the one live graph kept per items list. Anything else rebuilds: a first or cleared request, which adds or drops a `startOffset` node; predecessors, which change formulas; the plan's start; tasks added, removed or reordered; a plan, a Tree or any other item; and a value the graph source would refuse, which the rebuild then refuses, naming the item. Each draft record's graph is an immutable snapshot of the values, so a graph a component holds never changes afterwards, and a recalculated graph keeps the build's warnings.
- **Why not the shell:** the shell is in every srcdoc, and `compute` is far larger than the shell; the shell would then carry it on plain boards. When a second computing widget arrives (the WBS-with-PERT change), the board graph moves behind the port into a library chunk that every computing widget needs; the module's interface is written for that move.
- **`compute` as a library chunk:** `LIBRARY_CHUNKS` gains `compute`, providing `@askboard/compute` with the names the Gantt imports, so `assemble` inlines it only for boards with a Gantt. `radix` adds `ToggleGroup` for the zoom.
- **The baseline:** the sent graph's `startDate` and `finishDate` per task, for tasks that exist in it (proposal, open question 6). The spine draft states in AD-13 that the view builds the graph from the board document with the draft's values and builds the baseline from the document as sent.

*Alternatives:* `set` and `recalc` for every edit (a predecessor edit changes formulas, and a first request adds a node, so neither can); a rebuild for every edit (the first draft: at the full limits a drop passed the 100 ms aim in Firefox, task 6.8, and a test checks that each recalculated value equals a fresh build's); the baseline as extra fields in one graph (the WBS's estimates as sent would have to enter the graph twice).

### 8. The model: pure functions in `packages/widgets/src/gantt/model/`

- `tasks.ts`: the rows. For a Gantt with its own tasks, its `tasks`; for a plan, the leaves of its Tree's current nodes in document order, with their labels, each joined by ID with its entry in `tasks`, if any. Each row knows whether it was sent, its label, and the cells it shows.
- `schedule.ts`: per row, from the live graph, `startDate`, `finishDate`, `duration`, `critical`, `earliestDate`, or the formula error and its kind; from the sent graph, the baseline dates; the plan's `finishDate`; the answer's derived values by `GANTT_ANSWER_DERIVED`, an error left out.
- `edits.ts`: `requestStart`, `clearStart`, `setDuration` and `setPredecessors` on a task's fields, each returning a new frozen value, or the same value when nothing changes; a field whose value comes back to the sent one is restored to it (left out when the sent task had none), an empty predecessor list is left out, a plan entry is created by its first field and deleted when it holds none; `sameGantt` tells the component to put `undefined` in the draft. `canPrecede(value, rows, task, candidate)` refuses a candidate that would close a cycle (a walk over the current predecessors) or break the predecessor or dependent limits, with the reason. `setPredecessors` keeps an ID the task already holds that names no other row, itself included, since the contract accepts both (decision 2).
- `predecessors.ts`: the panel's boxes. One per other row, never the task itself, checked as the panel holds them and refused with `canPrecede`'s reason. Then one checked box per ID the task held when the panel opened that names no other row: a package deleted in the Tree, an agent's unknown ID or the task itself. It is labelled with the ID and says that it names no task, and the user may uncheck it, or check it again to restore it. No other task's panel offers it, and `canPrecede` never sees it, since it throws for a non-row. The first draft listed rows only, so such a predecessor could not be removed (task 9.3).
- `scale.ts`: per zoom, the pixels per calendar day (day 32, week 15 as the UJ-2 mock, month 4), the axis ticks (each day, each Monday, each month's first day) and labels in en-US (`Mon 2`, `Nov 2`, `Nov 2026`), and the conversion between a date and an x position. Calendar days, weekends unmarked (proposal, open question 8). An axis draws at most about 2,000 ticks: a span that would draw more keeps every n-th tick of its zoom, the smallest n that stays within the bound, each kept tick labelled, so the labels thin with the ticks. A start up to 9999-12-31 is valid, and the first draft drew every tick: 415,971 at week zoom for a plan reaching 9999. The accepted dates do not change (task 9.2).
- `drag.ts`: a move's new start from the pointer's travel: the nearest day, then the first working day from it, never before `earliestDate`; a drop on `earliestDate` clears the request. A resize's new duration: the working days from the start to the nearest day under the bar's end, at least 1.
- `date.ts`: the en-US date parser (`M/D/YYYY`, or `YYYY-MM-DD`), refusing anything else, a day that does not exist and a year outside the contract's range, with a reason; the echo (`= Wed, Dec 9, 2026`) and the grid's format (`12/9/2026`). Dates are the Gantt's (proposal, open question 16), so the parser stays in its model until a second widget needs it. Durations are read by the seam's `shared/number.ts` and refused unless whole and in range. The Gantt makes no element ID, so it does not use `shared/ids.ts`.
- `marks.ts`: per task, changed start, duration or predecessors against the sent value; in a plan, added (absent from the sent Tree) or re-estimated (its duration in the live graph differs from the sent graph's); the count "Your changes" shows (tasks changed in this item, once each).
- `keys.ts` and `focus.ts`: the grid's focus position, its moves on the arrow keys, Home and End, the action of each key in navigation and in edit mode (proposal, open question 18), and the toolbar's roving focus.

The model computes no date: every date and flag comes from `compute`, and the calendar helpers are `compute`'s.

### 9. The component: grid beside an SVG chart

`packages/widgets/src/gantt/index.tsx` registers `gantt` through `@askboard/view/catalog`; the rest of the folder renders the model:

- **Frame:** the widget frame with a toolbar row on `muted`: in a plan, the "Day | Week | Month" segmented control on Radix Toggle Group (labels provisional), its roving focus the model's (`focus.ts`) with Radix's own turned off, since Radix's kept Shift+Tab inside the group in Firefox; in both, the counter on the right. Below, the body: the grid on the left and the chart on the right, the chart in a horizontally scrollable region; under them the legend ("task", "critical path", "your change") and the field errors that name no task.
- **Grid** (`role="grid"`, labelled by the question's text): a header row in `text-label` on `muted` ("Task", "Start", "Duration", "Depends on"; provisional), 36px rows under a 32px header as in the mock. Start and duration cells are text inputs in edit mode with the parsed echo in `text-code`; a plan's duration is a right-aligned value. "Depends on" shows the predecessors' names; Enter opens the inline panel under the row: Radix Checkboxes, one per other task and one per held ID that names no other task (decision 8), disabled with their reason when `canPrecede` refuses, with Enter or "Done" committing and Escape cancelling. A refused entry shows a `field-error` under the row and keeps the focus and the draft. One element holds `tabIndex` 0.
- **Chart** (SVG, `role="img"`, labelled "Gantt chart, <zoom> zoom"; not focusable): the time axis on `muted` with labels in `text-badge` and `muted-foreground` and gridlines in `border`; per task a 14px bar in `gantt-bar`, or `critical` on the critical path; finish-to-start elbow arrows, 1px in `gantt-bar` or 2px in `critical`, with arrowhead markers; a changed task's 2px `change` outline offset by 1px; in a plan the baseline, a 4px bar in `border-strong` under the task's bar (provisional, proposal open question 7). Geometry is written as SVG attributes and colours as classes; no `style` attribute (AD-8).
- **Pointer edits:** a bar takes pointer down, captures the pointer, follows its travel through `drag.ts`, and commits on pointer up; while it moves, the guide (a 1px dashed line in `muted-foreground` at `earliestDate`, over the row) shows; Escape or a lost capture cancels. In a Gantt with its own tasks, the bar's last 6px resize it. A move below the drag threshold of 3px is a click and changes nothing.
- **States:** `disabled` keeps the zoom, the grid's navigation and the horizontal scroll, and turns off editing keys, the panel and pointer edits; the seam's ready helper reports ready once laid out; a task in error has a field error under its row and no bar (spec, "Gantt formula errors").
- **Data it did not get through the board page:** the component checks its props with `ganttPropsProblems(props, "agent")` and a plan's link with `ganttPlanLinkProblems` against the board's items, flattened (`model/link.ts`), and throws on a problem, so the error boundary fails the item (AD-10). The port's `board` holds every question's items in one list, so the component cannot single out its own question: on a board of one question, as every test document is, the result is the same, and a plan naming a Tree in another question is left to the send-time check (Handed on). Only test documents reach it before the follow-up.
- **The answer:** the seam's answer path sends the Gantt's draft value as `values.<id>`; the Gantt reports its derived values through `onDerived` after each rebuild or recalculation, and the question card sends them in the view answer's `derived`.

*Alternatives:* TanStack Table for the grid, as EXPERIENCE chooses (not installed; proposal, open question 16); a drag-and-drop library (EXPERIENCE: Gantt tasks move by pointer drag with no library); a focusable chart with arrow-key moves (the grid's start field is the keyboard path EXPERIENCE names, and a second keyboard model would need its own tests in three engines).

### 10. View integration: on the seams, not again

The seams of Context are the `tree-widget` change's; this change edits none of their behaviour. A Gantt item is a widget item like any other: the seam's view document, `componentsOf` and ready tracker take it by its `type`, and the seam's answer path and board-page refusal cover its value. If a seam turns out to list item types by name, `gantt` joins that list in the task that meets it, and nothing else changes. What the Gantt adds, each with tests first, leaving Choice's and the Tree's behaviour as their browser tests check it (proposal, open question 21):

- **Port** (`catalog/port.ts`): `board` and `onDerived`, as decision 7 says.
- **View protocol** (`view-protocol.ts`): an answer gains an optional `derived`, reference to value, in E3's `ANSWER` checks and its optional list; `readViewMessage` checks it structurally (own-property keys matching the reference pattern, JSON values), and `derivedAlone`, one small function beside the entry, admits it only beside `values`, on the answer message and on an answer act alike, since E3's entry serves both (task 10.3; on E4 the rule becomes the entry's `beside` slot). The shell holds the derived values its items last reported, and E3's send path (`card-acts.ts`, `withDerived`) adds those of the items in `values` when "Answer" is pressed, or when Submit sends a held answer.
- **Library chunks** (`tools/build/shared-modules.ts`): `compute`, and `ToggleGroup` in `radix`.
- **Board page:** it refuses a Gantt answer as it refuses any widget value, which a test checks; E3's `protocolAct` strips `derived` with `values`, so neither reaches `board-host` (task 10.3).

## Risks / Trade-offs

- [The seams or the Tree's own code may come out different from what this design names] → Task 1.2 stops if a commit of the range does not apply cleanly, and checks the keyed `ElementShape` and `widgetValidator` against decisions 2 and 3, and task 7.1 checks every Tree name the plan uses; a difference is recorded and the design revised with `/opsx:update` before any code, never worked around with a copy.
- [The keyed shape's round trip reads an empty entry or a `null` field as absent] → The model never keeps either (decision 8), and the property test in task 2.3 applies every diff back to the edited props.
- [Rebuilding the graph on each committed edit may be slow at 500 tasks over a 500-node WBS] → Measured in task 6.8: at the full limits a rebuild-only drop passed 100 ms in Firefox, so decision 7's recalculation is applied. Durations and held requests' moves recalculate (at the limits, 47 and 73 ms in Firefox); a first or cleared request, predecessor and WBS edits rebuild. A unit test times a rebuild and a recalculation at the limits, and the 500-task browser scenario times its drops; task 6.8's note records the times.
- [Known limit: at the full limits, 500 tasks with 50 predecessors and 50 dependents each, a first or cleared request rebuilds by design and takes up to 132 ms in Firefox, 90 ms in Chromium and 81 ms in WebKit (medians from pointer up to the bar changed), over the 100 ms aim] → Accepted and stated in the pull request: such a Gantt is at every limit at once, and on the scenario's 500-task Gantt a first request takes 29 to 53 ms. Recalculating a first request would need a `startOffset` on every task, which changes compute-engine's `es` formulas (decision 5).
- [`@askboard/compute` as a library chunk is the first workspace package the shared-modules plugin maps] → Task 5.3's build test lists the `compute` chunk and checks that `gantt` imports only names it provides; if the plugin cannot map a workspace package, the Gantt chunk bundles `compute` and the note records the size.
- [Ajv's strict mode may refuse the molecule's `$ref` into the Gantt's schema, or the `anyOf` inside a property] → The schema tests compile them first; the fallback is the definitions copied into the molecule, with a test that both accept and refuse the same values.
- [The `gantt` chunk grew from 8 KB, its entry at task 5.3 (8,221 bytes), to 51 KB with the component of group 6 (51,496 bytes) 60 KB with the plan of group 7 (60,346 bytes) and 61,467 bytes after the review and the integration onto E3] → It holds the component, the model and the board graph; `compute` is its own 39 KB library chunk; a board without a Gantt loads neither (spec, "The Gantt's chunks"), and the size check holds both to `chunk-sizes.json`'s record. The board graph leaves it for a shared chunk when a second computing widget comes (decision 7).
- [Pointer capture inside a sandboxed frame may differ by engine] → The drag scenarios run in all three engines with Playwright's mouse; a lost capture cancels the drag, which a test checks.
- [Treating a plan's Tree as a WBS may differ from what the WBS-with-PERT change decides] → `boardGraphSource` is the one place that decides it, and the spec scenario pins only the UJ-2 values.
- [The answer's `finish` is `compute`'s `finishDate`, not its `finish`] → `GANTT_ANSWER_DERIVED` names both sides, and the UJ-2 check compares the approved value.
- [The expansion may name the plan's items differently from the fixtures] → The fixtures use the reference's IDs, which answers use (AD-9); the molecules epic maps between the two, and the molecule's tests do not depend on the item ID.
- [Known limit: the chart's width is unbounded for far-future dates, so past each engine's clamp the bars no longer line up with the grid rows] → Kept as found by the PO on 2026-11-03 (Open Questions, 2); the axis ticks stay capped at 2,000 (task 9.2).
- [The port and the view protocol are seam files, and their integration is still open] → Each addition is small, tested first and listed in the proposal's merge points; E1's and the Tree's browser suites run in every task that touches the view.

   - **Answer (PO, 2026-11-03):** option (a): an answer will carry the declared derived values of every computing item in the question, changed or not.
