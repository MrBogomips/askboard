## Goals / Non-Goals

**Goals:**

- A Snapshot is assembled by the same `assemble`, from the same inputs, as the board the user saw (AD-9): the view renders a Snapshot as a locked board with no host.
- One gathering in `ask-core` serves both the agent and the board, under one owner check and one discard rule.
- Every addition is an appended block, so merging with E3, E4 and the widget changes stays mechanical.

**Non-Goals:**

- Configuration (`snapshotFolder`), AD-14's first-ask folders and the settings row (E8).
- Diagram renders on the board, their store and their message (the Diagram epic): E7 builds only the `assemble` seam (decision 4).
- Widget-specific Snapshot looks and references (the widget epics, E5).
- Listing, opening or deleting Snapshots from AskBoard: the folder is the interface (FR-26).

### 2. Contract

- **The `snapshot-data` set**, version 1.0, owner `snapshot`, one schema `urn:askboard:snapshot-data:snapshot-data`:

  ```text
  { versions: { snapshot, output, boardProtocol },
    snapshot: { takenAt, takenBy: "agent" | "user", who?, unsentWork?: true },
    epoch, askId,
    document,                                   // board document, current
    revisions: [ { itemId, rev, props } ],      // earlier revisions an event names
    state,                                      // board state, as the board receives it
    origin?,                                    // E4's origin message, when known
    events: [ { event, values? } ],             // the whole log in seq order, each event with its cursor
    molecules?: [ { itemId, reference, molecule, version } ],
    renders?: [ { itemId, rev, light, dark } ] }
  ```

  It `$ref`s the board document, board state, origin (E4's `urn:askboard:board-protocol:origin`) and output-event schemas, so it validates exactly what those sets define. `events[].event` is any output event but `discarded`, picked by its `type`, since an ask that is not discarded logs none. E4's origin schema is standalone, in no set (push-delivery design decision 1), and E1's shared validator does not hold it: until E4's follow-up joins it to the board protocol's set, `validateSnapshotData` compiles the data in a validator of its own, made by `createAjv` at its first call with the board protocol's standalone messages added (as E4's validators do), and the contract's compile check runs the sets with that group (task 1.1). `who` is required when `takenBy` is `user` and refused otherwise; `unsentWork` only with `user`. `events[].values` holds the full values `ask-core` keeps for that answer, by item ID in reference addressing (open question A2). Every level refuses fields it does not define, so a `draft` field fails.
- **Why `document` and `state` keep those names:** they are `BootData`'s, so the view boots a Snapshot through the same `parseBootData` and renders it through the same store; the extra fields are what a live board gets from other messages or never needs. `origin` is `BootData`'s name too: E4's `BootData.origin` is a `HeaderOrigin` (the message without `version` and `type`), which `parseBootData` reads through `isHeaderOrigin`; that check takes the whole message, so the Snapshot keeps the message as `board-host` sends it. E4's `BootData.agent`, the agent status, has no field here (What a Snapshot never holds), so a Snapshot shows no agent pill.
- **Tool envelopes:** `snapshot` joins `tools.json` as its fifth entry, the approved definition whole, with `urn:askboard:tool-envelopes:snapshot-request` built from it like the other requests; `snapshot-result` (`{versions, epoch, askId, state, path, unchecked?}`, `path` matching `^/`) and the typed `discarded` result, after E3's pattern for `fetch`.
- **Board protocol:** `snapshot` (page to host: `requestId`, `unsentWork?`), `snapshot-saved` (`requestId`, `path`) and `snapshot-failed` (`requestId`, `reason` of `write-failed`, `no-project-root` or `discarded`, `folder` with `write-failed` only), added by E3's decision 8 steps: a schema file each, names appended to `BOARD_PROTOCOL_MESSAGES` and `SCHEMA_IDS`, a recorded transcript. `requestId` reuses E3's action-ID schema.
- **View manifest 1.1:** optional `hostOnly: true` on a chunk and optional `keptRender` on a component chunk (decisions 4 and 5).
- **Constants:** E7's own are five, in `contract/src/snapshot/constants.ts`: `SNAPSHOT_NAME_PATTERN` (built from `ID_PATTERN` and the random part's length), `SNAPSHOT_RANDOM` (6 characters from `[a-z0-9]`), `SNAPSHOT_NAME_TRIES` (5), `SNAPSHOT_DATA_ELEMENT` (`askboard-data`) and `SNAPSHOT_LICENCES_ELEMENT` (`askboard-licences`). The Snapshot folder and the `.gitignore` lines are E8's, in `contract/src/project-folder.ts`: `SNAPSHOT_FOLDER` (`.askboard/snapshots`) and `ASKBOARD_GITIGNORE` (the four lines, as a tuple), beside `ASKBOARD_FOLDER` and `ASKBOARD_SUBFOLDERS`. Whichever of E7 and E8 lands first brings that file with those names and values, and the other reuses it; E7 defines none of them. The view's `BOOT_DATA_ID` takes its value from the contract's constant.
- **Versions:** `snapshot-data` starts at 1.0. The tool envelopes, the board protocol and the view manifest each take their next minor; as in E3's decision 2, the minor is a label assigned at merge, and E7 reads no other change's version number.
- **Registration:** `snapshotDataSet` appended to `SCHEMA_SETS`, the one list that takes no entry from outside; the set's `$id` is `SNAPSHOT_DATA_ID`, exported from the set's own module (`schemas/snapshot-data/index.ts`), with no `SCHEMA_IDS` entry unless a consumer needs one; the tool envelopes' new IDs appended to `SCHEMA_IDS`, as E3 appends `fetch`'s; one export block appended at the end of `src/index.ts`, `src/validate.ts` (`validateSnapshotData`, from `schemas/snapshot-data/validate.ts`, and `validateSnapshotRequest`) and `src/fixtures/index.ts` (a Snapshot data fixture and a `snapshot` result). Schemas compile on first use; the package stays `"sideEffects": false`.

*Alternative:* the data block as a new board-protocol message. Rejected: AD-7 gives the Snapshot data block its own set and owner, and a Snapshot outlives the protocol version that wrote it.

### 3. `ask-core`: one command, one gathering, one port

- **The port.** `SnapshotWriter.write(data) → Promise<{path}>`, rejecting with `SnapshotWriteError` (`code`, then `folder`, or for the code `no-project-root` the missing variable `CLAUDE_PROJECT_DIR` instead, and a message naming no agent content), declared in `core/src/snapshot/writer.ts` and exported from `core`'s index (built before group 0). E7's field appended to `CorePorts` in `ports.ts`, `snapshots?: SnapshotPorts` (`{writer, projectDir?}`, declared beside the port), carries the writer and, optional, the `projectDir` the session process gives `board-host` (`PushComposition.projectDir`, the display value), for the origin row only (decision 6, Two project values). `snapshot` implements the writer; the entry point wires both (decision 6). The field is optional, as E4's are, so every core built without it (E1's and E3's tests and harnesses) stays as it was; without it the command answers `no-project-root`, as in a session without a project root, and writes nothing (task 2.1).
- **The command.** `snapshot(askId, request)`, where `request` (`SnapshotRequester`) is `{takenBy: "agent", caller?: Binding}` or `{takenBy: "user", unsentWork: boolean}`, giving a `SnapshotOutcome`; its types and the hand-over to the writer are in `core/src/snapshot/command.ts`, so `core.ts` gains one short method. In order: an ask unknown to the epoch, or discarded, is `{outcome: "discarded"}`; for the agent's request, `AskCore.ownerRefusal(askId, caller)` gives `{outcome: "refused", why}`, `why` its `OwnerRefusal`, the check `fetch` applies; otherwise the data is gathered synchronously, so no event, document or state change can fall inside it, then handed to the writer, giving `{outcome: "saved", path, state, unchecked}`, `unchecked` when `AskCore.ownerOf(askId)` is `undefined`, `{outcome: "no-project-root", variable: "CLAUDE_PROJECT_DIR"}` when the writer refuses for want of a session project root (decision 6), or `{outcome: "write-failed", folder, code}`; a rejection that is not a `SnapshotWriteError` breaks the port's contract and rejects the command unchanged, for the adapter to report (task 2.1). The board's request carries no binding: the board token is its authority (AD-11), as for every board command.
- **The gathering** is a pure function in `packages/core/src/snapshot/` over what the command reads from the aggregate in that same step (decision 1, How E7 calls them), with the time from E3's `Clock` and `who` from the same rule as answers (FR-19). It takes the current board document and the board state from `lifecycleBoard(askId)`, the state with its own receipt mapping (decision 1, Receipts); the earlier revisions from `keptRevisions(askId)`, leaving out each question's current one and every revision no logged event names (by its `rev`, or an `ignore` edit choice's `keptRev`), which ask-core keeps only for the board's unsent work (AD-20), so `revisions` holds what the core spec names, the revisions its events name (task 2.2); the origin as `originMessage(projectDir, asked)` builds it, from `contract`, with `asked` from `AskCore.whoAsked(askId)` and `projectDir` from E7's `CorePorts` field, so it equals the `origin` message `board-host` sends the board, and none without that `projectDir`, as `board-host` then sends none; the log through the function `collect` reads it with, every entry from `seq` 1 with its cursor, unpaged (the aggregate's `eventsAfter(0)`, the log `read` returns, read without `read`'s owner check, which the board's request has no binding for); each answer event's full values from `keptAnswerValues(askId)`, by its cursor; the `molecules` entries from `expansionEntries(map)` over the map kept beside the current board document. It reads no draft record, no `BoardAddress` link, no agent record and no agent status.
- **Nothing changes.** No event, no publication on the subscription, no `received` move, no state change. A board's `unsentWork` is copied from the request, never derived from the draft record (E3's draft-record requirement: only the restore path reads it).

*Alternative:* `board-host` gathering for the board and `mcp-tools` for the agent. Rejected: two gatherings could disagree on what a Snapshot holds, and the owner check would sit in an adapter.

### 4. `assemble` builds both outputs

- **One function**, as AD-9 says: `assemble(data: BootData | SnapshotData, manifest, sources)`. Data that carries `snapshot` is a Snapshot. `sources` keeps E1's chunk texts by SHA-256 and adds `licences`, the notice texts by their manifest path, required for a Snapshot: a board's `sources` stays E1's `ChunkSources`, so its callers are unchanged, and a Snapshot's is `SnapshotSources`, `{chunks, licences}`, the same chunk texts beside the notice texts; two overloads pair each data with its sources, so a Snapshot without notice texts does not compile, and at run time it fails naming `sources.licences` (task 3.1). `targetOf(data)` gives the selection's mode (`SelectionTarget`: a board, or a Snapshot with its `renders`), so `snapshot` reads the files of the chunks `assemble` will select.
- **Order** (open question A3): charset; the view policy meta tag; the data block (`<` escaped, as E1 does); the styles; `#root`; the scripts; for a Snapshot, the `askboard-licences` block. The board's srcdoc is unchanged apart from the host-only chunks now selected as roots.
- **Selection** gains a mode: for a board, every `hostOnly` chunk is a root; for a Snapshot, none is, and a selected chunk that needs a host-only chunk is an error naming both (the build check of decision 5 prevents it).
- **Kept renders** (open question B3): for each component whose chunk names a `keptRender` chunk, a Snapshot whose `renders` cover every item of that component selects the kept-render chunk instead, and one that misses any selects both. A render covers an item when it names the item's ID and the current `rev` of the question that holds it, the revision the Snapshot shows; a render of an earlier revision does not count (task 3.3). Selection reads `renders` only for this; the kept-render chunk's own rendering is the Diagram epic's. Unit tests use a fixture manifest with `probe-diagram` and `probe-diagram-svg` chunks.
- **Licence notices** (open question B4): the notices of the selected chunks, one per package and version, sorted, each `{package, version, licence, text}`; the texts come from `sources.licences`, and a missing one is an error.
- **Purity:** no DOM, Node or Bun API, so the same code runs on the board page and in the session process; the server's typecheck compiles it with Node's types only.

*Alternative:* a separate `assembleSnapshot`. Rejected: AD-9 names one function, so that the board and its Snapshot cannot drift.

### 5. The view build: ext-apps only with a host

- `tools/build/chunks.ts` marks the `ext-apps` chunk `hostOnly`. The shell stops importing `App` at load: `connectToBoardPage` takes it from the shared-module registry (`shared("@modelcontextprotocol/ext-apps")`) only when `window.parent !== window`, with only a type import of `App`. The build's shared-module plugin records no need for a lookup it does not see, and a build check fails when a non-host-only chunk needs a host-only one.
- `packages/view/chunk-sizes.json` is re-recorded in the change that moves the import, saying why.

*Alternative:* a channel chunk kind holding the shell's connection code. Rejected: a new chunk kind changes the manifest more and splits the shell's boot.

### 6. The `snapshot` unit

- **Factory:** `createSnapshotWriter({projectRoot, folder, prepareFolders, viewBuild, randomness, report, fs?})` returns the `SnapshotWriter`; `projectRoot` is the real path of `CLAUDE_PROJECT_DIR`, or absent. It assembles the page and hands it to the unit's file side, `snapshotFiles({projectRoot, folder, prepareFolders, randomness, report, fs?})` (`files.ts`), whose `save({askId, takenAt, html})` prepares and checks the folder and calls `writeSnapshotFile` (`write.ts`). `viewBuild` is a port the unit declares, `{load(): Promise<{manifest, sources, folder}>}`; the entry point implements it over the build `board-host` loaded (open question B12), and the unit reads each notice text from `folder` by its manifest path, whose pattern admits no dot segment.
- **Folder** (open questions A5, A6): `folder` relative to the project root, which the entry point passes as E8's `SNAPSHOT_FOLDER`, so `<projectRoot>/.askboard/snapshots`, the project root being the real path of `CLAUDE_PROJECT_DIR`, resolved once. The entry point takes the root from E4's `sessionProjectRoot(env)` (`server/src/push-composition.ts`), the root E4's origins use, so neither `PushComposition.projectDir`, the display value, nor the working-folder fallback of the session's identity ever reaches the Snapshot folder.
- **Two project values, one seam each** (E4's answer of 2026-11-03, decision 1): the Snapshot's files take the session project root from `sessionProjectRoot(env)`; the Snapshot data's `origin` takes `PushComposition.projectDir` through E7's `CorePorts` field (decision 3), and nothing else reads that value. *Why:* the origin row must equal the board's, and `board-host` builds the board's row with `originMessage` from that same display value, so the two cannot differ; the files must never land under the working folder, which the display value falls back to without `CLAUDE_PROJECT_DIR`. Since no Snapshot is written without `CLAUDE_PROJECT_DIR` (XC-A1, below), that fallback never reaches a written Snapshot, and a written Snapshot's origin row names the same project as its folder. `sessionProjectRoot(env)` also gives none when the variable is set but not absolute or not naming a folder (E4's review fix L2); the writer then refuses as below, `no-project-root` naming `CLAUDE_PROJECT_DIR`. *Alternative:* the display value for both, which would write Snapshots under the working folder, as XC-A1 forbids; or `sessionProjectRoot(env)` for both, a real path whose folder name differs from the board's row when `CLAUDE_PROJECT_DIR` goes through a symbolic link.
- **No project root** (XC-A1, decided by the PO on 2026-11-01 under open question A5): without `CLAUDE_PROJECT_DIR` there is no session project root (AD-12), and no other folder stands in for it. `write` then rejects at once, before any folder preparation or file-system call, with `SnapshotWriteError` code `no-project-root`, naming `CLAUDE_PROJECT_DIR` and no folder, so nothing is created or written; `ask-core` returns it as the outcome `no-project-root` (decision 3).
- **Creating and checking the folder** (open question A6: the folders are still created when a Snapshot is written and they are missing; only who implements the creation changes): the unit creates no folder and no file but the Snapshot's. It takes the preparation as a port it declares, `prepareFolders(projectRoot) → Promise<FolderResult>`, shaped like E8's `FolderResult` (`ready {created}`, `no-project`, `failed {path, code}`), because AD-1 lets the unit import only `core`, `contract` and `view/assemble`, never the entry point's files, where E8's `ensureProjectFolders` lives (`packages/server/src/project-folders.ts`). The entry point wires `ensureProjectFolders`, which creates `.askboard/` and its subfolders when missing, then `.askboard/.gitignore` with AD-14's four lines and an exclusive create (an existing file is left alone). The unit calls it before each Snapshot: `no-project` is the `no-project-root` refusal, and `failed`, or a rejection, fails naming the Snapshot folder and the code. It then resolves the real paths of the root and of the folder, and refuses a folder whose real path is neither the root's nor below it, with the code `outside-project`, naming the folder as the caller named it.
- **Name and write** (open questions A4, B10): the HTML is assembled first; the name is `<askId>-<takenAt in YYYYMMDDTHHMMSSZ>-<6 random characters>.html`; the bytes go to `.<name>.partial` with exclusive create and `fsync`, then `link` to the final name; `EEXIST` draws a new suffix, up to five names; `EPERM`, `ENOTSUP` or `EXDEV` from `link` falls back to an exclusive create of the final name; the partial file is always removed. The path returned is the folder's real path joined with the name.
- **Failures** reject with `SnapshotWriteError` naming the folder and the error code, or `CLAUDE_PROJECT_DIR` for `no-project-root`, and one stderr diagnostic that names the folder, or that variable, and the code only. `report` is a line writer, `(line: string) => void`, and the unit writes the line itself (`askboard: ` and the error's message): the session's error reporter prints only an error's class and code, so it could not name the folder; the line never names the file, whose name holds the ask ID.
- **Platforms:** `node:fs/promises` only, so it runs the same on Bun and Node 24, macOS and Linux, devcontainer bind mounts included; the fallback covers a file system without hard links.

*Alternative:* `rename` from the partial file. Rejected: `rename` replaces an existing name, which AD-15 forbids.

### 7. `mcp-tools`: the `snapshot` tool in its own appended block

The unknown-tool error names the five tools with no edit of `server.ts`, whose `TOOL_NAMES` is built from `TOOL_DEFINITIONS`, which the contract's fifth tool joins.

The handler does not call `ownerCheck`: `ask-core`'s command checks the discard before the owner (decision 3), so the handler binds and hands the binding to the command, as `read(askId, after, caller)` takes it.

## Risks / Trade-offs

- [E3 or E4 lands with names other than decision 1's] → Group 0 checks each and stops for `/opsx:update`; nothing is built on an unmerged branch. E4's final names (`432f2f0`) are already folded in.
- [A Snapshot opened from `file://` runs AskBoard's script outside the sandboxed iframe] → The view policy rides along as a meta tag (`connect-src`, `frame-src`, `form-action`, `base-uri` `'none'`, scripts by hash); no view code creates a script element with a URL (AD-8); the browser tests record every request and include Firefox's file-script control.
- [A shared Snapshot carries project content off the machine] → By the user's choice (SOLUTION-DESIGN §6, residual risks); the file holds only what the board showed, and no token.
- [Large Snapshots: a diagram without a kept render inlines its renderer (PlantUML's chunk is 3.4 MB)] → No diagram renders on boards before the Diagram epic, which brings the kept renders; size is not bounded otherwise (FR-27 sets none).
- [Assembling a big board blocks the session process's event loop] → `assemble` is linear in the output; the end-to-end run times the golden board's Snapshot; requests are rare and user-driven.
- [The shell's lazy ext-apps breaks a board's handshake] → E1's and E3's browser suites run on every view task, and the build check fails on a static need.
- [Two branches append to the same contract and server files] → Appended blocks only; a conflict between appended blocks keeps every line of each (Merge points).
- [E7's receipt mapping drifts from `board-host`'s `stateOf`] → A `board-host` test compares a board's Snapshot state with the `state` message (task 6.1), and the gathering switches to `stateOf` if it moves where `ask-core` may import it (task 0.2).
- [Hard links refused by a mount] → The exclusive-create fallback keeps "never overwrite"; only the partial-file guarantee is lost there.
