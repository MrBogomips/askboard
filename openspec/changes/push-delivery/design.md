# Design

## Context

See proposal.md for why E4 comes now and what it leaves out. What the code starts from (E1, integration head `4913f52`; the E1 worktree's later commit only records task 9.7):

- **E1 in code:** `contract` with six schema sets listed in `sets.ts`, compiled once by `createAjv`, three entry modules (`.`, `./validate`, `./fixtures`) and `"sideEffects": false`; `ask-core` with the `Ask` aggregate, `AskStore`, ports `BoardAddress`, `BoardShowing`, `Identity`, `Randomness`, `Report`, and one subscription (events appended, `received` raised, ask discarded); `mcp-tools` over stdio with `ask` and `collect`, the no-hooks warning on every result and `unchecked: true` on every entry; `board-host` on `node:http` and `ws`, opening at the first ask; `notifier` with AD-18's detection rule and the argument-vector opener; the board page and view for one plain question; `dist/askboard.mjs`, run by the development plugin with `bun`. `packages/mod` and `packages/hooks` are empty, and the import check allows each only `contract`.
- **Mod delivery spike** (decided 2026-10-30, applied to the spine): the push paths, the interrupt retry, the PID key, the Unix socket, SIGINT, the guard's condition from 2.1.311, the toast and status entry, the process-client fallback. Its probe (`spike-mod-delivery/probe/hooks/register.js`) is evidence, not a starting point (its design, Non-Goals). E1's design hands four notes to E4 (Handed on): stamp the append time before the append; count only delivered pushes; one submit for a turn's catch-up; update the status entry when an ask closes.
- **Packaging spike:** hooks run `askboard hook <event>` through the launcher, which never fetches in hook mode and exits 0 when the executable is missing; Claude Code stays the parent of what the launcher `exec`s. E4 runs the bundle with `bun` until E11 brings the launcher.

ADs this design relies on: AD-1, AD-2, AD-3, AD-4, AD-5, AD-6, AD-7, AD-8, AD-10, AD-11, AD-12, AD-14, AD-16, AD-18, AD-19, AD-21, AD-22. ## Goals / Non-Goals

**Goals:**

- Each answer reaches the agent that owns its ask, by push where the mod runs and by `collect` everywhere, and is never lost or misrouted when a path fails (AD-3, AD-4).
- The three configurations of AD-1 (mod and hooks, mod disabled, hooks disabled) run in CI against the real session process, with real hook processes.
- Every local API rule of AD-5 and AD-11 is enforced from the first commit that serves the API.

**Non-Goals:**

- Live Claude Code in CI: the minimum, `stable` and `latest` matrix and the legacy-negotiation run need the live CI of E10 and E11 (E1's design, Non-Goals). The PO runs the live checks (tasks 11.x).
- Row 2 of the context header beyond the agent pill, which is E3's (ask state, counts, next-open jump, unread replies, agent-change flag).
- `with-references`' predicate and the asking rule's source (open question 1).

## Decisions

### 1. Contract: standalone schemas, append-only entry modules

As agreed across the parallel changes, E4's schemas stay out of `sets.ts`, `SCHEMA_SETS` and `SCHEMA_IDS`, and nothing in `contract` registers a schema when it loads:

- **Folders:** `packages/contract/src/push/local-api/` (records, stop, rule, notice, mod hello, mod turn, poll, delivered; owner `board-host`, version 1.0, `$id`s `urn:askboard:local-api:<name>`), `push/session-file/` (`urn:askboard:session-file:session-file`, owner `board-host`, `format` 1.0), `push/push-message.json` (`urn:askboard:output:push-message`, owner `contract`), `schemas/output/closed-event.json` (`urn:askboard:output:closed-event`, owner `contract`, in the output format's set since task 14.5) and `push/presence.json`, `push/origin.json` and `push/agent.json` (`urn:askboard:board-protocol:presence`, `:origin` and `:agent`, owner `board-host`, each naming the board protocol's version).
- **Validation:** `validateLocalApi(name, value)`, `validateSessionFile`, `validatePushMessage`, `validateClosedEvent`, `validatePresence`, `validateOrigin` and `validateAgentStatus` compile their schemas on first call into an Ajv of their own, made with `createAjv`'s options, adding the E1 schemas they reference (ID, cursor, epoch, output events). They refuse an unsupported major first, as E1's `validateVersioned` does, and map errors to E1's `Problem`.
- **Exports:** one new export block at the end of each of `index.ts` (types, constants, the session-folder functions, the asking rules, the schema objects the mod build needs), `validate.ts` (the seven validators) and `fixtures/index.ts` (the fixtures of the contract spec). No other existing contract file changes.
- **Constants:** `POLL_INTERVAL_MS` 1,000; `RECORD_TIMEOUT_MS` 10,000 (the spine's Deferred row leaves it to implementation: long enough for a slow hook, short enough that a stale record cannot bind a later call); `CLAUDE_CODE_MINIMUM` "2.1.311"; `LOCAL_API_MAX_BYTES` 1 MiB; `HOOK_REQUEST_TIMEOUT_MS` 2,000, inside the hooks' 5 s; `WORKING_WINDOW_MS` 60,000; `SESSION_TOKEN_BYTES` 16; `SOCKET_PATH_MAX_BYTES` 103 on macOS and 107 on Linux; `NOTICE_TEXT_MAX_CHARS` 120.
- **Session folder (open question 4):** `sessionFolder({env, uid})` returns `$XDG_RUNTIME_DIR/askboard` when that variable is set and absolute, else `${TMPDIR:-/tmp}/askboard-<uid>`; `sessionFilePath` and `socketPathFor` add `<key>.json` and `<key>.sock`, and `socketPathProblem` checks the limit. Pure functions, so the session process, the hooks and the mod compute one path from one environment.
- **Asking rules:** `ASKING_RULES` (`none`, `always`, `with-references`). The predicates are `hooks`' (AD-16): `sendsToAskBoard(rule, input)` in `packages/hooks`, for `none` and `always`; for `with-references` it throws until E8 defines it, and nothing can select that rule before then.
- When E1, E3 and E4 have merged, a follow-up moves the new schemas into `SCHEMA_SETS` as their own sets (local API, session file) or as minors of the output format and board protocol, as the Tree change plans for its schemas.

*Alternative:* add the local API and session file as sets in `sets.ts` now. Rejected: it edits E1's set list while E2, E3 and the widget changes add schemas in parallel.

### 2. The local API: HTTP over a Unix socket, inside `board-host`

- **Transport:** `node:http` listening on the socket path (AD-19 forbids `Bun.serve`). The mod reaches it with `$.http.fetch(url, {socketPath})`, the hooks and the client mode with `http.request({socketPath})`. The URL host is fixed (`askboard`); routes are contract constants: `POST /v1/records`, `POST /v1/stop`, `GET /v1/rule`, `GET /v1/notice?askId=<id>` (an ask's title and link, for the terminal link), `POST /v1/mod/hello`, `POST /v1/mod/turn` (decision 12), `GET /v1/mod/poll`, `POST /v1/mod/delivered`.
- **Checks, in order:** a request with `Origin` is refused (403); the `X-AskBoard-Session` header must equal the session token, compared in constant time (403); the body must be JSON under 64 KiB and valid against its schema, with its major supported (400 with the problems; the version refusal names the version supported). Board routes and the local API share no listener, so neither token can reach the other's routes.
- **Start (AD-2):** `mcp-tools` reports the first request other than `server/discover` to the entry point, which starts the local API; in practice that is `subscriptions/listen`, right after the handshake (spike O6). The board listener still opens at the first ask, as in E1. The folder is created with mode 0700 and checked to be owned by the user and not a symlink, its mode set to 0700 whenever it differs, special bits included (`& 0o7777`), so that the mod's exact check passes (decision 7, Start); the socket is created under a 077 umask and then `chmod`ed to 0600, since Bun and Node create it from the umask (spike, Linux harness).
- **Answers at once:** no handler waits. A poll response that would pass 1 MiB stops before the first board command that does not fit whole, the first command of a page going whole as in `collect` (AD-20), and returns `more: true` with a continuation (ask ID and the command's first `seq`), which the mod passes back. ask-core gives each event's command group with the events (`AskOverview.groups`, from E3's `entriesAfter`), and refuses a delivery report inside a command, which no poll gives (review fix M1, 2026-11-01).
- **Poll response:** for each owned ask with events above `received`: the ask ID, the owner's `agent_id` or none, the state, the latest cursor and the events with their cursors; then the pending asks (proposal, open question 3, for what each line shows). Events of unchecked asks are never listed. One request per poll serves both push and the pending-asks band.
- **Stop:** `POST /v1/stop` with `agent_id`, `agent_type` and `stop_hook_active` returns `{decision: "block", message}` or `{decision: "allow"}` and acts in the same call: a block raises `received` for what it carries; an allow tells `ask-core` that the agent finished. One call, so no other request can interleave between the decision and its effect.
  - *Review fix M1 (2026-11-01):* the block's fit gets each open ask's events with their command groups (`StopCandidates`) and cuts only between commands (AD-20); a fit that cuts inside one throws before anything is raised. Unlike the poll, the first command does not go whole when it passes the limit: the hook drops a response over 1 MiB and lets the stop through, after `received` was raised. The block then carries that ask without events, at the cursor before them, raising nothing, and its open asks tell the subagent to collect.
  - *Review fix (2026-11-01):* the block carries events in order up to the response limit, leaving room for `openAsks`, and raises `received` only to the last event it carries; the rest stay above `received`, and the open-asks list tells the agent to collect them, so no answer is marked delivered that the hook could drop for its size.
- **Diagnostics:** never a token or agent text; request failures name the route and the status.

*Alternatives:* keep the board listener's TCP port for the local API (rejected by the spike's row 7: a port is reachable by any local process that guesses the token, and the socket adds file permissions); a long-poll for the mod (AD-5 forbids it: a mod hook has 10 s, and `$.http.fetch` 30 s).

### 3. The session file

- Written with the local API, as `<key>.json` in the session folder, where `key` is `process.ppid`: the Claude Code process, parent of the session process and of each hook (spike criterion 13). Written to a temporary name with mode 0600 and renamed into place.
  - *Review fix (2026-11-01, following PO decision XC-A1):* `projectDir` is the session project root, the real path of `CLAUDE_PROJECT_DIR`, and is written only when the session has one; the schema makes it optional at format 1.0, since no version has shipped. No unit of AskBoard reads it; the browser tests' harness finds a session's local API by it, comparing real paths.
- **Collision:** when `<key>.json` exists and its `pid` is alive (`process.kill(pid, 0)`), the session process writes nothing, closes its local API and runs on pull alone, with one diagnostic. When the `pid` is gone, it replaces the file and its socket. While writing, it removes the other files and sockets of the folder whose `pid` is gone (AD-22's pruning of session files).
  - *Review fix (2026-11-01):* the claim is atomic: the session process writes a temporary file and links it to `<key>.json`, which fails when the name exists. On that failure a live holder means pull alone, and a dead one is removed and the claim tried once more. Only the winner removes `<key>.sock` and listens, so two servers starting together can never both believe they hold the file.
- **Exit:** E1's shutdown gains one step after the discard: remove the session file, if it is still ours (same `pid`), and the socket, then close the local API. SIGINT is already handled (E1, task 5.5).
- **Reading:** hooks and the client mode read `<ppid>.json`, validate it, and treat a missing, invalid or other-major file as "unreachable". The mod reads the same path through `$.fs`.

### 4. Agent records, owners and origins

- **Record table** (`board-host`, local API adapter): records keyed by `tool_use_id`, unbound until a call claims them, expiring after `RECORD_TIMEOUT_MS`; owners keyed by ask ID. The table alone holds Claude Code identifiers (AD-5).
  - *Review fix (2026-11-01):* a call that carries a `tool_use_id` binds its record whatever its age, since `PreToolUse` runs before Claude Code's permission prompt and the user may take minutes to approve. `RECORD_TIMEOUT_MS` limits only the next-call fallback. Unbound records are held for `RECORD_HOLD_MS` (30 minutes), at most `RECORDS_HELD_MAX` (1,000), the oldest dropped first.
- **Binding:** `mcp-tools` passes each call's identity to `ask-core`: the `_meta["claudecode/toolUseId"]` of the request, the tool name and the ask IDs it names. `ask-core` asks a new port, `AgentRecords.bind(call)`, which returns `{ownerKey, origin}` or nothing. `ask-core` sees the owner key only, an opaque string the table maps to the `agent_id` (absent for the main conversation). The next-call fallback binds the oldest unbound record with the same tool and ask IDs within the timeout; the spike never needed it (criterion 14), and a unit test covers it.
- **Owner checks** (`ask-core`): the first bound `ask` sets the owner and origin; `collect` on an owned ask, and E3's `update` and `fetch` once they exist, from an unbound call or another owner is refused, so a record lost to a hook timeout costs a retry, never another agent's answers. The refusal is `isError` text naming the ask, so no result schema changes.
- **Origin:** the adapter resolves it once, at the first bind of an `ask`: label from `agent_type` ("Main agent" or "Subagent <type>"), `cwd`, and with one `git -C <cwd> rev-parse --show-toplevel --git-common-dir --abbrev-ref HEAD` (argument vector, 2 s bound): the worktree's top level, the branch, and whether its common directory is the project's (`CLAUDE_PROJECT_DIR`'s, resolved once). Root is that top level when it is, else the project root, the real path of `CLAUDE_PROJECT_DIR` (AD-12), resolved once per session, and none unless the variable is an absolute path whose real path is a folder (review fix L2). A failed git run gives the project root and no branch, never an error to the agent.
  - *Review fix (2026-11-01, PO decision XC-A1):* without `CLAUDE_PROJECT_DIR`, or when its real path cannot be read, the session has no project root: an origin carries its label and `cwd` alone, with no root, branch or worktree, and git does not run. The session process's working folder stands in only where the project is named for display: the header's Project, the notification and the identity's git user name. The worktree's top level is kept as its real path, and git runs without `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR` and `GIT_INDEX_FILE`, which would point it at another repository.
- **No hooks:** an `ask` with no bound record keeps E1's behaviour: no owner, the no-hooks warning, `unchecked` on its `collect` entries. An ask with a bound record carries neither.

### 5. `ask-core` changes

- **Ports:** `AgentRecords` (above) and `Notices` (`notify(notice)`: the notifier) join `CorePorts` as optional members, so E1's tests and E3's additions compile unchanged; without them, E1's behaviour holds.
- **`received`:** new commands `delivered(askId, cursor)` (the mod's report) and `stop(ownerKey, stopHookActive)` (the guard), both through `Ask.markRead`, so the subscription's "`received` raised" event, and with it the receipt, follows every path (AD-3).
- **Agent finished:** `agentFinished(ownerKey)` closes the owner's open asks through E3's `close(reason)` with `agent-finished`, the one reason E3 does not use, and appends E4's `closed` event, since AskBoard, not the agent, closed the ask (AD-3). It waits for E3's change (Dependencies); until then the task stays open and the guard lets stops through without closing. When E3's output-format minor has merged, the `closed` event joins `collect`'s event union there, the one edit E4 makes to an existing schema: a finished subagent that the main conversation resumes can still collect its ask.
  - *Integration (2026-11-01, task 14.6):* the stop guard's allow calls `agentFinished`, which closes each open ask of the owner through the ask's `finish()`: it appends the `closed` event, then closes with `agent-finished`, which the board protocol's `closed` message now takes in E3's minor 1.1 (task 14.4); the subscribers hear the event, then the close. The `closed` event joined the output format's set and `collect`'s union in E3's minor 1.1 (task 14.5). `update` and `fetch` bind their call and refuse another owner's or an unbound one on an owned ask, with `ownerRefusalText`, before the ask is touched; their results carry `unchecked` only for an unchecked ask, as `collect`'s do.
- **Working boards:** `board-host` reports each board's working signal with `setWorking(askId, working)`, and `false` when its socket closes. On a new ask, `ask-core` calls `showing.open(link)` only when no ask of the epoch has a working board, and always `notices.notify(...)` for a showable, non-resent ask (AD-2, FR-23).
- **Version gate:** `ask-core` holds the client version, set by `mcp-tools` from the client information (the per-request envelope `io.modelcontextprotocol/clientInfo`, else `initialize`'s `clientInfo`) when its name is `claude-code`, else by `board-host` from the mod's hello. `ask` refuses a known version below `CLAUDE_CODE_MINIMUM` before creating anything, after the showability check (SOLUTION-DESIGN §5.1). The comparison is numeric per dot-separated part; a pre-release suffix counts as below its release.

### 6. Hooks: one hook mode in the bundle

- **Entry point:** `main.ts` reads `process.argv`: `hook <event>` runs `runHook(event)` from `@askboard/hooks`, `client <request>` runs its client mode, and anything else starts the session process as before. This needs AD-1's entry-point rule to name `hooks` (open question 8; `spine-update-draft.md` block 1); the import check's `server` row changes with tests first. `hooks` imports only `contract` and Node's API, and never the server units.
- **Each hook** reads stdin to its end (bounded at 1 MiB), parses the hook input, finds the session file by `process.ppid` and makes one local API request with a 2 s timeout. Any failure exits 0 with no stdout and one stderr line (AD-19). Stdout carries only the hook's JSON output.
  - **`PreToolUse`, AskBoard tools:** sends the record with the ask IDs from `tool_input` (`askId` for `ask`, and for E3's `update` and `fetch`; every `asks[].askId` for `collect`); no output.
  - **`PreToolUse`, AskUserQuestion:** asks `/v1/rule`; when the rule sends the question to AskBoard and boards can be shown, outputs a `deny` permission decision with a reason naming AskBoard's `ask` tool; otherwise nothing.
  - **`PostToolUse`, `ask`:** reads the `ask` result from `tool_response`; for the main conversation (no `agent_id`) and a result holding a board link, asks `/v1/notice` for the title, since the result carries none and the derived title is `ask-core`'s, and outputs `systemMessage` "AskBoard · <title> · <link>" (open question 3), or "AskBoard · <link>" when the session process cannot be reached. A subagent's ask costs no request.
  - **`SubagentStop`:** posts the stop; outputs `{decision: "block", reason}` when the session process blocks. The reason is a fixed preface line and the push message with the open asks (decision 8).
- **`hooks/hooks.json`:** matchers `mcp__plugin_askboard_askboard__.*|mcp__askboard__.*` for records, `AskUserQuestion`, `mcp__plugin_askboard_askboard__ask|mcp__askboard__ask` for the link, and no matcher for `SubagentStop`; every command `bun "${CLAUDE_PLUGIN_ROOT}/dist/askboard.mjs" hook <Event>`, timeout 5; `"modules": ["./askboard-mod.js"]`.

*Alternative:* a second bundle, `dist/askboard-hook.mjs`, from `packages/hooks`, leaving AD-1 as it is. Rejected as the default because AD-19 runs hooks from the one executable, so E11 would need the amendment anyway.

### 7. The mod: one module file, a small state machine per session

- **Build:** `bun run build:mod` (`tools/build/mod.ts`) bundles `packages/mod/src/index.ts` with Bun's bundler as one ESM file with no imports, `hooks/askboard-mod.js`, which git ignores and `bun run build` produces. It generates standalone Ajv validators for the poll response, the hello and delivered responses and the session file, as the view build does for the board page, so the mod compiles nothing at run time. The build fails on an `import`, `require` or `import.meta` in the output. `packages/mod` declares its own types for the subset of the mod API it uses, and compiles with ECMAScript libraries and no runtime types, like `core`.
  - *Review fix (2026-11-01):* Claude Code's module check accepts `$` passed only to functions declared at the top of the file, as function declarations or `const` bindings, and Bun's bundler writes top-level bindings as `var`. The build rewrites the module's top-level `var` bindings of functions to `const` and fails on any top-level `var` left bound to a function. Running `claude plugin validate` stays the PO's (group 11, common steps).
- **Start:** at `session.start`, one `$.process.run(["sh", "-c", "printf '%s %s' \"$PPID\" \"$(id -u)\""])` gives the key and the uid; the session folder comes from the contract with `$.env.get` of `XDG_RUNTIME_DIR` and `TMPDIR`. `$.clock.every(POLL_INTERVAL_MS)` starts the poll, which skips a tick while the previous one runs.
  - *Review fix (2026-11-01):* owner and mode, which `$.fs` does not show, are checked by `$.process.run` of `find <folder> -maxdepth 0 -type d -uid <uid> -perm 700` and `find <file> -maxdepth 0 -type f -uid <uid> -perm 600`, which BSD and GNU `find` answer alike (`-uid` and not `-user`, which both try first as a user name: review fix L3), with the uid of the start's run. The mod checks when it first finds a session file, since the folder may not exist yet at its start, again whenever the file names another `pid` or `epoch`, and every sixtieth poll, about once a minute, while it acts on one session process, so that a folder removed and made again by another user is found out; until both checks pass it polls nothing, shows no pending asks and writes one debug line, and it checks again at the next poll. Without them, on Linux without `XDG_RUNTIME_DIR` (containers, CI, `sudo -u`), another user who made `/tmp/askboard-<uid>` first could feed the mod a session file, a socket and forged answers (AD-10). The session process clears any special bit of the folder it makes or finds, so that the folder is 0700 exactly.
- **Per poll:** read and validate the session file (a new `pid` or `epoch` resets the mod's memory, and the hello goes again); `GET /v1/mod/poll`; for each ask entry, drop the events already pushed in this epoch, then route:
  - **subagent** (`agent_id` present): `$.agent.list()`; when it is listed with a status other than `completed`, `failed` or `killed`, one `$.session.append({message, agentId})` with every new event of that agent's asks;
  - **main conversation, turn running:** one `$.session.append({message})`, stamped with the time taken before the call, and kept in the turn's appended list;
  - **main conversation, idle:** one `$.prompt.submit({text})` with every new event; a result with `drop` puts the events on the dropped list.
- **Turn tracking** (main conversation only: events without `agentId`): `turn.start` marks it running, resets the step count and appends the dropped list (each marked as carried only from the turn's second request); `turn.step` counts requests and stamps the last one; `turn.complete` marks it idle and makes one submit with every appended event that no request carried (appended after the last step's stamp, or marked for a second request the turn never made) and every event still dropped.
  - *Review fix (2026-11-01):* whether a request carried an appended row is judged by request counts, never clock times: the mod notes the agent's request count when an append resolves, and the row counts as carried once a later request of that agent starts, and, for an append before a turn's first request, only from its second. Subagents' turns are tracked the same way, by `agentId`: an append to a subagent is reported only once carried, and not at all if its turn completes first, so the stop guard carries it (AD-10). The `turn.start` hook never waits for delivery reports; they go out with the next poll.
- **Pushed once:** an event enters the pushed set when its append or submit is called (spike O7); a call that throws leaves it out, so the next poll tries again. A successful append or a submit that was not dropped is reported with `POST /v1/mod/delivered`; a failed report is retried on the next poll, alone.
- **Turn reports (decision 12):** at `turn.start` and `turn.complete` of any agent, the mod reports `{agent_id?, running}` with `POST /v1/mod/turn`, only when the agent's state changes, through the socket or the process client; a report that fails is retried once on the next poll, then dropped, since the next transition replaces it.
- **Pending asks:** the mod keeps each poll's pending list and redraws the band (`$.ui.invalidate("ui.render")`) only when the list changes; a new pending ask owned by a subagent gets one toast. Lines are cut to `NOTICE_TEXT_MAX_CHARS`, the link kept whole.
  - *PO decision (2026-11-03, live run 11.3):* the terminal draws `$.ui.status` as one line, so four asks joined by newlines ran together and were cut at the terminal's width. The pending asks are therefore drawn in a band above the prompt, by a `ui.render` hook on `{ component: "AbovePrompt" }`: a dim header row, `AskBoard · <n> pending`, then one row per pending ask, `<title> · <who> · <n> open · <link>`, with the link drawn as a `Link`.
    - Rows are fitted to `e.props.bodyColumns`: the text before the link is cut, the title giving way first, and the link is kept whole; where that leaves the title fewer than 20 columns, the row draws the title alone as the link's label, still one row.
    - With no ask pending, or while a survey holds the band (`e.props.hasSurvey`), the hook passes (`next(e)`); otherwise it draws its rows above what the plugins beneath it draw.
    - The list lives in the mod's memory, not `$.state`: a reload starts empty and the next poll, within 1 s, fills it, so the plugin declares no state contract.
    - The engine raises `AbovePrompt` on the terminal and desktop surfaces only. While `$.session.surfaces()` lists another (VS Code, mobile), the mod also keeps a status entry of one line, the first ask's line and `+<n> more`, and clears it otherwise; the multi-line status entry is gone.
    - The mod API subset gains the `ui.render` hook with its matcher, `$.ui.resolve`, `$.ui.invalidate` and `$.session.surfaces`. The spine's Consistency Conventions row "Board link and notice" is amended in the same change.
  - *PO decision (2026-11-03, recheck of the band on `4d87002`, Claude Code 2.1.317):* at about 120 columns the rows above cut who asked and dropped the open count, while at about 80 the title-only row read cleanly; that layout now holds at every width. The header reads `🙋 AskBoard · <n> pending`, and each row `🙋 AskBoard › <title>`, the title being the link to its board (a `Link` whose child is the title's `Text`), with no address, who asked or open count. Everything is drawn in the accent colour: the named colour `cyan`, the nearest to DESIGN.md's petrol `primary` (`#0b6e7f` light, `#5fb4c2` dark) that each terminal draws from its own palette, so it stays legible on light and dark themes. On a narrow band only the title is cut, ending with `…`; the prefix, 14 columns with `🙋` counted as two, stays whole. The status entry kept for a surface without the band reads `🙋 AskBoard › <first title> · +<n> more`, the title cut to the notice limit. The rules above that fitted the text before a link no longer apply.
- **Fallback (AD-5):** a `$.http.fetch` that fails sends that request through the process client: `$.process.run(["bun", <plugin root>/dist/askboard.mjs, "client", <path>, <body>])`. After three requests in a row to one session process (same `pid` and `epoch`) whose fetch failed while the client reached it, the session sends everything through the client; any fetch that succeeds resets the count, and a new session process starts a new count. When both fail, the client is tried again at the next poll. So one transient socket error, such as a session process restarting, never pins the session to the client, and a client that fails once never hides a push for more than one poll (review fix, 2026-11-01). E11 replaces `bun` and the bundle path with the launcher; the command is one constant in `packages/mod`.
- **Never:** `$.session.send`, `asUser`, reading `CLAUDE_CODE_SESSION_ID`, writing a file, or logging a token or agent text (`$.ui.log` debug lines name routes and counts only).

*Alternatives:* the mod reading tool results in `tool.call` to show the link without waiting for a poll (the probe's way): a second path to the same data, and the poll is at most 1 s; one push per event: rejected, since the spike's runs woke one turn per catch-up submit (E1's Handed on).

### 8. The push message

Every push, catch-up submit and stop block carries the contract's push message: one fixed preface line, "AskBoard: the user acted on your ask. Skip any event whose seq you have seen.", then the JSON `{versions: {output}, epoch, asks: [{askId, state, cursor, events}]}`, the ask entries shaped as `collect` returns them, so the agent reads one shape whatever the path; a stop block adds `openAsks: [{askId, state, cursor}]`. The approved tool definitions and server instructions do not change (R5's count).

*Alternative:* a prose summary of each answer. Rejected: the agent would read answers in two forms, and AD-3's idempotence needs the cursor.

### 9. Notices

### 10. The board's working signal

The board page tracks `document.hasFocus()` with `focus`, `blur` and `visibilitychange` on the page, and input with `keydown` and `pointerdown` on the page. Input inside the sandboxed view does not reach the page, so the view sends a new view message, `askboard.view.activity`, at most once every 5 s while the user acts in it; the page's `AppBridge` answers it itself, as it does E1's view messages. A `blur` on the window that moves focus into the view's iframe does not end the signal, since `document.hasFocus()` stays true. The page sends `presence` on each change and after each `connect`; a 60 s timer from the last input turns it off. Hidden Chrome tabs run timers once a minute (F33), but a hidden tab has no focus, so the signal is already off.

*Review fix (2026-11-01):* when focus is inside the view and the browser window loses focus to another application, only the view's window gets a `blur`, so the page also checks `document.hasFocus()` once a second while the signal is on.
