# Proposal

## Why

The build order puts the widgets AXFX needs first: the Tree with the WBS-with-PERT molecule, and the Gantt with the Gantt plan (SOLUTION-DESIGN §3.1, AXFX FR-38). The `tree-widget` and `gantt-widget` changes build the two widgets, the Gantt plan's parameters and the board graph, and each hands the same remainder to "the molecules epic": the molecule definition's format, its expansion into board items, the mapping of a molecule's answers to the reference's addressing, the WBS-with-PERT molecule with the WBS-side rules that reach the plan (F20, deleting a package with dependents), and how an expanded plan names its expanded WBS (`tree-widget` design, Handed on; `gantt-widget` design, Handed on, and open questions 11, 12 and 20). This change takes that remainder, so that UJ-2's ask, two molecule references in one question, becomes a WBS and a Gantt plan on the board whose answer folds into the approved form: `wbs.*` operations, `schedule.u-1.dependencies`, and `derived` with PERT and CPM values (FR-15, AD-9).

## What Changes

- **`contract`, the molecule formats:** the molecule reference's props `{molecule, version?, data}` (`urn:askboard:input:molecule-props`) and the molecule definition format 1.0.0 (`urn:askboard:input:molecule-definition`): `format`, `molecule`, `version`, `parameters` (a JSON Schema), `items` (a composition of one widget item) and `fills` (per parameter, the JSON Pointers into the composition it fills, with four declarative forms: copy, `item`, `entries` and `omit`). Their checks, the validators of a reference, a definition and a reference's data against its definition's parameters, all on the shared `widgetValidator`, standalone and outside `sets.ts` like the widgets' schemas. A dispatcher, `widgetItemProblems(item, question, origin)`, runs the Tree's and the Gantt's own checks on any widget item, for the expansion now and for the input format widening later.
- **`contract`, the Tree's PERT:** two optional Tree props, `pert: true`, which requires the three estimate columns and gives every node and the item the built-in derived fields `expected` and `spread` (AD-13), and `openDepth`, accepted only with `pert`; estimates are working days, never negative (F8); the derived values a WBS answer carries, those that changed since the board was sent plus the item's totals, to two decimals (F7). Fixtures: the UJ-2 question expanded, and its edited values after the approved answer's edits.
- **`molecules`, two ready-made molecules as data:** `wbs-pert` 1.0.0 (new: a Tree with the three estimate columns, `pert` and the opening depth, filled from `nodes` and `depth`) and `gantt-plan` 1.0.0 (the `gantt-widget` change's parameters, completed with the format's `items` and `fills`). `READY_MOLECULES` lists both.
- **`ask-core`, expansion and addressing:** the `MoleculeSource` port; `expandMolecules`, which replaces each molecule reference in a question by its definition's item, filled from the reference's data, under the ID `<reference>__<item>` (AD-9): `wbs` becomes the Tree `wbs__tree` and `schedule` the Gantt plan `schedule__plan`, whose `workPackages: "wbs"` becomes `wbs__tree`; refusals name the reference (unknown molecule or version, data outside the parameters, an expanded item failing its widget's checks, an ID over 64 characters or already in the ask). The expansion map, kept beside the board document, rewrites every address of an expanded item to its reference's ID, for an answer's `changes`, its `derived` keys and the graph's warnings, so the UJ-2 answer comes out in the approved form.
- **`molecule-source`** (in the `board-host` capability): the adapter that serves the shipped definitions through the port: lookup by name and version (the highest shipped of the major, at or above a given version), the format's major checked, each definition validated on first use.
- **`compute`:** `boardGraphSource` maps every Tree with `pert` to its WBS-with-PERT source, whether or not a plan names it, and the index exports the evaluator's own `ROUND`, which the WBS rounds its answer's derived values with.
- **`view` and `widgets`, the WBS with PERT:** the Tree with `pert` shows the estimates with the "d" affix and the expected effort and spread as read-only values from the board graph, rolled up on parents, with a total row when the WBS has more than one top-level package; it opens to `openDepth` levels; it reports its declared derived values for the answer. A package the user adds gets predecessors in every plan linked to the Tree (F20: the package it was added after, or the one it was added under), and deleting a package with dependents asks first, then connects them to its predecessors (EXPERIENCE Molecules, WBS with PERT). The board graph moves from the Gantt's chunk into a `board-graph` library chunk the Tree and the Gantt share, as the `gantt-widget` design planned for the second computing widget.
- **One new seam, built here:** the port's `onValuesChange`, by which a component puts the values of several items of its own question into the draft record in one update, so that a WBS edit and the plan edit it causes are one draft change (AD-9, AD-20). Every other seam is the `tree-widget` and `gantt-widget` changes', reused as they are: the generic element diff, `widgetValidator`, the view document, the port's `board` and `onDerived`, the view answer's `values` and `derived`, the widget host.
- **Tests:** unit tests at 80% per file for every new module; browser scenarios in Chromium, Firefox and WebKit on the `tree-widget` change's widget host, ending with UJ-2's edits by keyboard whose answer, mapped by `ask-core`, equals the approved one.
- **Documents:** `spine-update-draft.md` (AD-6, where per-molecule schemas live; AD-9, the definition format, the expansion's rewriting and map, and linked edits; SOLUTION-DESIGN §4.11 aligned) and `ux-update-draft.md` (EXPERIENCE's "its parent's predecessors" worded as F20 resolved it), both applied on 2026-11-01, once the PO had accepted the open questions they name. No PRD change.
- **Not in this change:**
  - Wiring: the molecule reference in the input format and the board document (1.1), `ask` and `update` calling the expansion, `collect` and `fetch` calling the mapping, and the board protocol carrying widget answers. They belong to the input format widening that the `tree-widget` and `gantt-widget` changes name, which now covers molecule references too (open question 1).
  - The excerpt per work package and its row detail: E5, with `excerpts` (open question 10).
  - The sales estimate review and the decision matrix, which need the Table and the Approval; agent-built, registered and exported molecules (FR-16, FR-17) (open question 2).
  - Roll-ups and formulas on a Tree without `pert` (FR-12 and FR-14 for a standalone Tree), the Table and the Spreadsheet.

## Capabilities

### New Capabilities

- `contract`: the molecule reference and definition formats, their checks and validators, `widgetItemProblems`, the Tree's PERT props and derived declarations, the molecule fixtures (AD-6, AD-7, AD-9, AD-13). E1's, `compute-engine`'s, `tree-widget`'s and `gantt-widget`'s changes add requirements here too; whichever is archived first creates the spec.
- `molecules`: the ready-made `wbs-pert` and `gantt-plan` definitions as data (AD-9, FR-15). The `gantt-widget` change creates this capability's first requirements.
- `core`: expanding molecule references and mapping a molecule's addresses back to its reference (AD-9, AD-12, AD-20). E1 creates this capability.
- `board-host`: the `molecule-source` adapter (AD-9, AD-12). E1 creates this capability.
- `compute`: a Tree with `pert` in the board's graph source (AD-13). `compute-engine` creates this capability.
- `view-and-widgets`: the WBS with PERT, the WBS-side rules that reach a linked plan, the port's `onValuesChange` and the `board-graph` library chunk (AD-8, AD-9, AD-10, AD-13, AD-20).

### Modified Capabilities

None in `openspec/specs/`, which is empty. The deltas modify requirements that E1's, `compute-engine`'s, `tree-widget`'s and `gantt-widget`'s changes add (the Tree's item props and plain values, the Gantt plan's parameters and expansion, the board's graph source, the Gantt's predecessors), so this change is archived only after those four.

## Open questions for the PO

The PO is away and asked every session to keep working. Each question records the narrowest choice taken and why; the change is proposed with these choices, and each can be reversed with an `/opsx:update` before apply. The PO answered on 2026-11-01 and accepted every open question as proposed.

1. **Wiring waits for the input format widening.** E1's input format, board document and board protocol admit no widget item and no molecule reference, and the `tree-widget` and `gantt-widget` changes hand their joining (input format 1.1) to one follow-up. This change builds and tests the reference and definition formats, `expandMolecules`, the addressing map and the `molecule-source` adapter, and leaves calling them from `ask`, `update`, `collect` and `fetch` to that follow-up, which now joins the molecule reference too. *Why:* wiring here would edit the same sets, tools and protocol as the follow-up, twice. *Alternative:* wait for the widening and wire here.
   - **Answer (PO, 2026-11-01):** accepted as proposed.
2. **Two molecules in format 1.0.0.** `wbs-pert` and `gantt-plan`, the ones AXFX needs. The sales estimate review and the decision matrix come with the Table and the Approval; FR-15's agent-built molecules are, in the first version, widgets and formulas placed in a question, with no definition; FR-16 and FR-17 stay later (Deferred). *Why:* the other two need widgets that do not exist yet.
   - **Answer (PO, 2026-11-01):** accepted as proposed.
3. **The definition format: one item, four fill forms.** A definition is `{format, molecule, version, parameters, items, fills}`; `items` holds exactly one widget item; each fill names a JSON Pointer into it and a form: copy (the default), `item` (the value names an item of the ask, rewritten to the expanded item when it names a molecule reference), `{entries: <field>}` (an object's values become entries holding that field) and `{omit: [keys]}` (a copy without those keys, at any depth). *Why:* AD-9's plain pointer fill cannot turn the plan data's map of lists into the plan's map of entries (`gantt-widget` design decision 6), and one item keeps "the reference's ID and the child IDs of its data" unambiguous. Several items, with internal references between them, come with the first molecule that needs them (the sales estimate review), as a minor version of the format.
   - **Answer (PO, 2026-11-01):** accepted as proposed.
4. **Where per-molecule schemas live.** AD-6 says per-molecule schemas exist only in `contract`; the Structural Seed puts the ready-made molecules in `molecules` as data, and `gantt-widget` already wrote the plan's parameters there. The default keeps each definition, its parameters included, whole in `molecules`, written in `contract`'s definition format, and drafts AD-6 to say so (spine draft, Block 1). *Why:* a definition is one document that FR-17 will export whole. *Alternative:* the parameter schemas in `contract` and the compositions in `molecules`, with no spine change.
   - **Answer (PO, 2026-11-01):** accepted as proposed.
5. **Expanded IDs.** As AD-9 says, `<reference>__<item>`: `wbs__tree`, `schedule__plan`. A reference whose expanded ID exceeds 64 characters, or equals another item ID in the ask, is refused, naming both; `__` is not reserved in agent IDs. *Why:* AD-9's rule as written; reserving `__` would change E1's ID rule.
   - **Answer (PO, 2026-11-01):** accepted as proposed.
6. **The expansion map stays in `ask-core`.** The board document holds the expanded items only, never the reference, and the view has no molecule code; `ask-core` keeps, beside each board document, which expanded item belongs to which reference, molecule and version. *Why:* the view, `fetch` and Snapshots read only board documents (AD-12), and none needs the map, while adding it would widen the board document. A Snapshot's data block naming expanded IDs is E7's to decide.
   - **Answer (PO, 2026-11-01):** accepted as proposed.
7. **Versions.** A reference without `version` gets the highest shipped version of the current major; with one, the highest shipped version of that major at or above it, else a refusal naming the shipped versions. A definition whose `format` major is not 1 is refused. AskBoard ships one version per major of a molecule, so the parameters' `$id`, `urn:askboard:molecule:<name>:<major>` as `gantt-widget` wrote it, stays unique in the one widget validator. *Why:* semantic versioning without shipping every old version (FR-17's format rule, applied early).
   - **Answer (PO, 2026-11-01):** accepted as proposed.
8. **The WBS is a Tree with `pert`.** The expansion gives a Tree whose props add `pert: true` and `openDepth`, not a new widget type and not a provenance mark on the item. `openDepth` is accepted only with `pert`, so a plain Tree still opens fully expanded and takes no depth prop (`tree-widget` open question 8). *Why:* EXPERIENCE's composition is "a Tree with three-point estimate fields and PERT formulas", and a type or mark would need the Gantt plan's link and `boardGraphSource` changed to know it. A Tree with `pert` that an agent sends directly, once the widening admits Trees, is the same WBS; the skills teach the molecule.
   - **Answer (PO, 2026-11-01):** accepted as proposed.
9. **The WBS's look.** Estimates and values show the "d" affix, values with one decimal in en-US as the UJ-2 mock does; the item's totals show in a "Total" row (provisional) only when the WBS has more than one top-level package, since a single top-level package already shows them; a parent's own estimates are kept, ignored by PERT and neither shown nor editable; no derived value takes the change highlight. *Why:* DESIGN.md gives Values but no total row or decimals.
   - **Answer (PO, 2026-11-01):** accepted as proposed.
10. **No excerpt yet.** The `wbs-pert` parameters accept a pointer `excerpt` per node, so the approved data validates, and the expansion leaves it out (`omit`); no leaf chevron or row detail shows. E5 resolves the pointers and adds the row detail, with a minor version of the molecule. *Why:* `excerpts` is empty until E5, and a pointer shown unresolved would be noise.
    - **Answer (PO, 2026-11-01):** accepted as proposed.
11. **An added package's predecessors (F20).** A package the user adds, once named, gets in every plan linked to its Tree the predecessors that the plan gives the package it was added after ("Add node", the split: F20 and the approved answer) or under ("Add child": its parent's, as EXPERIENCE says); none when that package has none. The entry is written with the Tree edit, in one draft update, so UJ-2's split gives `set schedule.u-1.dependencies` with no plan edit. `ux-update-draft.md` words EXPERIENCE to match; the `gantt-widget` scenario that linked `u-1` by hand now links another task.
    - **Answer (PO, 2026-11-01):** accepted as proposed.
12. **Deleting a package with dependents.** The Tree's inline confirmation, which a node with children already has, also shows when a deleted package has dependents in a linked plan, naming how many; confirming connects each dependent to the deleted packages' own predecessors, followed through other deleted packages, without repeats; each deleted package's own plan entry goes back to what the agent sent for it, none for a package the user added, since the plan ignores an entry naming no leaf. *Why:* EXPERIENCE's rule, with no operation in the answer beyond the dependents' new predecessors, and a split taken back by a delete leaves no draft.
    - **Answer (PO, 2026-11-01):** accepted as proposed.
13. **A leaf that becomes a parent keeps its dependents.** "Add child" or "Indent" can turn a package with dependents into a parent, which has no bar: its dependents then show `compute`'s "names no task" field error, as `gantt-widget` open question 10 says, and the user relinks them. *Alternative:* a predecessor naming a parent stands for its leaves, a change to CPM.
    - **Answer (PO, 2026-11-01):** accepted as proposed.
14. **Linked edits through the port.** The Tree writes a linked plan's draft value through the new `onValuesChange`, limited to items of its own question, with the plan's own model functions keeping its invariants (no empty entry, a value back to the sent one restored). *Why:* AD-9 keeps every edit in the draft record, and one update keeps the two items consistent through a reload; the Gantt inferring the edit from the Tree's value could not tell a split from an "Add child".
    - **Answer (PO, 2026-11-01):** accepted as proposed.
15. **The board graph chunk.** `board-graph` (the board graph and the plan-link rules) is a library chunk that the `tree` and `gantt` chunks need, with `compute`; a board holding a plain Tree loads it too. *Why:* chunk needs are per component, not per item, and the formula spike measured `compute` at about 9 KB gzipped. The sizes are recorded.
    - **Answer (PO, 2026-11-01):** accepted as proposed.
16. **Derived values in the answer (F7).** Per node, `expected` and `spread` when their value, rounded to two decimals, differs from the board as sent, or the node is new; the item's `expected` and `spread` always; rounded half away from zero to two decimals; a value in error left out. The view computes them against the sent graph it already builds and reports them through `onDerived`. *Why:* this gives exactly the approved answer's 12 `wbs.` keys.
    - **Answer (PO, 2026-11-01):** accepted as proposed.
17. **Estimates and depth.** Estimates are numbers of working days from 0 to 100,000 (F8), unordered: an optimistic value above the pessimistic one is computed as given. `depth`, 1 to 8, defaults to 2 levels (EXPERIENCE).
    - **Answer (PO, 2026-11-01):** accepted as proposed.
18. **`update` and `fetch` on a reference.** For the follow-up that wires them: an `update` that changes a molecule reference re-expands it whole, and `fetch` of a reference returns its expanded item's full value under the reference's ID. *Why:* the agent never sees expanded IDs (AD-9).
    - **Answer (PO, 2026-11-01):** accepted as proposed.
