## Goals / Non-Goals

**Goals:**

- One definition format that both ready-made molecules are written in, data only, checked by `contract`.
- One expansion in `ask-core`, pure and deterministic, and one mapping back to the reference's addresses, checked end to end against the approved UJ-2 ask and answer.
- The WBS with PERT on the board: PERT values live, opening depth, the rules that carry a WBS edit into its plan.
- Every behaviour the specs name tested: pure logic under `bun test` at 80% per file, the rest in Chromium, Firefox and WebKit on the widget host.

**Non-Goals:**

- Anything proposal.md lists under "Not in this change", the wiring into the tools first.
- A second copy of any seam: the element diff, `widgetValidator`, the view document, the widget host, the port's `board` and `onDerived`, the answer's `values` and `derived`.
- Editing `docs/` in the apply, another change's folder or E1's schema sets; the spine and UX changes were drafted, then applied on 2026-11-01 once the PO had accepted the questions they name (task 0.3).

### 2. The molecule formats in `contract`, standalone, on the shared validator

`packages/contract/src/molecules/` holds:

- `molecule-props.json` (`urn:askboard:input:molecule-props`): `molecule` (`^[a-z][a-z0-9-]{0,63}$`, `MOLECULE_NAME_PATTERN`), `version` (MAJOR.MINOR.PATCH with no leading zero and at most nine digits a part, `MOLECULE_VERSION_PATTERN`, so that two spellings never name one version and each part compares as a number, as E1's `majorOf` reads `major.minor`), `data` (an object); `additionalProperties: false`; `required: ["molecule", "data"]`.
- `molecule-definition.json` (`urn:askboard:input:molecule-definition`): `format` (a version like `version`; the validator reads its major), `molecule`, `version`, `parameters` (an object; the checks say the rest), `items` (an array of exactly one `{type, id, props}`, `type` the molecule name's pattern, `id` E1's ID schema), `fills` (an object from parameter name to a non-empty array of `{pointer, as?}`, `pointer` an RFC 6901 JSON Pointer, `as` one of `"item"`, `{entries: <field name>}` (the Tree's field pattern), `{omit: [<key>…]}` (a non-empty list of distinct keys)).
- `index.ts`: the types (`MoleculeProps`, `MoleculeDefinition`, `MoleculeFill`, `MoleculeFillForm`, `MoleculeItem`), `MOLECULE_FORMAT_VERSION` (`1.0.0`), `MOLECULE_FORMATS_SUPPORTED` (`[1]`, the majors read), `MOLECULE_NAME_PATTERN` and `MOLECULE_VERSION_PATTERN` (both schemas state them, and a test holds them equal), `EXPANDED_ID_SEPARATOR` (`__`), and `expandedItemId(reference, item)`.
- `pointer.ts`, plain ECMAScript: `pointerTokens(pointer)` (`~1` read as `/`, then `~0` as `~`; `undefined` for no pointer), `pointerOf(tokens)` and `valueAt(root, tokens)`, which finds a place through own properties and the indexes a list has only, so that no pointer reaches a prototype. The checks resolve pointers with them and `ask-core`'s fills write through `pointerTokens`.
- `checks.ts`, plain ECMAScript: `moleculeDefinitionProblems(definition)`: `parameters` declares `$schema` 2020-12, its `$id` is `urn:askboard:molecule:<molecule>:<major of version>`, it has no root combinator and is an object schema; each `fills` key is one of its own `properties`; each pointer lies at or inside `/0/props` (the ID is the expansion's and the type the definition's) and its parent resolves in `items` (RFC 6901, `~0` and `~1` handled), a list's index being one the list has; no two fills share a pointer or fill places inside each other, the later fill named, so the order of the fills never matters (decision 3); an `item` fill's target is a string slot or absent; no string or key anywhere holds `<` or a `javascript:` URL, case-insensitive, after dropping tabs and line breaks as URL parsers do. These checks run on the definitions AskBoard ships, through `validateMoleculeDefinition` in `molecule-source`, and on no agent-supplied value: an agent's data goes through `moleculeDataValidator` only, and the expansion fills a composition the checks already passed, so refusing `javascript:` anywhere in a string costs no agent label. FR-17's agent-built or exported definitions would go through them; there a label such as "javascript: basics" would be refused, and that change revisits the rule.
- `validate.ts`: `validateMoleculeProps(value)`, `widgetValidator` over its schema; `validateMoleculeDefinition(value)`: first the format's major and the item count, refused before the schema as E1's versioned validators refuse a major (another major with reason `version`, naming the format this contract reads, `format 1 (1.0.0)`; a composition of other than one item at `/items`, saying that format 1.0.0 composes exactly one item); then `widgetValidator` over its schema; then the checks; last, the parameters compiled in strict mode beside the widget props schemas in an Ajv of their own made by `createAjv`, refused at `/parameters` when they do not compile, so that a definition that passes compiles in the data validator and a failing one never reaches the shared widget validator, which would keep its `$id`; `moleculeDataValidator(definition)`, a `widgetValidator` over the definition's `parameters` beside every widget props schema `contract` defines (`WIDGET_PROPS_SCHEMAS`: `tree-props`, and `gantt-props` once the Gantt's contract is on the branch, at group 0), so that the plan's parameters keep their `$ref`s into the Gantt's definitions. Problems name the path in the data; `ask-core` prefixes the reference's ID. The data validator checks the form the parameters state: the Gantt's `fullDate` is a pattern, so `2026-02-30` passes it, and whether the day exists is the Gantt's own check, at expansion step 4 (decision 4).

Like the widgets' schemas, these are in no set (`sets.ts` unchanged), compile on first use, and register nothing at import time; the widening joins them to input format 1.1. One export block is appended to each of `index.ts` and `validate.ts`.

**One version per major.** The parameters' `$id` carries only the major (as `gantt-widget` wrote it), and the one widget Ajv keeps the first schema with an `$id`; so AskBoard ships at most one version per major of a molecule, which the version rule (decision 5) needs anyway. `molecules`' tests check it.

*Alternatives:* the parameters' `$id` with the full version (two schemas of one major in one Ajv, and the `gantt-widget` file changed for nothing); a set of its own for molecules (AD-7's table puts molecules in the input format).

### 3. The fill forms, and one item per composition

AD-9 says a definition declares, per parameter, the JSON Pointers it fills. A plain copy cannot turn the plan data's `dependencies`, a map of lists, into the plan's `tasks`, a map of entries, which the keyed diff needs to give `schedule.u-1.dependencies` (`gantt-widget` design decision 6). So format 1.0.0 has four forms, each a pure, declarative copy:

| Form | What lands at the pointer | Used by |
| --- | --- | --- |
| copy (no `as`) | the value, deep-copied | `gantt-plan` `start`; `wbs-pert` `depth` → `openDepth` |
| `item` | the expanded item's ID when the value names a molecule reference of the ask, else the value | `gantt-plan` `workPackages` |
| `{entries: f}` | an object whose each value `v` becomes `{f: v}` | `gantt-plan` `dependencies` → `tasks` |
| `{omit: keys}` | a deep copy without those keys in any object | `wbs-pert` `nodes` → `nodes` without `excerpt` |

A fill whose parameter the data leaves out does nothing, so the composition's value stands (`openDepth: 2`, `tasks: {}`). Fills apply in the order of `fills`' keys, then of each list; a definition with two fills on one pointer, or with a fill inside another's place, is refused by the checks, so the order never matters for the result.

`ask-core` applies them with `fillItem(definition, data, references)` (`packages/core/src/molecules/fills.ts`), `references` being the expanded item's ID of each molecule reference of the ask (`ExpandedIds`): on a deep copy of the item, written immutably along each pointer, so the item shares nothing with the definition or the data; copies use `Object.fromEntries`, so a `__proto__` key stays data; a new key goes last and an existing one keeps its place. An `item` value that is no string is copied. An `entries` value that is no object, and a pointer naming no place (possible only in a definition that skipped the checks), are problems at the parameter's path in the data, never exceptions.

**One item.** Answers address a molecule "through the reference's ID and the child IDs of its data" (AD-9). With one item, that address is the item's own address under the reference's ID, with no ambiguity; with several, two items could share a child ID, and the format would need to say which item an address means. The sales estimate review (a Table and an Approval) is the first molecule that needs several; it brings a minor version of the format with that rule and with internal references between its items.

*Alternatives:* a JSONata-like expression per fill (code in a molecule, refused by AD-8 and FR-17); the plan's props taking `dependencies` as the data writes it (the keyed diff would then need a shape whose entries are lists, which the seam does not have); per-molecule expansion code in `ask-core` (AD-9: molecules are data, not code).

### 4. Expansion in `ask-core`, pure and deterministic

`packages/core/src/molecules/expand.ts`: `expandMolecules(items, source)` returns `{ok: true, items, map}` or `{ok: false, problems}`, so that no items can come with a problem, with no Node, Bun or DOM API (AD-1), and changes none of its inputs.

1. **IDs first.** For every molecule reference among the items of every question, at the top level or in an area (E3), its definition from the port (decision 5) and its expanded ID, `expandedItemId(reference.id, definition.items[0].id)`. A reference whose props fail `validateMoleculeProps`, or whose lookup fails, is a problem and is not expanded.
2. **Data.** `moleculeDataValidator(definition)(reference.props.data)`; a failure is a problem naming the reference and the path.
3. **Fill.** A deep copy of the definition's item, each fill applied (decision 3), its ID replaced by the expanded ID. The `item` form reads the IDs of step 1, so the order of the references in the ask does not matter.
4. **Check.** Every expanded ID at most 64 characters and unique among the ask's item IDs, the references' and the areas' own IDs included, so that an answer names each item unambiguously; each expanded item through `widgetItemProblems(item, question, "agent")` (decision 6) in its question as expanded, so a plan whose Tree sits in another question fails its link there, and a plan whose `start` is `2026-02-30`, a day the data validator's pattern passes, fails `ganttPropsProblems` there. A step 4 problem's `path` is the reference's place in the items given, since a path in the expanded item's props is no path in the reference's data, which the fills reshape; its message names the reference and that path in reference addressing (`schedule`, `/start`).
5. **Result.** The questions with each reference replaced in place by its item; `map`, a `ReadonlyMap` from expanded ID to a frozen `{reference, molecule, version}`, in the order of the references in the ask (`ExpansionMap` in `packages/core/src/molecules/map.ts`, beside `expansionEntries(map)`, which lists it as frozen `ExpansionRecord`s `{itemId, reference, molecule, version}` for E7); problems in reference addressing (decision 7), in the order of the references, each `{itemId?, path, message}`: `path` a JSON Pointer into the items given (the widening prefixes `/items`), `itemId` the reference's ID, and a message naming the reference, as E1's request problems name their item. With any problem, the caller refuses the request (AD-10); the expansion never returns a partial board.

Only references in a question's `items` expand: E1's and E3's input formats hold no top-level reference, and AD-7 puts molecules in questions. A question in an area is a question like any other: its references expand in place there, each problem's path going through the area (`/0/props/items/1/props/items/0`). A molecule item anywhere else is left as it is, for the input format to refuse. A reference with no ID, or a type `molecule` with props of the wrong shape, is a problem, not an exception. So is a definition whose parameters do not compile, or whose data check throws: a source hands out checked definitions, and the expansion still fails closed, refusing the reference at its `molecule` field.

*As built before group 0* (on `main` 0e85456): steps 1 to 3, step 4's ID checks and step 5, tested with a fake source over a test copy of `wbs-pert` and a test-only plan molecule; step 4's `widgetItemProblems` (task 2.3), the UJ-2 cases that need the shipped `gantt-plan`, and the walk into the questions of E3's areas, which the code before group 0 does not make, come with task 5.1 after group 0 (its note).

**What the caller does with it.** The widening's `ask` and `update` call it before storing a revision's board document (AD-12) and keep `map` beside it in the ask's state; the send-time check builds the graph of the expanded items. This change tests the function and builds no caller (proposal, open question 1).

### 5. `MoleculeSource` and `molecule-source`

The port's types are in `packages/core/src/molecules/source.ts`, exported from `core`'s index; `ports.ts` is unchanged until the widening adds `CorePorts.molecules`, which may move them there:

```ts
type MoleculeLookup =
  | { readonly found: true; readonly definition: MoleculeDefinition }
  | { readonly found: false; readonly reason: "unknown-molecule" | "unknown-version" | "broken";
      readonly shipped: readonly string[]; readonly detail?: string };
type MoleculeSource = { lookup(molecule: string, version?: string): MoleculeLookup };
```

`shipped` names the shipped molecules for `unknown-molecule` and the named molecule's shipped versions otherwise; the expansion words them (`it ships wbs-pert 1.0.0`, `it ships gantt-plan and wbs-pert`). `CorePorts` does not gain it yet: the widening, which calls the expansion, adds it there and composes it in `main.ts`.

`packages/server/src/molecule-source/index.ts`: `createMoleculeSource(definitions = READY_MOLECULES)`. On the first lookup of a molecule it checks that molecule's definitions with `validateMoleculeDefinition` and the format major, and caches the outcome; a broken one gives `broken` with the problem, never a definition. The version rule: without `version`, the highest shipped version of the highest shipped major; with one, the shipped version of that major if it is at or above the requested one, else `unknown-version` naming what is shipped. The definitions are imported JSON, bundled into the executable: the adapter reads no file and opens no connection (AD-11, NFR-9), and nothing runs before the first lookup (AD-2). `packages/server/package.json` declares `@askboard/molecules` (`workspace:*`).

### 6. `widgetItemProblems` and `elementShapeOf` in `contract`

`packages/contract/src/widgets/items.ts`, plain ECMAScript:

- `widgetItemProblems(item, question, origin)`: `tree` → the Tree's props check; `gantt` → the Gantt's props check and, with `workPackages`, `ganttPlanLinkProblems(item, question)`; any other type → a problem naming the item and its type. It runs the same checks the validators run, through them, and adds none.
- `elementShapeOf(item)`: `TREE_SHAPE` for a Tree, `ganttShape(props)` for a Gantt, `undefined` otherwise.

`ask-core` needs both now (expansion, and the fold's tests); the widening needs both for agent-sent widget items. Written once here, exported from `contract`'s `validate.ts` block, not `index.ts`: `widgetItemProblems` runs the validators, which use Ajv, and `src/index.ts` exports only checks and constants, as the Tree's and the Gantt's validators are exported; `core` already imports `@askboard/contract/validate`. Listed in "Handed on" for the widening.

### 7. Reference addressing

`packages/core/src/molecules/addressing.ts`: `referenceAddressing(map)` gives `toReference(address)`: when the part before the first `.` is an expanded ID in `map`, it becomes the reference's ID and the rest is kept (`wbs__tree.portal.label` → `wbs.portal.label`, `schedule__plan.finish` → `schedule.finish`, a bare `wbs__tree` → `wbs`); any other address is returned unchanged. Its helpers `changes`, `derived` and `warning` apply it to:

- an answer's `changes`: each `target`; `parent` and `after` are element IDs and stay (F3);
- an answer's `derived`: each key, values untouched;
- a problem or warning: its item ID and any address in it. `core` declares no dependency on `compute`, so `warning` is structural, for compute's `{error, address, detail}` and E1's problems alike, at any depth: the fields `address`, `target` and `itemId` are addresses and go through `toReference`, so a child ID that happens to equal an expanded ID stays; every other text has each expanded ID it names, as a whole ID, replaced by `textToReference`, so a detail such as "the work packages wbs__tree name no WBS-with-PERT item" names `wbs`.

`answerInReferenceAddressing(map, question, sentItems, editedValues, derived)` is the fold the widening's `collect` path will call: for each widget item of the question that has an edited value, in the question's order, `elementChanges(item.id, sent.props, edited, elementShapeOf(item))`, concatenated and mapped; `derived` mapped. A test runs it on the contract's molecule fixtures (decision 9) and compares the result with the approved answer: the changes as a set (the approved file lists them in the user's order, the diff in its own, as `tree-widget` open question 19 says), the derived values as a map.

*Alternative:* calling the diff with the reference's ID as `itemId` (no rewrite for changes, but derived keys and warnings would still need one; one rewrite for all three keeps one rule).

### 8. The Tree's PERT in `contract`

In `packages/contract/src/widgets/tree/`: `tree-props.json` gains `pert` (`const: true`) and `openDepth` (integer 1 to 8); `treePropsProblems` gains the rules of the spec's "Tree PERT props", written in a new `pert.ts` that it calls, reading the estimates from `GANTT_PLAN_ESTIMATES`, the one list the plan's link check already reads (before group 0, a private copy of the three names, which task 2.1 replaces with the import now that the Gantt is on `main`); the rules repeat the schema's for `pert` and `openDepth`, for the props the Tree's chunk checks unseen by a schema, and walk the estimates no deeper than the depth limit; `index.ts` gains `TREE_PERT_DERIVED` (`{node: ["expected", "spread"], item: ["expected", "spread"]}`), `TREE_PERT_MAX_ESTIMATE` (100,000), `TREE_PERT_ANSWER_DERIVED` (`{fields: ["expected", "spread"], decimals: 2, itemTotals: true, onlyChanged: true}`), which the view reads to report and the contract's tests check against the approved answer, `treeDerivedFields(props)` (`TREE_PERT_DERIVED` for a Tree with `pert`, none otherwise) and the type `TreePertProps` (`TreeProps & {pert: true, openDepth?}`). `TreeProps` itself takes no new field: an optional field of a primitive type changes how `Object.freeze` infers in the Tree's widget tests, which stay unchanged. A parent's own estimates stay valid and ignored, as `compute`'s PERT ignores them; an edited value where an indent made a leaf a parent is never refused for it.

### 10. `compute`: a Tree with `pert`

`boardGraphSource` (`packages/compute/src/board.ts`) maps a Tree with `pert: true` to a `wbs-pert` source from its `nodes`, as it already maps the Tree a plan names; a Tree both is mapped once. `compute`'s index also exports the evaluator's own `ROUND` as `roundNumber(x, digits)`, so that the WBS rounds its answer's derived values exactly as a `ROUND` formula would, with no second rounding in the view (decision 14). Nothing else in `compute` changes: PERT's formulas, roll-ups and the plan's duration from `expected` are `compute-engine`'s.

### 11. The view's seams: `onValuesChange`, and the board as the user sees it

`ItemProps` gains `onValuesChange(values: Readonly<Record<string, unknown>>)`: the draft values of several items, `undefined` removing one, applied by the shell in one draft update. Each item's callbacks are built in `RenderItem` (`shell/renderer.tsx`), which already builds `onValueChange`, running E3's `onBeforeChange` first, `onDerived` and the error path; it builds `onValuesChange` bound to the item's question, whose item IDs the question card passes it (`itemIdsOf(question)`): a key naming an item outside that question changes nothing and is reported through the item's error path, as a thrown render error is. Like `onValueChange`, it runs `onBeforeChange` once, before the update, so the first linked edit of an answered question starts its revision once (E3, `revise`). The draft record's identity rules hold per item (an unchanged value keeps its identity), so `liveGraph`'s memo sees one new draft per update.

Built in `packages/view/src/catalog/port.ts`, `shell/draft-store.ts` (an update of several items that makes one new record and notifies once), `shell/renderer.tsx` and `shell/question-card.tsx`, tests first, with test-only `probe` items, as the `tree-widget` seams were. No other change needs it; it is listed in Merge points.

**The board as the user sees it** (integration session, 2026-11-03, option A; found at group 0). On an answered question the user revises, an item with no draft value shows its question's answer, which the port's board did not hold: `linkedPlans` would read the plan as sent, and a linked write from the Tree would drop the answer's plan edits. So `BoardContent` gains `shown`, item ID to the value the item shows: its draft value if it has one, else the value its question's latest answer holds for it (E3's logged answer, the content `cardState` shows as `shown`); an item with no entry shows its props as sent. While no answer holds a widget value, `shown` is the draft record itself, so the memos keep their identities. Every reader of the board as it stands reads `shown`: `liveGraph`, the Gantt's Tree nodes (`treeNodesOf` in `gantt/model/link.ts`, called from `gantt/index.tsx`), `linkedPlans` and the WBS; `sentGraph` keeps the items as sent, and change marks and counters keep reading the draft record. An item of a question being revised shows its `shown` value until the user changes it (`RenderItem`), as it showed the answer before the first edit, so the graph matches what the card shows. `revise` still seeds no widget value: the draft record holds only what the user changed, and its counters stay honest. Built in `catalog/port.ts` (the field), `shell/board-content.ts` (made from the board state as well as the document and the draft record, one object per items list, draft record and answers), `shell/renderer.tsx`, `graph/board-graph.ts` and the Gantt's `link.ts`, tests first, in task 8.1.

*Not taken:* option B, `revise` seeding the question's widget values from its answer before the linked update: values the user never changed would enter the draft record and its counters. Whether a revised answer carries the values of items the revision left alone is `widget-answers`'. So is option A's own limit, found in task 8.1 and accepted by the integration session on 2026-11-03: a revision cannot take one item back to its props as sent (Risks, Handed on).

*The Gantt's "Keep mine" issue* (its design, Handed on, E3): on a question kept on an earlier revision, the card shows that revision's items while the board lists the latest document's. Option A neither fixes nor worsens it: the issue is which items the board lists, and A changes only which value an item reads, an item's draft value still coming first on a kept question. It stays handed on.

*Alternatives:* the plan's component inferring the edit from the Tree's value (it cannot tell a split from an "Add child" under the same parent, and a hidden plan would miss it); the Tree calling `onValueChange` and a second callback (two draft updates, two graph builds, a moment where the two items disagree).

### 12. The plan-link rules: `packages/widgets/src/graph/plan-link.ts`

Pure functions over the port's `board` (items as sent, draft values; the type `BoardContent` imported from `@askboard/view/catalog` as a type only, as `board-graph.ts` imports it), used by the Tree's component. They apply to any Tree a Gantt plan names, with `pert` or without (integration session, 2026-11-01): F20 and the delete rule belong to the link, not to the WBS, as tasks 10.3 and 10.4 rewrite the Gantt's own plan-and-Tree scenarios, whose Tree has no `pert`.

- `linkedPlans(board, treeId)`: every Gantt item on the board whose `workPackages` is the Tree's ID, with its current value, the board's `shown` value, else as sent (decision 11). The port gives the board's items flattened, every question's, areas' included (`boardItemsOf`), with no question's bounds, so it reads the link board-wide, as the Gantt's own `linkedTree` (`gantt/model/link.ts`) does; keeping a plan in its Tree's question is the send-time check's (`widgetItemProblems`' link check, decision 4). Should a plan in another question ever reach the view, `onValuesChange`'s question bound (decision 11) refuses the write and the Tree item fails through its error path.
- `predecessorsOf(plan, packageId)`: the entry's `dependencies`, or none.
- `afterAdd(plan, sentPlan, added, anchor)`: the plan with `added` given `predecessorsOf(plan, anchor)`, through the Gantt model's `setPredecessors(value, sent, taskId, predecessors)`, which needs the plan as sent, so no empty entry is kept and a value back to the sent one is restored. `anchor` is the focused package for "Add node", the parent for "Add child".
- `dependentsOf(plans, packageIds)`: the tasks that list any of them, for the confirmation's count.
- `afterDelete(plan, sentPlan, deleted)`: for each surviving task that names a deleted package, that name replaced by the package's predecessors, followed through other deleted packages, keeping the first occurrence of each and never the task itself; then each deleted package's entry set back to `sentPlan`'s entry for it, or removed when the agent sent none.

The Tree's component calls them on the commit that names an added package (not on the insertion, which an empty name or Escape takes back) and on a confirmed delete, and puts the Tree's and the plans' values through `onValuesChange` in one update. A move, a rename, an indent or an outdent touches no plan (proposal, open question 13).

**Limits inside a linked write** (integration session, 2026-11-01; review L8): `setPredecessors` throws a `RangeError` past 50 predecessors of a task or 50 dependents of a task, and a new entry past 500 entries throws too. `afterAdd` gives each of the anchor's predecessors one more dependent and the plan one more entry; `afterDelete`'s merged lists can pass 50 predecessors and give a predecessor more dependents. So `afterAdd` and `afterDelete` return either the new plan or a refusal naming the limit the edit would pass, never throwing. On a refusal the Tree's component refuses its own edit with a field error naming the limit, at the name being committed or in the delete confirmation, and writes nothing, to the Tree or to any plan: a linked edit is whole or not at all, and the user can take the addition back with Escape or cancel the delete.

The module sits in the `board-graph` library chunk (decision 13), beside `board-graph.ts`; it imports the Gantt's `setPredecessors` from `gantt/model/edits.ts`, so the plan's invariants have one implementation.

### 13. `board-graph` as a library chunk

`gantt-widget` built the board graph inside the Gantt's chunk and planned this move. `packages/widgets/src/graph/index.ts` becomes the entry of a library chunk `board-graph` in `LIBRARY_CHUNKS`, needing `compute`. `@askboard/compute` is a package and maps by name; `graph/index.ts` is a file inside `widgets`, so the shared-modules plugin maps it by path, as it already maps the port's file (`PORT_PATH`). The `tree` and `gantt` chunks then need `board-graph`, and one module instance per srcdoc holds the memo, so the Tree and the plan read one live graph per draft update and one sent graph per revision. `board-graph.ts` and `recalc.ts` leave the `gantt` chunk, whose import of `../graph/board-graph.ts` (`gantt/index.tsx`) becomes `../graph/index.ts`. `plan-link.ts` (decision 12) brings the Gantt model's `edits.ts` and what it imports (`date.ts`, `tasks.ts`, the Tree's `rows.ts`) into `board-graph`, beside the `gantt` chunk's own copy: that code is bundled twice, and the sizes show it. The `compute` chunk provides an exact list of names, and an import of any other fails the build: `roundNumber` joins the list when the WBS imports it (decision 14). `chunk-sizes.json` records `board-graph`, the `tree` chunk's growth and the `gantt` chunk's shrinkage, with `--record-sizes`.

*Fallback:* if the plugin cannot map a path inside `widgets`, `packages/widgets/package.json` exports `./graph` and the chunk maps `@askboard/widgets/graph` by name; the task note records it.

### 14. The WBS in the Tree: model and component

Model, pure, in `packages/widgets/src/tree/model/`:

- `pert.ts`: per visible row, the expected effort and spread read from the live graph (`<item>.<node>.expected`), or the formula error; the totals (`<item>.expected`, `<item>.spread`) and whether the Total row shows (more than one top-level node); the display text, one decimal in en-US with the `d` affix (`5.5 d`); the derived values to report, by `TREE_PERT_ANSWER_DERIVED`, which an answer carrying the Tree's value carries beside it (whether an answer also carries those of an untouched computing item is `widget-answers`': on 2026-11-03 the PO chose FR-12 option (a), every computing item of the question, touched or not, its decision 10; until it lands the view follows the Gantt's decision 10, `withDerived`), comparing each node's values in the live and the sent graph rounded to two decimals with `compute`'s `roundNumber` (decision 10).
- `rows.ts`: with `pert`, the expanded set opens with the nodes above `openDepth`; without it, fully expanded as before.
- `edits.ts`: with `pert`, `setField` on an estimate refuses a negative value or one over the limit with a reason, and a parent's estimate cells are not editable (`can`).

Component (`packages/widgets/src/tree/`): with `pert`, the header reads "Work package", the three estimates, "Expected effort" and "Spread"; estimate cells show the affix, and in edit mode the input keeps it as an Input Group affix (DESIGN.md Input atoms); the two value cells are right-aligned and never focusable for editing, though the arrow keys reach them; the Total row is a last, read-only row of the treegrid, with no `aria-level`, labelled "Total" (provisional). It reads the graph through `board-graph` and reports `onDerived` after each committed edit and on first layout. Change marks are the Tree's own; derived values take none.

With `pert` or without, a Tree that a Gantt plan names calls the plan-link rules (decision 12): F20 and the delete rule belong to the link. Its inline delete confirmation, which a node with children already has, also opens when `dependentsOf` is not empty, and its text adds the count ("1 task in the plan depends on it", provisional); a linked edit past a plan's limit shows its field error there or at the name being committed.

## Risks / Trade-offs

- [The two changes merge with names or behaviour other than this design's] → Group 0 checks each name and stops; the design is revised with `/opsx:update` before any code.
- [Ajv's strict mode refuses a definition's `parameters` beside the widget schemas, or the `$ref`s into `gantt-props`] → The first contract task compiles them; the fallback, as in `gantt-widget`'s design, is the definitions written into the parameters, with a test that both accept and refuse the same values.
- [The widening wires the expansion differently from decision 4] → The function, its map and the fold have the inputs and outputs the core spec names, and "Handed on" lists them; the widening revises them through its own change if it must.
- [A linked write on an answered question the user revises starts from the plan as sent, dropping the answer's plan edits] → The board carries what each item shows (decision 11, option A; integration session, 2026-11-03), and `linkedPlans` reads it.
- [On a question the user revises, a widget whose edits bring an item back to the agent's props as sent writes no draft value for it (`undefined`), so the item shows its answer's value again: a revision cannot take one item back to its props as sent (option A's limit, found in task 8.1)] → Accepted by the integration session on 2026-11-03; before option A, the plan showed its props as sent once the revision started. Handed on to `widget-answers`.
- [A plan-link write lands while the plan's question is disabled] → The Tree and the plan share their question, so both are disabled together; the rules are called only from edits the Tree allows.
- [`onValuesChange` lets one component write another's draft] → It is bound to the component's own question, an item outside it changes nothing and is reported, and only the Tree uses it, through `plan-link.ts`.
- [The `tree` chunk now needs `board-graph` and `compute` on every board with a Tree] → The sizes are recorded; a later change can split a `wbs` component chunk if a plain Tree board's size matters (proposal, open question 15).
- [Rounding to two decimals in the view differs from a `ROUND` formula] → The view calls the evaluator's own `ROUND` (`roundNumber`), which reads the value to 15 significant digits as Excel does; `compute`'s test checks it over the approved values and over halves such as 2.675 and 1.005.
- [A leaf turned parent leaves its dependents in error] → It is visible and does not block the answer (AD-13); proposal, open question 13, offers the alternative.
- [The fixtures and the approved answer differ in operation order] → Compared as a set, as `tree-widget` does; the diff's own order is checked separately.
